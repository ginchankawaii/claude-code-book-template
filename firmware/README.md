# MindClip DIY — ファームウェア書き込みガイド（電子工作がはじめての人向け）

自作ウェアラブル音声ロガー **MindClip DIY** の Phase 1 ファームウェア（`mindclip/`）を
**書き込み → 設定 → 疎通確認 → 消費電流の実測ゲート**まで通すための手順書です。
コマンドは1行ずつコピペできる形で書いてあります。

- **仕様の「正」は** [`SPEC.md`](SPEC.md)（634行の確定仕様）です。挙動の理由を知りたくなったら必ずそちらを見てください。
- **ハードの組み立て**は [`../hardware/README.md`](../hardware/README.md)、
  **サーバ側**は [`../voice-logger/README.md`](../voice-logger/README.md) です。

> **前提**: [`../hardware/README.md`](../hardware/README.md) の §8.2〜§8.5（テスト1〜4:
> Lチカ・スイッチ・SD・マイク）が**全部通っていること**。
> ここが通っていない状態でこのファームを焼いても、原因がハードかソフトか切り分けられません。

## 0. 全体の流れ

```
[1] Arduino IDE を入れる         ─┐
[2] ボード設定（PSRAM=OPI が必須）│  PCでの作業
[3] ファームを書き込む            ─┘
[4] サーバ(voice-logger)を立てる  ← PKIと共有鍵をここで作る
[5] シリアルモニタで設定を入れる  ← WiFi / URL / 証明書 / 鍵
[6] test wifi → test server → 実録音 → 同期の通し確認
[7] USB電流計で10分平均を測る（28mAゲート）
```

**[4] を [5] より先にやってください。** デバイスに入れる証明書と共有鍵はサーバ側で作るためです。

## 1. 用意するもの

| もの | 補足 |
|---|---|
| 組み上がった MindClip 本体 | hardware/README §8 のテスト1〜4が通っていること |
| **データ通信対応の USB-C ケーブル** | 充電専用ケーブルだと**PCがデバイスを認識しません**（よくある詰まり） |
| PC（Windows / macOS / Linux） | Arduino IDE か arduino-cli が動けばOK |
| microSDカード | **FAT32・32GB以下**。exFATはマウントできません |
| サーバ機 | `voice-logger` が動く常時稼働PC。**デバイスと同じLAN・2.4GHz帯に届くこと** |
| USB電流計（bom の T9） | §7 の実測ゲートで使う。**これが無いとゲートを判定できません** |
| USB-ACアダプタ | 電流測定用。PCのUSBポートは電流が変動して平均が読みにくい |

## 2. Arduino IDE のセットアップ

### 2.1 IDE とボードパッケージ

1. [Arduino IDE 2.x](https://www.arduino.cc/en/software) をインストールします。
2. **ファイル → 基本設定 → 追加のボードマネージャのURL** に以下を貼ります。
   ```
   https://espressif.github.io/arduino-esp32/package_esp32_index.json
   ```
3. **ツール → ボード → ボードマネージャ** で「esp32」を検索し、
   **esp32 by Espressif Systems** の **3.x 系**をインストールします（数分〜十数分かかります）。
   - 検証済みのバージョンは **3.3.11** です。2.x 系では API が違うためコンパイルが通りません。
4. **ツール → ボード → esp32 → XIAO_ESP32S3** を選びます。

### 2.2 XIAO ESP32S3 特有の設定（ここを間違えると「動くけど要件を満たさない」状態になります）

**ツール** メニューを上から順に、次の表のとおりに設定してください。

| 設定項目 | **必ずこの値** | 間違えるとどうなるか |
|---|---|---|
| **PSRAM** | **OPI PSRAM** | **最重要**。既定は `Disabled` です。無効のまま焼くと `ps_malloc()` が NULL を返し、録音バッファが 60秒 → **5秒に縮退**します（SPEC §7 E12）。省電力要件2「30〜60秒ためてまとめ書き」を満たせません。**シリアルの `[stat]` 行の `buf=` が `60s` でなく `5s` になっていたらここです** |
| **USB CDC On Boot** | **Enabled** | Disabled だとシリアルモニタに**何も出ません**。§5 のプロビジョニングが一切できなくなります |
| Flash Size | 8MB (64Mb) | 書き込みに失敗する／起動しない |
| Partition Scheme | **Default with spiffs (3MB APP/1.5MB SPIFFS)**（既定のまま） | 既定の `default_8MB` を使います（APP領域 3,342,336バイト）。NVS 20KB に証明書3本＋鍵が入る前提です（§9.1 参照） |
| Upload Speed | 921600（失敗するなら 115200 に下げる） | 書き込み中に止まる |
| CPU Frequency | 240MHz（既定のまま） | ファームが起動直後に `setCpuFrequencyMhz(80)` で 80MHz に落とすので、IDEの設定は既定で構いません |
| Core Debug Level | なし（None） | ログが増えて電流が増えます |

5. USB-Cケーブルで XIAO と PC を繋ぎ、**ツール → ポート** で出てきたポートを選びます。

### 2.3 スケッチを開く

**ファイル → 開く** で `firmware/mindclip/mindclip.ino` を選びます。
タブが `mindclip.ino` / `app.cpp` / `recorder.cpp` … と並べば正しく開けています。

> `mindclip.ino` の中身がほぼコメントなのは意図的です。実装は `.cpp` に置いています
> （理由は [`BUILD_ENV.md`](BUILD_ENV.md)。`.ino` に関数定義を書くとプロトタイプ生成が壊れる環境があるため）。

### 2.4 arduino-cli を使う場合

```sh
arduino-cli core install esp32:esp32@3.3.11

# ★ FQBN には必ず :PSRAM=opi を付ける（付けないと PSRAM 無効でビルドされます）
arduino-cli compile --fqbn esp32:esp32:XIAO_ESP32S3:PSRAM=opi firmware/mindclip

# 書き込み（ポート名は環境に合わせて。macOS は /dev/cu.usbmodem*、Windows は COM3 等）
arduino-cli upload  --fqbn esp32:esp32:XIAO_ESP32S3:PSRAM=opi -p /dev/ttyACM0 firmware/mindclip

# シリアルモニタ（改行は LF、ボーレート 115200）
arduino-cli monitor -p /dev/ttyACM0 -c baudrate=115200
```

コンパイルが通ったときの実測サイズ（2026-08-28 / core 3.3.11 / `PSRAM=opi`）:

```
Sketch uses 1105621 bytes (33%) of program storage space. Maximum is 3342336 bytes.
Global variables use 53896 bytes (16%) of dynamic memory, leaving 273784 bytes for local variables.
```

警告を確認したいときは **`-v` を付けないと1行も表示されません**（詳細は [`BUILD_ENV.md`](BUILD_ENV.md)）:

```sh
arduino-cli compile -v --warnings all --fqbn esp32:esp32:XIAO_ESP32S3:PSRAM=opi firmware/mindclip
```

## 3. 書き込み

### 3.1 通常の手順

1. **スライドスイッチを「録音ON」側**（GPIO2 = LOW）にしておきます。
   OFF のまま起動すると、ファームは同期を試みてすぐ deep sleep に入り、シリアルが切れます。
2. Arduino IDE の **→（書き込み）ボタン**を押します。
3. `Hard resetting via RTS pin...` が出れば完了です。
4. **ツール → シリアルモニタ**（**115200 baud / 改行コード = LF**）を開きます。

起動直後、シリアルに次のような行が出れば成功です。

```
[BOOT] -> RECORDING (buf=60s psram=1 rtc_valid=0)
```

- `buf=60s` … 録音バッファが60秒ぶん取れている（**`5s` なら PSRAM が無効**）
- `psram=1` … PSRAMからバッファを確保できた
- `rtc_valid=0` … まだ時刻を知らない（初回は正常。同期すると `1` になります）

失敗しているときは代わりに `[BOOT] SD mount failed` / `[BOOT] I2S init failed` /
`[BOOT] buffer degraded -> 5s` のいずれかが出ます。

### 3.2 ポートが出てこない / 書き込めないとき（ブートローダモード）

XIAO の基板上には **B（BOOT）** と **R（RESET）** の2つの小さなボタンがあります。

1. **B を押したまま**、USBケーブルをPCに挿す
   （既に挿さっているなら、**B を押したまま R を押して離し、最後に B を離す**）
2. PCに新しいシリアルポートが現れるので、**ツール → ポート**で選び直す
3. 書き込む
4. **書き込み後に R（RESET）を1回押す**（ブートローダモードから通常起動に戻すため）

> **筐体に組み込んだ後はこの2つのボタンが押せません。** 書き込みに不安があるうちは、
> 筐体を閉じる前にこの手順で1回書き込んでおくと安心です。
> なお**通常の書き込みや設定変更にボタン操作は不要**です（§5 のプロビジョニングも
> 「USBを挿してEnterを押す」だけで、ボタンは使いません）。

### 3.3 つまずきポイント

| 症状 | 原因と対処 |
|---|---|
| ポートが一切出てこない | **充電専用ケーブル**の可能性が最も高い。別のケーブルを試す → それでもダメならブートローダモード（§3.2） |
| `A fatal error occurred: Failed to connect to ESP32-S3` | ブートローダモード（§3.2）。Upload Speed を 115200 に下げるのも有効 |
| 書き込めるがシリアルに何も出ない | **USB CDC On Boot が Enabled になっていない**（§2.2）。設定を直して焼き直す |
| 書き込み後、ポートが消える | 正常。ファームが起動して USB CDC を張り直すため。数秒待って**ポートを選び直す** |
| 書き込み直後に LED が高速点滅し続ける | プロビジョニングモードに入っています（シリアルモニタが起動時に何か送ったため）。`reboot` と打つか R を押せば通常動作に戻ります |
| コンパイルエラー `'I2S_MODE_PDM_RX' was not declared` | ボードパッケージが **2.x 系**。3.x 系（3.3.11 推奨）に更新する |

## 4. サーバ側の準備

デバイスは **mTLS（クライアント証明書）と 共有秘密HMAC の両方**が揃わないと1バイトも送りません
（SPEC §6.1）。先にサーバ側で「CA・サーバ証明書・デバイス証明書・共有鍵」を作ります。

### 4.1 voice-logger を入れる

```sh
cd voice-logger
pip install -e .            # もしくは python -m pip install -e .
python -m pytest tests/ -q  # 57件パスすれば動作環境はOK
```

### 4.2 プライベートCAと証明書を作る

**`192.168.1.10` は、サーバ機の実際のLAN IPに置き換えてください。**
（IPが変わると証明書を作り直すことになるので、ルータでDHCP固定にしておくと楽です）

```sh
mkdir -p ~/voice-logger/pki && cd ~/voice-logger/pki

# CA
openssl req -x509 -newkey rsa:2048 -nodes -days 3650 -subj "/CN=MindClip CA" \
  -keyout ca.key -out ca.crt

# サーバ証明書（CN と SAN はサーバのLAN IP）
openssl req -newkey rsa:2048 -nodes -subj "/CN=192.168.1.10" -keyout server.key -out server.csr
echo "subjectAltName=IP:192.168.1.10" > server.ext
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 3650 \
  -extfile server.ext -out server.crt

# デバイス証明書（CN はデバイスID）
openssl req -newkey rsa:2048 -nodes -subj "/CN=mindclip-01" -keyout device.key -out device.csr
echo "extendedKeyUsage=clientAuth" > device.ext
openssl x509 -req -in device.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 3650 \
  -extfile device.ext -out device.crt

# 共有秘密（HMAC）— ★デバイス側の `gen hmac` ではなく、こちらで作った値を使うのが正
voice-logger serve --gen-key > hmac.key
cat hmac.key      # 64桁のhex。§5 でデバイスに貼り付ける
```

### 4.3 config.toml を書く

`voice-logger/config.example.toml` をコピーして `[ingest]` を埋めます。

```toml
[ingest]
host = "192.168.1.10"     # 既定は127.0.0.1。デバイスから届かせるにはLAN IPを明示する
port = 8443
tls_cert = "~/voice-logger/pki/server.crt"
tls_key  = "~/voice-logger/pki/server.key"
client_ca = "~/voice-logger/pki/ca.crt"
require_mtls = true
hmac_key_file = "~/voice-logger/pki/hmac.key"
```

### 4.4 起動する

```sh
voice-logger serve            # 受信API（デバイスが繋ぎに来る）
voice-logger watch            # 別ターミナルで。inbox を監視して文字起こし〜Obsidian追記
```

`serve` は **共有秘密が無い / TLS証明書が無い場合は起動を拒否します**（無認証で待ち受けません）。

サーバ機自身から生存確認:

```sh
curl --cacert ~/voice-logger/pki/ca.crt \
     --cert ~/voice-logger/pki/device.crt --key ~/voice-logger/pki/device.key \
     https://192.168.1.10:8443/healthz
# → {"ok": true}
```

> **ファイアウォール**: サーバ機で 8443/tcp を開けてください。ここを忘れると
> デバイス側は「サーバ応答なし（LED 2回点滅）」としか言いません。

## 5. プロビジョニング（WiFi・証明書・鍵の設定）

**SSID もパスワードもソースコードには一切書きません**（要件6）。すべてこの手順でデバイスのNVSに入れます。

### 5.1 プロビジョニングモードに入る

1. デバイスを **USB-C で PC に繋ぐ**
2. Arduino IDE の **シリアルモニタを開く**（**115200 baud / 改行コード = LF**）
3. XIAO の **R（RESET）ボタンを押す**（筐体に入れた後なら、USBを挿し直すだけでも同じ）
4. **3秒以内に、シリアルモニタの入力欄で Enter を押す**（何か1文字送れば入ります）
5. LED が**高速点滅**に変わり、次が表示されればOKです

```
=== MindClip provisioning mode ===
MindClip provisioning CLI
  help                       このヘルプ
  ...
mindclip>
```

> - 3秒待って何も送らなければ、そのまま通常動作（録音）に入ります。
> - **deep sleep からスイッチONで起きたときは、この3秒の待ち時間はありません**（USBが繋がっていないため。SPEC §9）。
>   設定を変えたいときは必ず **R を押す or USBを挿し直す**ところから始めてください。
> - **ボタンを押しっぱなしにする必要はありません。** 筐体に組み込んだ後でも設定変更できます。

### 5.2 設定を1つずつ入れる

`mindclip>` プロンプトに、**1行ずつ**次を打ちます（`OK: ...` が返ればその項目は保存済みです）。

**手順1: WiFi**（**2.4GHz帯のSSIDを指定してください。ESP32は5GHzに繋がりません**）

```
set wifi.ssid MyHomeAP
set wifi.pass MyWifiPassword
```

**手順2: サーバのURLとデバイスID**

```
set srv.url https://192.168.1.10:8443
set dev.id mindclip-01
```

- `https://` 必須です（`http://` は受け付けません）。
- 末尾の `/` は自動で落とします。`dev.id` は §4.2 で作ったデバイス証明書の CN と揃えてください。

**手順3: CA証明書を貼る**

```
paste srv.ca
```

と打つと `PEM を貼り付けてください。最後に "." だけの行で終了します` と出ます。
`~/voice-logger/pki/ca.crt` の中身を**まるごとコピーして貼り付け**、
最後に **`.`（ピリオド1文字だけの行）を送信**します。

```
-----BEGIN CERTIFICATE-----
MIIDxxxxxx...
-----END CERTIFICATE-----
.
```

→ `OK: srv.ca に 1204 バイト保存` のように返れば成功です。

**手順4: デバイス証明書と秘密鍵を貼る**（手順3と同じ要領で、`device.crt` と `device.key`）

```
paste dev.crt
paste dev.key
```

**手順5: 共有秘密（HMAC）を入れる**

§4.2 の `hmac.key` の中身（64桁のhex）をそのまま貼ります。

```
set hmac.key 3f9a...（64桁）
```

> デバイス側で生成する `gen hmac` もありますが、**サーバ側で作った値を入れるのが正**です
> （SPEC §10.2。デバイスの乱数源は無線オフ時に品質が落ちるため、`gen hmac` は
> `bootloader_random_enable()` で補ってはいるものの、長期鍵はOSのCSPRNGで作る方が確実です）。

**手順6: 確認して保存**

```
show
save
```

`show` の出力例（秘密は伏字になります）:

```
wifi.ssid        = MyHomeAP
wifi.pass        = ****word
srv.url          = https://192.168.1.10:8443
dev.id           = mindclip-01
srv.ca           = 1204 bytes
dev.crt          = 1180 bytes
dev.key          = **** (1704 bytes)
hmac.key         = **** (32 bytes)
cfg.led_duty     = 15 %
cfg.split_sec    = 600
cfg.gap_sec      = 3
cfg.buf_sec      = 60
cfg.vad_margin   = 9 dB
cfg.vad_hang     = 800 ms
cfg.vad_clamp    = 0
cfg.wifi_to_s    = 30
clk.last_epoch   = 0
st.boot_count    = 3
```

**`srv.ca` / `dev.crt` / `dev.key` / `hmac.key` の4つが「未設定 (unset)」でないこと**を必ず確認してください。
1つでも欠けると、起動時に **LED 5回点滅（E11: 設定不備）** になり同期しません。

## 6. 疎通確認

### 6.1 WiFi だけ試す

```
test wifi
```

- 成功: `OK: ip=192.168.1.23 rssi=-58 dBm (2140 ms)`
- 失敗: `NG: 接続できません（SSID/パスフレーズ/2.4GHz帯かを確認）`

`rssi` が **-75dBm より弱い**場合、装着位置によっては同期が不安定になります。
ルータとの距離や、金属に密着していないかを見直してください。

### 6.2 サーバまで通す（TLS + HMAC の確認）

```
test server
```

これは実際に `GET /api/v1/time` を叩きます（送るファイルが無ければ時刻取得だけで終わります）。

- 成功: `result=OK sent=0 carry=0` に続いて `OK: TLS/HMAC 検証成功。server epoch=...`
- 失敗時の見分け方:

| 表示 | 意味 | 見るところ |
|---|---|---|
| `result=NO_WIFI` | WiFiに繋がっていない（E4） | §6.1 に戻る |
| `result=AUTH_FAIL` | 401/403（E6）。鍵・証明書・デバイスIDの不一致 | `hmac.key` がサーバと同じか / `dev.id` と証明書CN / サーバの `client_ca` |
| `result=SERVER_FAIL` | 応答なし・5xx・TLS失敗（E5） | サーバが起動しているか / ポート8443が開いているか / `srv.url` のIPとポート / サーバ証明書のSANがそのIPになっているか |
| `result=NOT_PROVISIONED` | 設定が足りない（E11） | `show` で `srv.ca` / `dev.crt` / `dev.key` / `hmac.key` が埋まっているか |
| `result=SD_FAIL` | `/rec` を開けない（E18） | SDカードの異常。§8.2 へ |

**この2つが両方OKになるまで、筐体を閉じないでください。**
（hardware/README §8 の「テスト5」＝§8.6 に相当します）

### 6.3 録音から同期までを通しで確認する

1. `reboot` と打つ（またはRを押す）→ 通常動作に戻る
2. **スライドスイッチを ON（録音）**にして、20〜30秒ほど普通に喋る
   - LED: 無音のときは **4秒に1回パッと光る**、喋っている間は **弱く点灯しっぱなし**
3. **スイッチを OFF** にする
   - LED が **1Hz点滅（同期中）**になり、終わると消灯して deep sleep に入ります
4. サーバ側を確認します

```sh
ls ~/voice-logger/inbox/          # 20260828_213045.wav のような名前で届いていれば成功
```

5. `voice-logger watch` を動かしていれば、しばらくして Obsidian の Daily Note に追記されます。

> **初回だけの注意**: 工場出荷直後は時刻を知らないので、最初の録音は
> `UNSYNC-0001-001.wav` という名前でSDに保存されます。これは異常ではありません。
> 同期時にサーバが正しい時刻へリネームして `inbox` に置くので、SD上の名前は気にしなくて構いません（SPEC §6.3）。
> 一度同期すれば、以後は `YYYYMMDD_HHMMSS.wav` になります。

### 6.4 シリアルログの読み方（`[stat]` 行）

録音中は**60秒ごとに1行**、次の形式で状態が出ます（SPEC §4.2）。**§7 の実測ゲートではこの行を必ず記録してください。**

```
[stat] up=3600s D_cap=0.31 D_spi=0.010 cpu_busy=0.18 buf=60s floor=-58.2dB margin=9 wrote=118.2MB files=57 flush_ms_max=41 drops=0B
```

| フィールド | 正常な範囲 | 外れていたら |
|---|---|---|
| `buf` | **`60s`** | `5s` なら **PSRAMが無効**（§2.2 の設定ミス。要件2未達） |
| `flush_ms_max` | **90 未満** | 90以上ならSD書込が I2S DMA(90ms)を溢れさせ、**音が欠けます**。SDカードを速いものに替える／`SD_SPI_HZ` を見直す |
| `drops` | **`0B`** | 0でなければ書込が追いついていない（同上） |
| `D_cap` | 0.15〜0.35 | 常に0に近い＝マイクが拾えていない。常に1に近い＝騒音下（`margin` が上限12に張り付く） |
| `cpu_busy` | 小さいほど良い | **`I_idle` の代理指標**。28mAを落としたとき、ここが大きければ「寝られていない」側の問題 |
| `D_spi` | 0.01〜0.05 | 大きければ書込が遅い（`flush_ms_max` と一緒に見る） |
| `files` / `wrote` | — | 1日300件・0.6GB前後が想定（SPEC §3.2） |

### 6.5 LEDの意味（早見表）

| LEDの様子 | 状態 |
|---|---|
| 4秒に1回、短くパルス | 録音中・無音（LISTEN）。**正常** |
| 弱く点灯しっぱなし | 録音中・発話検出（CAPTURE）。**正常** |
| 1秒周期で点滅 | WiFi同期中 |
| 通常表示＋10秒ごとに2回点滅 | RTC未同期のまま録音中（E9）。まだ一度も同期していない状態 |
| **3回点滅＋1.5秒休み**（繰り返し） | **FAULT**: SDが無い/満杯/書込エラー、またはマイク(I2S)の異常 |
| 2回点滅を10秒 → 消灯 | WiFiに繋がらなかった / サーバが応答しなかった（E4/E5）。持ち越して sleep |
| 5回点滅を10秒 → 消灯 | **認証失敗**（E6）。鍵・証明書・dev.id を見直す |
| 起動時に5回点滅 | **NVS未設定**（E11）。§5 のプロビジョニングが済んでいない |
| 起動時に4回点滅 | **PSRAM確保失敗**（E12）。§2.2 の PSRAM 設定を確認 |
| 高速点滅（5Hz） | プロビジョニングモード |
| 消灯 | deep sleep（スイッチOFF）。正常 |

## 7. 実測ゲート: 平均電流 28mA

[`../hardware/ELECTRICAL.md`](../hardware/ELECTRICAL.md) §2.2 は
**「装着日相当の使い方で電池側の平均電流 ≤28mA」**を、**筐体を確定して量産印刷する前の必須ゲート**として課しています。
根拠は「一晩10時間の充電で戻せるのは 50mA×10h = 500mAh、装着15時間なら平均33mAが上限、そこに安全代を見て28mA」です。

> **現時点では合否が決まっていません。** SPEC §8.3 の見積では録音時平均は
> **21.5〜30.4mA（中央値およそ26mA）**のレンジで、**28mAはこのレンジの内側**にあります。
> 「余裕がある」と書いていた初期の記述は撤回済みです（SPEC §8.2/§8.3）。**実測してください。**

### 7.1 測り方（USB電流計・推奨）

1. **電池を繋いでいない状態**で測るのが最も簡単です。
   すでに電池を付けている場合は、**充電が終わって赤LEDが消えるまで待ってから**測ります
   （充電中は 50mA が上乗せされて読めません）。
2. **USB-ACアダプタ** ← USB電流計 ← デバイス、の順で挟みます（PCのUSBポートは使わない）。
3. **このファーム（`firmware/mindclip/`）で、10分以上の平均電流**を読みます。
   積算容量(mAh)が出る電流計なら `平均電流 = 積算mAh ÷ 経過時間(h)` が最も正確です。
   - **hardware/README §8.5 のテスト4（VADもバッファも無い連続書込スケッチ）で測ってはいけません。**
     省電力要件2/3の効果をまったく評価できません。
   - **同時に §6.4 の `[stat]` 行を記録してください。** 電流値だけでは落ちた原因を切り分けられません。
4. **「会話と無音が混ざった、実際の装着日に近いプロファイル」で測ります。**
   ずっと無音／ずっと喋りっぱなしでは VAD の効果を正しく評価できません。
5. **電池側の電流に換算します**（電流計が見ているのは5V側です）:
   ```
   電池側 ≈ USB側 × 5.0V × 効率 ÷ 3.8V ≈ USB側 × 1.1   （効率0.85と仮定）
   ```
   → **ゲート「電池側28mA以下」= USB電流計の読みで約25mA以下**。
   （効率0.85は仮定値です。厳密にやるなら電池ラインにテスターを直列に入れて測ります）

### 7.2 A/B で4条件測る

ビルド構成で数mA変わり、その数mAが合否を分けます（SPEC §8.4）。各10分平均で表にしてください。

| # | 構成 | 見るもの |
|---|---|---|
| 1 | `PSRAM=opi` + `USB CDC On Boot=Enabled`（既定） | **ゲート判定の本命** |
| 2 | `PSRAM=opi` + `USB CDC On Boot=Disabled` | USB Serial/JTAG の PHY が食っている分 |
| 3 | `PSRAM=disabled` + `CDC=Disabled` | オクタルPSRAMの常時消費（**測定専用**。バッファが5秒に縮退し要件2は満たしません） |
| 4 | 1 の構成で **SDカードを抜いて**起動（FAULT点滅のまま放置） | 「拡張ボード＋SD＝3mA」の内訳 |

### 7.3 落ちたときの切り分け（順番が大事）

**まず `[stat]` を見て、原因が「常時オンの床」か「喋りすぎ」かを確定させます。**

```
cpu_busy が大きい / D_cap は小さい   → I_idle（床）の問題 … (A)へ
D_cap が 0.5 を超えている            → VAD/騒音の問題    … (B)へ
flush_ms_max が 90 以上 / drops > 0  → SD書込が遅い      … (C)へ
```

**(A) 床（`I_idle`）が高い場合** — SPEC §8.4 の結論は「**28mAゲートの成否はほぼ `I_idle` で決まる**」です。この順に試します。

1. **`USB CDC On Boot = Disabled` でビルドし直して差分を測る**（上表の #1 vs #2）。**最も安い切り分け**です。
   ただし Disabled にすると §5 のプロビジョニングができなくなるので、**設定を全部入れ終えてから**にしてください。
2. `PSRAM=opi` / `disabled` の A/B（#1 vs #3）で `I_psram` の実額を出す。
   差が大きい場合の逃げ道は「バッファを内部DRAM 160KB(5秒)で回し、代わりに分割条件を短くする」ですが、
   **これは省電力要件2の再交渉が必要**です。実測してから判断してください。
3. SDスロットを空にして測る（#4）。「拡張ボード＋SD＝3mA」の内訳が分かります。
4. 長い無音時に `SD.end()` でSPIバスを落とす（**未実装**。再マウントに約80msかかるため既定では入れていません）。

> `esp_pm_configure()` による自動ライトスリープは**このArduinoコアでは使えません**
> （`sdkconfig` が `CONFIG_PM_ENABLE` 未設定で、DFS/tickless idle がビルドに入っていない）。対策候補から外してあります。

**(B) `D_cap` が高い場合** — VADのマージンを上げます（既定9dB、上限12dB）。

```
set cfg.vad_margin 11
```

ただし SPEC §8.4 のとおり、**`D_capture` を 100%→20% に下げても平均は 2.1mA しか下がりません**。
`D_cap ≤ 35%` の要件は主に **SD容量(0.6GB/日)・転送時間・SD寿命**の予算です。電流対策としては(A)を優先してください。
騒音下で `margin` を上げても効かない場合は §9 の既知の限界（絶対クランプ -25dBFS）に当たっています。

**(C) 書込が遅い場合** — SDカードを速いもの（信頼できるメーカーのClass10以上）に替えます。
`flush_ms_max ≥ 90` は電流よりも**音の欠落**の問題なので、電流ゲートより先に直してください。

### 7.4 それでもゲートを通らない場合（ELECTRICAL §2.2 のフォールバック）

**ファーム側の対策を尽くしてもダメなら、バリアントを変えます。**

- **slim(500mAh) → allday(800mAh) へ切り替え**
  ```sh
  MINDCLIP_VARIANT=allday python hardware/cad/mindclip_case.py
  ```
  電池はフットプリント（30×25mm）が同じで厚みだけ 5.0→8.0mm 変わるため、
  筐体の奥行きが 12.9→14.6mm になるだけで済みます。**body と lid の再印刷は必要**（backplate は共通）。
- **注意**: allday の 800mAh は「1日の消費上限を上げるもの」ではありません
  （一晩に戻せる充電量は 500mAh のままです）。効くのは
  ①省電力実装が間に合わない期間のマージン ②充電を忘れた日の余力 ③経年劣化代 としてです。
  **したがって 28mA 目標そのものはバリアントによらず変わりません。**
- それでも足りない場合は 703040(800mAh, 30×40×7mm) 等への格上げになりますが、
  高さ40mmは筐体高さ(49.4mm)に収まらず**全面的な再設計**になります。

## 8. トラブルシューティング

### 8.1 書き込めない

§3.3 の表を参照してください。**9割はケーブルかブートローダモードです。**

### 8.2 SDカードを認識しない（LED 3回点滅の FAULT）

シリアルに `[BOOT] SD mount failed` が出ます。

| 確認 | 対処 |
|---|---|
| カードが奥まで入っているか | 「カチッ」と押し込む |
| フォーマット | **FAT32**（exFATは不可）。32GB以下 |
| 拡張ボード | B2Bコネクタが斜めに刺さっていないか。一度抜いてまっすぐ押し直す |
| カード自体 | PCで読み書きできるか。安価なノーブランド品は初期不良が多い |
| 空き容量 | **50MB を切ると E2 で FAULT**（録音を止めます）。同期して減らすか、PCで古いファイルを退避する |
| 書込エラーが続く | `[REC] -> FAULT` のあと `[FAULT] retry failed (cause=1 ...)` が繰り返し出るなら不良セクタの可能性。**SPI速度を落とす**（`config.h` の `SD_SPI_HZ` を `SD_SPI_HZ_LOW`=10MHz へ）か、カードを交換 |

> FAULT でも**同期経路は生きています**。スイッチをOFFにすれば送信して容量を空けられます（SPEC §7 E2）。

### 8.3 WiFiに繋がらない（LED 2回点滅→消灯）

| 確認 | 対処 |
|---|---|
| 2.4GHz帯か | **ESP32は5GHzに繋がりません。** SSIDが5GHz専用でないか確認 |
| SSID/パスフレーズ | `show` で確認 → `set wifi.ssid` / `set wifi.pass` で入れ直す |
| 電波強度 | `test wifi` の `rssi`。-75dBm より弱いと不安定 |
| タイムアウト | 既定30秒。弱い環境なら `set cfg.wifi_to_s 45` |
| ステルスSSID / MACフィルタ | ルータ側の設定を確認 |

**仕様として、WiFiに繋がらないときはリトライしません**（ファイルをSDに残して即 deep sleep）。
外出先で他のAPを探し回って電池を減らさないためです（COMMS §4 / SPEC §7 E4）。

### 8.4 録音されない

| 症状 | 原因 |
|---|---|
| SDに `.wav` が1つもできない | スイッチがOFF側になっている（ON=LOW=録音）。hardware/README §8.3 のテスト2でどちら側がONか確認 |
| `[stat]` の `D_cap` がずっと 0.00 | マイクが音を拾えていない。**筐体のマイク穴（φ1.5mm×3）が塞がっていないか**。開口をφ2.0に広げる対策は hardware/README §8.5 |
| LED 3回点滅 + `[FAULT] retry failed (cause=2 ...)` | **E15/E13**: マイク(I2S)が5秒間データを返していない。断線か拡張ボードの接触不良。30秒ごとに再初期化を試みます |
| 2秒未満のファイルができない | **仕様です。** 物音の誤検出を捨てるため、2秒未満は作りません（SPEC §3.2） |
| ファイルが細切れ（数十秒ごと） | **仕様です。** 無音が3秒続くとファイルを分けます。ファイル内の時刻ズレを±3秒に抑えるための設計判断（SPEC §3.2）。1日300件前後になります |
| 起動時に LED 4回点滅 | **E12**: PSRAM未確保。§2.2 の PSRAM=OPI を確認（要件2未達のまま動いています） |

### 8.5 同期されない

**まず `test server` を実行して、result を見てください**（§6.2）。

| result / 症状 | 原因と対処 |
|---|---|
| `AUTH_FAIL`（LED 5回点滅） | サーバとデバイスの `hmac.key` が違う／`dev.id` と証明書CNが違う／サーバの `client_ca` がそのデバイス証明書を検証できない |
| `SERVER_FAIL`（LED 2回点滅） | `serve` が起動していない／8443がファイアウォールで閉じている／`srv.url` のIP・ポート違い／サーバ証明書のSANがそのIPでない |
| 起動時に LED 5回点滅 | **E11**: `srv.ca` / `dev.crt` / `dev.key` のどれかが未設定。`show` で4項目が埋まっているか確認 |
| `result=CARRY_OVER` が毎回出る | 送り切れていない。回線が遅い（19MBを60秒で送れない）／セッション15分上限に当たっている。次回に持ち越されるのでデータは消えません |
| 同期後もSDからファイルが消えない | **正常な安全側の動作**です。デバイスは **200応答かつsha256一致**を確認したときだけ削除します（SPEC §6.4） |
| サーバに届くが Daily Note に出ない | `voice-logger watch` が動いていない。`inbox/` にファイルがあるなら受信は成功しています |
| 同じファイルが毎晩3回送られ続ける | 恒久的に400になるファイルです。3セッション連続すると `.wav.bad` にリネームして送信対象から外します（E16）。**削除はしません**。SDカードの劣化を疑ってください |
| 同期が終わらない／deep sleepしない | スイッチのチャタリング（§9 の既知の課題）。スイッチのはんだ付けと配線を確認 |

> **サーバ側のログの見方**: `voice-logger serve` は 400/401/413/507 を返した理由をログに出します。
> デバイス側のLEDだけでは分からないときは、サーバのログを先に見てください。

## 9. 既知の課題・未検証事項

**実機で確認できていない項目と、仕様として割り切った制約を全部ここに書きます。**
（実装レビューで指摘され、意図的に直していない／実測待ちにした項目の一覧です）

### 9.1 実測して確定させる数値（すべて assumption）

| 項目 | 採用値 | 状況 |
|---|---|---|
| **28mAゲートの合否** | 未確定 | 録音時平均の見積は **21.5〜30.4mA（中央値 約26mA）**で、**28mAはレンジの内側**。実測するまで合否は決められない。「7.2mAの余裕」「25〜37%の余裕」という初期の記述は撤回済み（SPEC §8.2/§8.3） |
| `I_idle`（RF off・CPU idle@80MHz + 拡張ボード/SD + マイク） | 18mA | **最重要の未検証値**。SPEC §8.4 の結論は「ゲートの成否はほぼ `I_idle` で決まる。26mA以上なら VAD をどう詰めても不合格」 |
| `I_psram`（`PSRAM=opi` の常時消費） | 2〜5mA | **当初の予算から抜け落ちていた項**。要件2に必須のビルドオプションなので、#1 vs #3 の A/B で実額を出す（§7.2） |
| `I_sdw`（SPI書込中の増分） | 8〜16mA | 当初の +45mA は公式実測 54.4mA と矛盾するため**撤回**。逆算値であり依然 assumption |
| ΔCPU（240→80MHz の削減分） | 17〜18mA | assumption。レンジの広さの主因 |
| SD書込スループット | 1.0MB/s | **未実測**。PSRAM上の非整列バッファだと `sdmmc_write_sectors()` のバウンス経路に落ち 100〜300KB/s まで下がりうる。内部DRAMの整列バウンスバッファで回避しているが、**実機で `flush_ms_max < 90ms` を確認するまで確定値にしない** |
| USB Serial/JTAG（CDC On Boot=Enabled）の消費 | 未測定 | プロビジョニングに必須なので既定では切れない。28mAを落としたら**最初にここをA/B**（§7.3） |
| SDカード単体のアイドル電流 | 「拡張ボード＋SD＝3mA」に内包 | 未検証。SDスロットを空にして測れば内訳が分かる（§7.2 の#4） |
| LED予算 0.9mA | 過大（実効 約0.33mA） | 連続微灯はCAPTURE中だけで、LISTEN中は100ms/4000ms。**保守側にずれているので予算はこのまま**（隠れマージン約0.57mA） |
| NVSパーティション容量 | 足りる見込み | `default_8MB` の `nvs`=20KB に対しPEM3本＋鍵で約5KB、実効約16KBという**算術のみ**の見積。数KBのblobを5ページで回すのは既知の詰まりどころなので、**初回プロビジョニング時に実機で確認すること** |

### 9.2 仕様として割り切った制約

- **騒音下ではVADのデューティ・ガバナが効かない。** 判定閾値に絶対クランプ **-25dBFS** が掛かっているため、
  ノイズフロアが **-34dBFS を超える環境（騒がしいカフェ・電車内）では `cfg.vad_margin` を上げても閾値が1dBも動きません**。
  ただし `D_capture ≤ 35%` は電力要件ではなく **SD容量・転送時間・SD寿命**の予算なので、28mAゲートには影響しません。
  予算を守りたい場合は `set cfg.vad_clamp 1`（`D_capture > 0.50` で強制LISTEN。**既定は無効**）を使います。
- **「RAMに30〜60秒ためてまとめ書き」は名目上の達成。** 無音3秒で分割する設計のため、実際の書込は
  「発話1区切りごと」（数秒〜十数秒ぶん）で、SDが起きる周期を決めているのはバッファ容量ではなく
  **ファイル数（1日300件前後）**です。総書込バイト数は同じなので電力の結論は変わりませんが、
  `[stat]` の `files` / `flush_ms_max` を「45秒バッファの1回」と読み違えないでください。
- **長い無音での `SD.end()` は未実装。** ELECTRICAL §2.2 の「書込中以外はSDをアイドルに落とす」を
  能動的にはやっておらず、カードはマウントしたままです（再マウントに約80msかかるため）。
- **`esp_pm_configure()` による自動ライトスリープは使えません**（コアの `sdkconfig` が `CONFIG_PM_ENABLE` 未設定）。
  電流の逃げ道は §7.3 の (A) 1〜4 とバリアント変更だけです。
- **`duplicate:true` は sha256完全一致で返る**ため、理屈の上では「1バイトも違わない2本の別録音」は1本に潰れます。
  実機のマイクノイズがある限りまず起こりませんが、**マイク故障で全ゼロPCMが出た場合**は起こりえます（消えるのは無音ファイルだけ）。
- **nonceのリプレイ防止はサーバのプロセス内メモリのみ**（LRU 4096件/24h）。サーバ再起動後や4096件を超えた後は、
  古いnonceの再送が401になりません。**防御はボディsha256による冪等化**（再送しても `duplicate:true` で inbox は1本のまま）。
- **413/507 は「上限内なら」ボディを読み捨ててから返します。** 上限を超える送信は接続が切られるため、
  デバイスからはステータスの取れない送信失敗に見え、**一時障害と同じ扱い（リトライ→持越し）**になります。データは消えません。
- **`PSRAM=disabled` ビルドは測定専用**です（§7.2 の#3）。バッファが5秒に縮退し、省電力要件2を満たしません。

### 9.3 実装の細かい未対応（動作は安全側だが、仕様と数値が揃っていない）

- **スイッチのデバウンスは実効約180ms。** `swPollNonBlocking()` 自体は「20ms×3回一致」ですが、
  呼び出し元が `recorderPump()` 1周（約60ms）ごとに1回しか呼ばないため、確定まで約180msかかります
  （SPEC §2.2 の「20ms×3回」と実周期がずれています。動作は安全側）。
- **チャタリングするスイッチでは SYNCING↔RECORDING がピンポンしうる。** E14（デバウンス不成立5秒で
  録音側に倒す）の判定結果が同期中断（E8）にも使われるため、中断→録音→再びOFF検出→同期 を繰り返すと
  1周ごとに最大30秒のWiFi接続が走り、deep sleep に入れません。**レート制限やセッション失敗回数の上限は未実装**です。
  スイッチのはんだ付け・配線が怪しいときはここを疑ってください。
- **`.wav.rec` 復旧の削除しきい値が 1秒**（`AUDIO_BYTES_SEC`）で、SPEC §5.3 の `MIN_FILE_MS`（2秒）と一致していません。
  **保存する側に倒れている**ので音声は失われませんが、数値は揃っていません。
- **電源断からの復旧は1起動あたり32件まで。** 超過分はログ（`recover: >32 .wav.rec`）を出して次回起動に持ち越します。
  通常は同時に1件しか存在しないので実害はありません。
- **`config.h` / `vad.cpp` のコメントに旧NVSキー名 `cfg.vad_hardclamp` が残っています。**
  実際のキーは **`cfg.vad_clamp`** です（NVSのキー名上限15文字に収めるため改名済み。旧名は保存/読出が必ず失敗します）。
- **`.wav.bad` に隔離されたファイルは自動では消えません**（削除は「ACK確認後」と「2秒未満」だけという共通ルールのため）。
  SDカードを直接PCに挿して回収・削除してください。Phase 0 のパイプラインは `.bad` を拾いません。

### 9.4 このガイド自体の未検証

- **このデバイスはまだ実機で組まれていません。** §7 の実測ゲートは**誰も通していません**。
  最初の1台を組む人は、§7.2 の4条件の表を埋めて、`hardware/README.md` §8.7 と
  `SPEC.md` §8 の数値を実測値で置き換えてください。
- マイク開口（φ1.5mm×3）を通した集音性能は未実測です（hardware/README §9.2）。
