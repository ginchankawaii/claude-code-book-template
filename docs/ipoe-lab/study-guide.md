## 0. この虎の巻の使い方

**やってはいけない使い方**: 第1章から順に読む。→ 25章+付録あり、470ページ。若手は必ず折れます。

**推奨**: 下の「3回シリーズ」の順に、**ラボで現象を見てから該当節を読む**。
IPv6 は抽象的な仕様の塊なので、`tcpdump` で本物のパケットを見た後に読むと定着率が段違いです。

```
   ① ラボで壊す/直す  →  ② 「なんで?」が生まれる  →  ③ 教科書の該当節を読む  →  ④ もう一度ラボ
```

各回の資料は `docs/ipoe-lab/slides/toranomaki.pptx`(自動生成)。
生成し直す場合は**リポジトリのルートから**:

```
python3 docs/ipoe-lab/slides/build-toranomaki.py docs/ipoe-lab/slides/toranomaki.pptx
```

`fe80::` とグローバルの違いが言える。

#### 演習 1-A: CPE の WAN に何が付いているか(**実測済み / サイクル 2**)

1. **CPE**(OpenWrt-CE または実機。クライアント VM ではありません)で PPPoE 接続する
   - 認証情報: `user1@isp-a.example` / `pass1` / サービス名 `lab-isp`([build.md](build.md) §2)
2. CPE の WAN 側インターフェースで `ip -6 addr show` を実行(実機なら `show ipv6 interface brief`)
3. 出てきたアドレスを 1 個ずつ「これは何か」に分類する

**ラボの仕掛けと、そこから学ぶこと(講師が必ず説明する)**

- ラボの BRAS は `ipv6=deny`([`lab/ipoe/bras/accel-ppp.conf`](../../lab/ipoe/bras/accel-ppp.conf))。
  つまり **PPPoE セッション自体では IPv6 は一切降りません**(= IPv6 非対応の PPPoE 契約の再現)。
- しかし CPE の WAN は NGN アクセス網の L2 に直結しており、**NGN-SIM の radvd は ra/pd どちらのモードでも
  常時 RA を流しています**([`lab/ipoe/ngn/setup-ngn.sh`](../../lab/ipoe/ngn/setup-ngn.sh))。
  そのため **PPPoE とは無関係に、NGN 由来のグローバル IPv6 が付いている可能性があります。**
- これは実網の姿と同じで、**付録 A.1「NTT 閉域網 IPv6 フォールバック問題」/ A.2「マルチプレフィックス問題」の正体**です。
  「ISP の契約とは別に、NGN の IPv6 が勝手に来ている」という状況を最初に体感させるのが、この演習の狙いです。

> **実走結果(サイクル 2 で確認済み。演習の進め方に影響するので必読)**
>
> RA は **PPPoE 接続中も CPE の WAN に届いています**。NGN-SIM 側で実測:
>
> ```
> tcpdump -ni eth1 -nn "icmp6[icmp6type]==134"
> 09:03:28.741815 IP6 fe80::ac:ff:fe00:1 > ff02::1: ICMP6, router advertisement, length 88
> 09:03:49.314972 IP6 fe80::ac:ff:fe00:1 > ff02::1: ICMP6, router advertisement, length 88
> ```
>
> **ただし OpenWrt を CPE にすると、既定のままでは GUA が付きません。**
> PPPoE を上げた瞬間に netifd が搬送路の物理 NIC の `disable_ipv6` を 1 にするため、
> IPoE 側(`wan6`)が落ち、**リンクローカルまで消えます**。
>
> ```
> odhcp6c[6555]: Failed to send RS (Network unreachable)
> cat /proc/sys/net/ipv6/conf/eth1/disable_ipv6 → 1
> ```
>
> 対処は `/etc/config/network` に 1 セクション足すだけです([build.md §5](build.md) に反映済み):
>
> ```
> config device
>         option name 'eth1'
>         option ipv6 '1'
> ```
>
> **演習としてはこれ自体が良い教材です。**「RA は届いているのに IPv6 が付かない」
> という状況を tcpdump で切り分けさせると、
> 「届いていない」と「受け取れていない」の違いが体で分かります。
> 当日の進行では、まず既定のまま踏ませてから対処を入れる順で見せてください。
>
> プレフィックスは PD 方式なら `2001:db8:100a:500::/56`(CPE の `br-lan` に `/60` が切り出される)、
> RA 方式なら CPE WAN に `2001:db8:1014:300::/64` が付きます。

**Temporary アドレスについて**: lab-client(Ubuntu Server)では既定で生成されません。
見せたい場合は `sudo sysctl -w net.ipv6.conf.<if>.use_tempaddr=2` を打つか、宿題の自宅 PC で確認させてください。

**宿題**: 自宅の PC で IPv6 アドレスを見て、種類を数えてくる。
Windows は `ipconfig /all`、Mac/Linux は `ip -6 addr` か `ifconfig`。
自宅回線が IPv6 非対応・管理画面に入れない場合は**スマホのテザリング**で代替可(モバイルは IPv6 が来ていることが多い)。

#### 演習 2-A: 4 兄弟をキャプチャする(**実測済み / サイクル 2**)

**NGN-SIM の方式を切り替えるときは、VNE 側(BR)も同じ組み合わせに合わせて再実行しないと IPv4 が全断します。**
必ず 2 コマンド 1 組で実行してください([build.md](build.md) §3 の期待値表)。

| NGN-SIM モード | ユーザプレフィックス | 共有 IPv4 | PSID | VNE 側の実行方法 |
|---|---|---|---|---|
| `pd`(ひかり電話あり) | `2001:db8:100a:500::/56` | `198.51.100.10` | 5 | `sudo ./setup-map-br.sh`(既定値) |
| `ra`(ひかり電話なし) | `2001:db8:1014:300::/64` | `198.51.100.20` | 3 | `sudo CE_MAP_ADDR=2001:db8:1014:300:0:c633:6414:3 CE_SHARED_V4=198.51.100.20 ./setup-map-br.sh` |

```
# NGN-SIM で(root 必須)
# ★ 先に Kea のリースを消すこと。残っていると Renew に旧プレフィックスで応答し、
#   「切り替えたのに CPE が前のプレフィックスのまま」で当日ハマります
sudo systemctl stop kea-dhcp6-server
sudo rm -f /var/lib/kea/kea-leases6.csv*
sudo systemctl start kea-dhcp6-server

sudo ./lab/ipoe/ngn/setup-ngn.sh ra     # ひかり電話なし相当
# ↑ に切り替えたら VNE でも必ず(値は build.md §3 の表から取る)
sudo CE_MAP_ADDR=2001:db8:1014:300:0:c633:6414:3 CE_SHARED_V4=198.51.100.20 \
     ./lab/ipoe/vne/setup-map-br.sh

# CPE 側でキャプチャしながら再接続
sudo tcpdump -nn -i <ACCESS_IF> 'icmp6 or udp port 546 or udp port 547'
```

- **実行ホストとインターフェース名を事前に確定しておくこと。** NIC 名は環境で変わるため
  `lab/ipoe/detect-ifs.sh` が MAC から解決します。OpenWrt の `wan` は論理名で、tcpdump には実体名(`eth1` など)が必要です。
- **OpenWrt には tcpdump が既定で入っていません。** 演習で使うなら事前に導入しておくこと
  (ラボ内にインターネットはないので `opkg` は管理経路が必要。[build.md](build.md) §5 参照)。
- `setup-ngn.sh` は毎回 `apt-get update && apt-get install` を走らせます。**管理経路からインターネットに出られること**が前提で、
  出られないと演習中にスクリプトが落ちます。事前に一度実行してパッケージを入れておいてください。

**見てほしいこと**: RS → RA が飛ぶか。PD なら Solicit → Advertise → Request → Reply の 4 往復が見えるか。
`ip -6 route` と CPE の LAN 側アドレスを比べ、**RA 方式だと LAN に配れる /64 が無い**ことを確認する
(だから PD が必要。ラボでは odhcpd の relay で回避している。[build.md](build.md) §5)。

#### 演習 2-B: DUID の罠(講師が仕掛ける・15分)

**ラボ既定ではこの癖は再現しません**([README.md](README.md) / [test-matrix.md](test-matrix.md) §3 Phase 1 手順 5)。

> ### ⚠ 参照 CE が OpenWrt のままだと、DROP を有効にしても罠は発動しません(サイクル 5 実測)
>
> キャプチャで確認したところ、**OpenWrt は DUID-LL(type 0003)を送っています**。
>
> ```
> client-ID hwaddr type 1 02ac00000010            ← OpenWrt = DUID-LL
> server-ID hwaddr/time type 1 time 839664689 ... ← Kea     = DUID-LLT
> ```
>
> DROP クラスは「**DUID-LL でないもの**を落とす」ので、OpenWrt は素通りして
> 普通に PD を取得します。「OpenWrt は DUID-LLT を送る」という当初の想定は誤りでした。

**当日の見せ方は次のどちらかにしてください**:

- **(a) 反転デモ(準備が楽。OpenWrt でそのまま見せられる)**
  `kea-dhcp6.conf` の DROP のテストを反転して「**DUID-LL を落とす**」にする。
  OpenWrt が無応答でハマるところを見せられます。
  「実網は逆向きに厳しい」と説明を添えてください
  → `{ "name": "DROP", "test": "substring(option[1].hex, 0, 2) == 0x0003" }`
- **(b) 実物デモ**: DUID-LLT を送る CPE(市販ルータや Windows のクライアント)を
  用意し、既定の DROP テストのまま無応答を見せる

手順(どちらの場合も):

1. `lab/ipoe/ngn/kea-dhcp6.conf` の `client-classes`(DROP クラス)のコメントを外す
2. Kea を再起動 → CPE から Solicit → **エラーではなく完全な無応答**になることを見せる
3. **終わったら必ず戻す**(残すと以降の演習で PD が降りません)

用語: **DUID-LL** = MAC アドレスベース、**DUID-LLT** = MAC + 生成時刻。NGN は LL(type 0003)しか受けないという報告が多い。
ただしこれは**独立した複数の報告に基づく実網の挙動**で、NTT の公開仕様として確認できたものではありません
([research-notes.md](research-notes.md))。断定せず「そういう報告が多いので DUID-LL で試す」と伝えてください。

#### 方式判定は 2 段(ここを間違えると事故る)

```
① ひかり電話は?          なし → RA 方式(/64)
                          あり → HGW が来る → ② へ

② 終端するのはどっち?    HGW で終端     → 配下ルータは PD を要求しない(ブリッジ/ルータモード)
                          配下ルータで終端 → HGW 側の IPoE を止める
```

**「ひかり電話あり = 配下ルータに PD を設定」は誤りです。**
HGW が PD を取るので、配下でも PD を要求すると**二重終端**(レシピ R7)になります。
ヒアリング #2「HGW 型番・VNE 対応機能の内蔵有無」が必須なのはこのためです
([test-matrix.md](test-matrix.md) §1)。

#### 演習 3-A: ポートを数えて、失敗させる(**実測済み / サイクル 5**)

1. **CPE に降りたプレフィックスから共有 IPv4 と PSID を確認**し、§1.5 の計算と一致するか照合する
2. **ポート集合を紙に書き出し、飛び飛びであることを目で見る**(240 個 = 16 個 × 15 ブロック)。
   **`a=0` のブロック(0-4095)が存在しない**ことに気づかせる — well-known ポートは原理的に使えません
3. **R3(ポート制限)を再現する。OpenWrt が CE なら enforce 用の nft は不要です**:

   ```bash
   for i in $(seq 20); do curl -s --limit-rate 1k -m 30 http://203.0.113.80/big.bin -o /dev/null & done
   ```

   > **⚠ 紙に書いた 240 とは違う数字が出ます。実測では 17 本目以降が失敗します(成功は 16 本)。**
   > これは OpenWrt の実装の癖で、生成される 15 本の nft `snat` ルールがすべて同じマッチ条件のため、
   > nftables の終端判定により**先頭ブロック(4176-4191)しか使われない**からです。
   > CPE で `nft list ruleset | grep ubus:wanmap` を見せると、`nat 1` だけ packets が増えて
   > **`nat 4` 以降が 0 のまま**であることが一目で分かります。
   >
   > **「割当の構造値(240)」と「その CE が実際に使える数(16)」は別物**という、
   > 実務でいちばん効く教訓がここで手に入ります。実機 CE では**必ず数え直してください**
   > ([build-log.md](build-log.md) バックログ 10)。
   >
   > 実機 CE が 240 を正しく使えた場合に、網側で強制したいときだけ
   > [test-matrix.md](test-matrix.md) R3 の `map-enforce` を使います(**戻し忘れ厳禁**)。

4. **R4(DS-Lite でポート開放不可)**: CPE でポート開放を設定し、INET-SIM 側から届かないことを確認

   > **前提が 2 つあります**([test-matrix.md](test-matrix.md) R4 に実測付きで記載):
   > ① **VNE と INET-SIM が別 VM であること**(`SPLIT_INET=1`)。同居だと網側 NAT が効かず**逆の結果**になります。
   > `EXPECT_SRC4=203.0.113.1 ./run-checks.sh` で出口が AFTR 側になっていることを先に確認
   > ② **対照実験**。待受を `sudo systemd-run --unit=r4test --collect python3 -m http.server 8000 --bind 0.0.0.0`
   > で起動し(**多段 ssh 越しの `nohup &` では起動しません**)、**LAN 内から到達できることを先に見せてから**外から叩きます。
   > これをやらないと「そもそも受け側がいない」のか「仕様どおり不達」なのか区別できません
5. **MTU の確認**: `ping -M do -s 1432`(通る)と `-s 1472`(通らない)、および `run-checks.sh` の 5MB 転送
   - `curl` 単体だと「遅い」と「落ちる」の区別がつかないので、判定は `run-checks.sh` に任せる
6. **結果を [test-matrix.md](test-matrix.md) §5 実績表に記録する**。記録しないと次の案件で活きません

## 1.5 MAP-E の計算(第3回の中核・これが無いと演習ができない)

**ラボのルール**([build.md](build.md) §3):

| パラメータ | 値 |
|---|---|
| rule-ipv6-prefix | `2001:db8:1000::/40` |
| rule-ipv4-prefix | `198.51.100.0/24` |
| ea-len / psid-offset | 16 / 4 |

**ポート数の式**:

```
psid-len = ea-len − (32 − IPv4プレフィックス長) = 16 − (32 − 24) = 8
1ブロックのポート数 = 2^(16 − offset − psid-len) = 2^(16 − 4 − 8) = 2^4 = 16
ブロック数           = 2^offset − 1              = 2^4 − 1        = 15   ← 0 はwell-known回避で使わない
使えるポート数       = 16 × 15 = 240
```

**PD 方式(`2001:db8:100a:0500::/56`)の場合の導出**:

```
① EA bits = プレフィックスの bit40〜55 を取り出す →  0x0a, 0x05
② 共有IPv4 = rule-ipv4-prefix(198.51.100.0/24)の下位8bit に 0x0a を入れる → 198.51.100.10
③ PSID     = 残り 8bit                                                     → 5
④ ポート集合 = 0x1050-0x105F(4176-4191), 0x2050-0x205F, … 0xF050-0xF05F   → 16個 × 15ブロック
```

**RA 方式(`2001:db8:1014:0300::/64`)なら** → 共有 IPv4 `198.51.100.20` / PSID 3。

**実サービスの実績値**([research-notes.md](research-notes.md) §2):

| サービス | 方式 | 使えるポート数 |
|---|---|---|
| v6プラス(JPIX。旧 JPNE) | MAP-E(draft-03互換) | **240**(16×15、offset=4 相当) |
| OCNバーチャルコネクト(NTT Com) | MAP-E(draft-03互換) | **1008**(16×63、offset=6 相当) |

> **240 は少ないです。** ブラウザは 1 タブで数十本張ります。台数の多い拠点や監視系があると足りません。
> 「MAP-E だから大丈夫」ではなく、拠点の同時セッション数を実測してから方式を決めてください。

## 1.6 MTU の引き算(「なぜ 1460 なのか」)

```
素の Ethernet                    1500
  − PPPoE ヘッダ 8               → 1492 …… ただし PPPoE の MRU 上限で実質 1454 が多い
  − IPv6 ヘッダ 40(トンネル)   → 1460 …… MAP-E / DS-Lite
  − encaplimit(Dst Options)8   → 1452 …… ip6tnl の既定で付く。実機 BR/CE で片方向断の原因(R11)
```

**現場の一手**(症状を知っているだけでは直せません):

- CPE で **TCP MSS clamp**(OpenWrt: firewall の `mtu_fix`、Cisco IOS: `ip tcp adjust-mss 1420`)
- CPE の WAN MTU を手動設定(OpenWrt: `option mtu '1460'`)
- トンネルの `encaplimit none`(ラボの VNE スクリプトは設定済み)
- 経路上で ICMP(v6 の Packet Too Big / v4 の Fragmentation-Needed)が落とされていないか確認

## 3. 初心者がつまずく壁 — 先生と生徒の Q&A

勉強会でそのまま読み上げられる形にしてあります。**生徒側のセリフは実際に若手から出た/出そうな疑問**。
時間割には含めていないので、各回 +15〜20 分の別枠で扱ってください。

### 壁1

> **生徒**: IPoE って NTT がやってるサービス名ですか?
>
> **先生**: いや、IPoE は "IP over Ethernet" の略で、**PPPoE の PPP を挟まずに Ethernet に直接 IP を載せる**という
> 接続方式の名前。NTT の商品名じゃない。PPPoE だと「ID とパスワードでセッションを張る」工程が入るけど、
> IPoE はそれがなくて、つないだら RA か DHCPv6 でアドレスが降ってくる。
> → 付録 A.3(p.443)。ここに PPPoE と IPoE が並べて書いてある。

### 壁2

> **生徒**: 「IPoE にすると速い」って営業が言うんですけど、なんで速いんですか?
>
> **先生**: **IPoE 自体が速いわけじゃない。** PPPoE は網終端装置(NTE)という装置を必ず通るんだけど、
> ここの収容数が決まっていて夕方に混む。IPoE は VNE 事業者のルータで直接 IPv6 を流すのでそこを通らない。
> つまり「速い」の理由は**プロトコルではなく通る箱が違う**から。客への説明もこう言うべき。
>
> **懐疑的な同僚**: それも常に正しくない。IPoE 側の VNE が混んでれば普通に遅い。「IPoE にしたのに遅い」案件は実在する。
> だから「速くなります」と言い切らないこと。約束すると後で詰められる。

### 壁3

> **生徒**: IPv4 が使えなくなるんですか?
>
> **先生**: ならない。IPoE でも IPv4 は使える。ただし **IPv6 のトンネルの中を通る**(MAP-E / DS-Lite)。
> だから「IPv4 の通信が IPv6 に依存する」という新しい壊れ方が生まれる。
> IPv6 側が不調なら IPv4 も道連れになる、という点が PPPoE 時代と決定的に違う。
> → 21.1(p.381) で共存技術の全体像、24 章で日本で実際に使われている方式。

### 壁4

> **生徒**: /64 とか /56 の数字は何ですか? IPv4 の /24 みたいなもの?
>
> **先生**: 考え方は同じ(前から何ビットがネットワーク部か)。ただ**運用の感覚が全然違う**。
> IPv4 は「アドレスを 1 個もらう」、IPv6 は「**プレフィックスを 1 個もらってその中を自分で切る**」。
> /56 をもらったら /64 が 256 個作れる。**SLAAC を使う限りホスト部は 64 ビット**(それが SLAAC の要求)。
> → 3.12 ユーザへの IPv6 アドレス割り当て(p.89)。

### 壁5

> **生徒**: `fe80::` から始まるアドレスがいっぱい出てくるんですが、これ何ですか? 消していいですか?
>
> **先生**: **消したら通信が全部死ぬ。** リンクローカルアドレスといって、同じリンク内だけで使う。
> IPv6 のルーティングも近隣探索も、実はこれを使って動いてる。RA の送信元も `fe80::`。
> IPv4 の `169.254.x.x` とは役割が全然違う(あっちは DHCP 失敗時の敗戦処理)。
> → 3.5(p.74) と 6.x。

### 壁6

> **生徒**: `tcpdump` に ICMPv6 がめちゃくちゃ流れてるんですが、攻撃されてます?
>
> **先生**: 正常。IPv6 では ICMPv6 が**プロトコルの本体機能を担っている**。
> ARP の代わり(NS/NA)、ルータ広告(RS/RA)、Path MTU 通知、全部 ICMPv6。
> だから **ICMPv6 を全部 drop するファイアウォール設定は IPv6 を壊す**。
> → 14.9「ICMPv6 を無条件にすべてフィルタリングすべきではない」(p.279)。ここは太字で覚える。
>
> **懐疑的な同僚**: 逆に「じゃあ ICMPv6 は全許可」も間違い。RFC 4890 相当の選別が必要。
> 「ICMP を落とすと MTU 探索が壊れる」原理は v4/v6 共通で、**このラボの R5 は IPv4 側**で再現している
> (外側パケットが 1500 に収まるため ICMPv6 Too Big は出ず、VNE が返す
>  **ICMPv4 Fragmentation-Needed** を drop している。[test-matrix.md](test-matrix.md) R5)。

### 壁7

> **生徒**: MAP-E の「ポートが制限される」って、何個使えるんですか?
>
> **先生**: 方式のパラメータ次第。ラボの設定(ea-len 16 / psid-len 8 / psid-offset 4)だと
> **1 ユーザあたり 240 個**(16 ポート × 15 ブロック)。実サービスでも v6プラス=240、
> OCNバーチャルコネクト=1008 程度。計算式と導出は §1.5 にある。
> しかも**連続していない**。PSID=5 なら `0x1050-0x105F`(4176-4191)、`0x2050-0x205F`、…と
> 16 個ずつ 15 箇所に散らばる。「4176〜8000 の範囲」のように連続だと思って NAT 設定を書くと動かない。
> → 24.3 A+P(p.423)。ラボ R12 で必ず一度失敗させること。
>
> **懐疑的な同僚**: 240 は少ない。ブラウザは 1 タブで数十本張る。台数の多い拠点や監視系がいると足りなくなる。
> 「MAP-E だから大丈夫」ではなく、拠点の同時セッション数を実測してから方式を決めること。

### 壁8

> **生徒**: 客先で「ポート開放して」と言われました。IPoE でもできますよね?
>
> **先生**: **方式を先に確認。**
> - MAP-E → 自分に割り当てられたポート**集合**の中なら可。80/443 は基本無理。
> - DS-Lite → **不可**。NAT が網側(AFTR)にあり、**利用者からそれを操作する手段が提供されていない**。
>   (プロトコルとしては PCP 等で開ける設計余地はあるが、日本の商用 DS-Lite では提供されていない)
>
> 代替は **固定 IP 系サービス**か **PPPoE 併用**。
> ここを聞かずに「できます」と答えると案件が炎上する。ラボ R4 で「本当にできない」を体験しておく。
> → 24.1(p.421), 19.4(p.362)。

### 壁9

> **生徒**: 切替後に「Web は見えるけど添付ファイルが送れない」と言われました。
>
> **先生**: MTU。トンネルでヘッダが増えるので、素の 1500 では通らない。引き算は §1.6 にある。
> 小さいパケット(HTTP の GET)は通るので「見えるけど大きいものが落ちる」という症状になる。
> **一手は TCP MSS clamp か CPE の MTU 手動設定**。
> → 第10章 + 9.2。ラボ R5 と R11。`/big.bin`(5MB) を落として再現する。

### 壁10

> **生徒**: IPoE にしたらセキュリティは上がりますか?
>
> **先生**: **下がる可能性がある。** PPPoE + IPv4 NAT では「NAT があるから外から入れない」状態だったのが、
> IPoE で各端末にグローバル IPv6 が付くと、**外から直接到達しうる**。
> ファイアウォール設定が入っているかを必ず確認する。
> → 14.1「IPv6 は IPv4 よりもセキュアというわけではない」(p.263), 14.7(p.278)。ラボ R13。
>
> **懐疑的な同僚**: とはいえ「NAT はセキュリティ機能ではない」というのも教科書の立場。
> NAT に守られていた**つもり**だっただけ。この誤解を客に共有してしまうと後々困る。

## 5. 講師向け運営メモ

### 準備(講師が事前にやること)

1. **ラボを一度自分で通す**。未実行のまま勉強会当日に流すと確実に事故ります。
   → [proxmox-prototype.md](proxmox-prototype.md) §0.5 → §2 → §5、または [runbook-vmware.md](runbook-vmware.md)
2. **「⚠未検証」印の演習を 1 本ずつ実走**し、期待結果と所要時間を本ガイドに書き込む
3. **各回の演習は「動く状態」から始める**(0 から構築させると 90 分では無理)。
   「動く状態」の定義(どのモードで、どのスクリプトを実行済みか)と復元手順を決めておく。
   電源 OFF からの復元後は setup スクリプトの再実行が必要([build.md](build.md))
4. **OpenWrt に tcpdump を導入しておく**(ラボ内にインターネットはない)
5. `tcpdump` の出力は**事前に取ってテキスト / pcap で配る**。
   ライブキャプチャは**各回 1 回だけ**にし、読み方の練習は配布版で行う
6. 教科書は**該当ページに付箋**。「p.443 を開いて」で全員が同じ図を見られる状態にする。
   **会社で何冊確保するかを先に決める**(手元に本が無い人は参加できません)

### 進め方のコツ

- **1回目に IPv6 の全体像を話しきろうとしない**。25章分を 90 分に圧縮すると全員脱落する
- **講師 2 名体制**(操作役 + 解説役)を推奨。1 人だとラボが詰まった瞬間に会が止まる
- **同時に検証できる CE は 1 台**です([runbook-vmware.md](runbook-vmware.md))。
  ペア演習の分担は「**叩く人 / 教科書の該当節を読み上げる人**」と割り切る。
  支店参加者には「画面共有 + 事前採取した pcap を各自の Wireshark で開く」形式にする
- 「壁」の Q&A は**生徒役を若手にやらせる**。読み上げるだけで理解が進む
- **懐疑的な同僚のセリフを飛ばさない**。「先生の話も条件付き」という感覚が現場で効く

### 教材の維持

- **数値パラメータの正本は [build.md](build.md) / [README.md](README.md) です。**

### 教科書とラボの関係(MAP-E のインタフェース識別子)

- 第2版第2刷の更新履歴に「**MAP-E のインタフェース識別子を RFC 7597 準拠に**」修正した旨の記載があります。
- **ラボの既定も RFC 7597**(OpenWrt の `legacymap` なし)で、**教科書と一致しています**
  ([`setup-map-br.sh`](../../lab/ipoe/vne/setup-map-br.sh) の `CE_MAP_ADDR` は RFC 7597 の IID)。
- 食い違うのは**実サービス側**です。日本の VNE は `draft-ietf-softwire-map-03` 互換のため、
  実案件のリハーサルをするときだけ `option legacymap '1'` を立て、`CE_MAP_ADDR` を再計算します
  ([build.md](build.md) §3 のコメント / [research-notes.md](research-notes.md) §2)。
- **ラボ既定のまま `legacymap '1'` を入れると、BR 側の静的トンネルとアドレスが合わず MAP-E が全断します。**
- 勉強会では「**教科書どおり(RFC 7597)で動くのがラボ。実サービスは draft-03**」と整理して伝えてください。
  RFC = 確定した仕様、draft = 確定前の草案。日本の VNE は**草案のまま製品化されて普及した**という経緯です。
