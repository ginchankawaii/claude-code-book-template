# PPPoE → IPoE 切替検証ラボ(VMware版) 全体設計

PPPoE から IPoE(IPv4 over IPv6)への切替案件で発生するトラブルを、**案件前に社内 VMware 基盤で再現・検証する**ためのラボ設計です。
NTT NGN 網・ISP の BRAS・VNE(MAP-E BR / DS-Lite AFTR)・インターネットをすべて Linux VM で模擬し、実機 CPE(お客様と同型のルータ)を物理 NIC 経由で収容できます。

- **構築ログ / PDCA 記録(実走の記録・未検証項目トラッカー・CE 入替手順)**: [build-log.md](build-log.md)

## 1. 背景と目的

切替案件でトラブルが多い理由は、**組み合わせの爆発**にあります。

| 軸 | 主なバリエーション |
|---|---|
| IPv6 払い出し方式 | ひかり電話**なし** = RA 方式(/64)、ひかり電話**あり** = DHCPv6-PD 方式(/56) |
| IPv4 over IPv6 方式 | **MAP-E**(v6プラス、OCNバーチャルコネクト、IPv6オプション等)、**DS-Lite**(transix、クロスパス、v6コネクト)、固定IP系、PPPoE 併用 |
| CPE | HGW 内蔵機能、市販ルータ(メーカー/機種/ファーム差)、業務用ルータ |
| 構成 | HGW 直下、二重ルータ、PPPoE ブリッジ併用、拠点間 VPN あり 等 |

これらを実網で試すと開通・切戻しに日単位のリードタイムがかかりますが、ラボなら**方式・払い出し・構成を数分で切り替えて**事前検証できます。

## 2. 方式の要点(ラボで再現すべき差分)

| 方式 | IPv4 の通り方 | NAT の場所 | ポート開放 | IPv4 MTU 目安 |
|---|---|---|---|---|
| PPPoE | PPP セッション(BRAS 終端) | CPE | 可 | 1454 |
| MAP-E | IPv4-in-IPv6 カプセル化。CE が共有 IPv4 + 制限ポート(v6プラス=240、OCNバーチャルコネクト=1008)で NAT | CPE(CE) | 制限ポートのみ可 | 1460 |
| DS-Lite | IPv4-in-IPv6 カプセル化。NAT は網側 AFTR | 網側(AFTR) | 不可 | 1460 |

トラブルの大半はこの差分(ポート制限、NAT 位置、MTU、払い出し方式とルータ設定の不整合、PPPoE セッション残留)に起因します。

## 3. トポロジ

```
                        [管理セグメント (各VMのeth0, NAT)]

  実機CPE ──物理NIC──┐
                      │ PG-ACCESS (NGNアクセス網 L2, MTU1500)
  OpenWrt-CE(VM) ─────┤   ・PPPoEフレームはこのL2上をBRASまで素通し
                      │   ・RA / DHCPv6-PD は NGN-SIM が配布
        ┌─────────────┴─────────────┐
        │ eth1                      │ eth1
   [NGN-SIM]                    [BRAS]  accel-ppp (PPPoE終端)
    radvd / kea                     │ eth2
        │ eth2                      │
        │ PG-CORE (NGN網内 IPv6)    │
        │ 2001:db8:ff00::/64        │
        │ eth1                      │
     [VNE]  MAP-E BR + DS-Lite AFTR │
        │ eth2                      │
        └────────────┬──────────────┘
                     │ PG-INET (模擬インターネット)
                     │ 203.0.113.0/24 + 2001:db8:cafe::/64
                [INET-SIM]  Web/DNS サーバ
```

## 4. VM 一覧(Ubuntu Server 24.04 想定)

| VM | 役割 | 主要ソフト | vCPU/RAM |
|---|---|---|---|
| NGN-SIM | NGN 網模擬。RA 方式 / PD 方式を切替可能。網内ルーティング | radvd, kea-dhcp6 | 2 / 2GB |
| BRAS | PPPoE 終端(従来 ISP 相当)。セッション残留などの再現も担当 | accel-ppp | 2 / 2GB |
| VNE | MAP-E BR と DS-Lite AFTR を両方収容 | ip6tnl, nftables | 2 / 2GB |
| INET-SIM | 模擬インターネット(Web / DNS)。v6 だけ落とす等の障害注入も担当 | nginx, dnsmasq | 1 / 1GB |
| OpenWrt-CE | リファレンス CPE(map / ds-lite パッケージ)。実機を持ち込む前の基準動作確認用 | OpenWrt x86 | 1 / 512MB |
| LAB-CLIENT | **CPE 配下の検証クライアント。`run-checks.sh` を実行する** | curl, iputils | 1 / 1GB |

合計 9vCPU / 9GB 程度。既存 VMware 基盤の空きで十分収まる規模です。

> **LAB-CLIENT を省略しないでください。** 検証は「CPE を通った通信」で成立します。
> 管理 LAN に直結したホストから `run-checks.sh` を流すと、通信が CPE を通らずに
> 管理 LAN へ抜けてしまい、**PASS したのに実は何も検証できていない**という
> 最悪の偽陽性になります。構築手順は [build.md §5.7](build.md) を参照。

## 5. vSwitch / ポートグループ設計

| PG | 用途 | 注意点 |
|---|---|---|
| PG-ACCESS | アクセス回線 L2 | **無差別モード・偽装転送・MACアドレス変更を「承諾」にする**(PPPoE と実機ブリッジに必須)。実機 CPE は物理スイッチ→物理 NIC 経由でこの PG に収容(構成図は [build.md §5.5](build.md#55-実機-cpe-の接続物理スイッチ経由))  |
| PG-CORE | NGN 網内(IPv6 のみ) | 内部専用、アップリンク不要 |
| PG-INET | 模擬インターネット | 内部専用、アップリンク不要 |
| PG-CLIENT | **CPE 配下の LAN**(OpenWrt-CE の LAN 側 ⇔ LAB-CLIENT) | 内部専用、アップリンク不要。ここに実機 CPE の LAN ポートも収容する |
| 管理 | 各 VM の eth0 | 既存の NAT / 管理ネットワークでよい。**LAB-CLIENT はここに既定経路を残さないこと**(上の注意) |

## 7. 使い方の流れ

1. [build.md](build.md) に従って 5 VM を構築(初回のみ。以後はスナップショットで即復元)
2. 案件の構成(払い出し方式 × IPv4 over IPv6 方式 × CPE)に合わせて NGN-SIM のモードと CPE を設定
3. 実機 CPE を PG-ACCESS に接続し、[test-matrix.md](test-matrix.md) のシナリオで**切替前 → 切替 → 切替後 → 切戻し**を通しでリハーサル
4. `lab/ipoe/tests/run-checks.sh` を CPE 配下のクライアントで実行し、疎通・DNS・MTU を機械的に判定
5. トラブルが予想される構成は「トラブル再現レシピ」で事前に症状と切り分け手順を確認しておく

## 8. このラボでできること・できないこと(網羅範囲)

**このラボは「全組み合わせを事前に保証する装置」ではありません。** トラブルの大半を占める定番パターンを案件前に潰し、実機で切替リハーサルをしてから現場に行くための環境です。展開時にはこの前提を必ず共有してください。

### できること

| 項目 | 内容 |
|---|---|
| 方式差の検証 | RA 方式 / PD 方式 × MAP-E / DS-Lite / PPPoE の組み合わせと、設定不整合時の症状確認 |
| 切替リハーサル | PPPoE 切断 → IPoE 設定 → 確認 → 切戻し、の通し練習と所要時間の計測 |
| 実機ルータの動作確認 | お客様と同型機・同ファームで「その方式で本当に繋がるか」を事前確認(MAP-E 自動設定専用機を除く — 下の「できないこと」参照) |
| トラブルの疑似体験 | 定番トラブル 13 種(R1〜R13、[test-matrix.md](test-matrix.md) §4)をわざと再現し、症状と切り分け手順を体で覚える |
| エビデンス採取 | `run-checks.sh` の切替前後ログをそのまま検証記録として保存 |

### できないこと

| 項目 | 補足 |
|---|---|
| 実 VNE(v6プラス、transix 等)の本物の装置の癖 | BR/AFTR は Linux による模擬。実装固有の挙動は実網でしか分からない |
| ISP 側の開通処理・認証・契約状態 | 開通タイミングや「IPoE 開通で PPPoE が止まる」の実際の発動は ISP 依存 |
| NTT 網固有の挙動 | v6オプションの開通反映、網内エラー、フレッツ・ジョイントの自動設定配信など |
| **市販ルータの MAP-E「自動設定」** | 自動判定は VNE のルール配布サーバ依存(方式が乱立、[research-notes.md §1](research-notes.md) JANOG53)。手動設定 UI がない機種はラボで MAP-E 接続できない場合がある。DS-Lite は AFTR を DNS で発見する仕様のため、ラボ DNS の FQDN 模擬で自動設定機種も動く可能性あり(build.md §4) |
| 性能・帯域・輻輳の測定 | ラボの帯域は実網と無関係。**機能・手順・切り分けの検証専用** |

**非対称性に注意**: ラボの網側(Kea/radvd/accel-ppp)は既定では実網 NGN より寛容です。つまり「ラボで FAIL → 現場でも FAIL」はほぼ確実に言えますが、**「ラボで PASS → 現場でも PASS」は保証されません**(実網には DUID-LL 限定・セッション数制限などの癖がある)。

再現できる癖のうち、**BRAS の二重セッション拒否は既定で有効**、**Kea の DUID-LL 限定は既定で無効(opt-in)**です。後者を既定で切っているのは、CPE が既定で DUID-LLT を送ることが多く、最初の疎通確認で切り分けが難しくなるためです([test-matrix.md](test-matrix.md) §3 Phase 1 の手順 5 に有効化方法)。**ラボを一度通したら、実網に近づけるために有効化することを推奨します。**

### 網羅性の担保は「運用」で行う

1. 新規案件は検証マトリクス([test-matrix.md](test-matrix.md) §2)の 8 パターンに当てはめ、**一致しない差分(機種・ファーム・アプリ)だけを追加検証**する
2. 現場で新しいトラブルが出たら、ラボで再現手順を作ってトラブル再現レシピに追加する
3. 検証実績(機種 × 方式 × 結果)を実績表として蓄積する — 溜まるほど新規案件の検証量が減る

作って終わりではなく、案件をこなすたびに網羅範囲が広がっていく設計です。

## 9. 用語ミニプライマ(初見メンバー向け)

| 用語 | ざっくり言うと |
|---|---|
| IPoE / IPv6 IPoE | PPPoE のようなセッションを張らず、Ethernet に直接 IPv6 が流れてくる接続方式 |
| RA 方式 / PD 方式 | IPv6 アドレスの配られ方。ひかり電話**なし**= RA(/64 が 1 つ降ってくる)、**あり**= DHCPv6-PD(/56 のブロックを委譲される) |
| VNE | IPv6 上で IPv4 を通すサービスの提供事業者(JPNE、インターネットマルチフィード等)。ISP はここを借りている |
| MAP-E | IPv4 パケットを IPv6 に包んで運ぶ方式。NAT は**自宅ルータ(CE)**がやるが、使えるポートが制限される |
| DS-Lite | 同じく IPv4 を IPv6 に包む方式。NAT は**網側(AFTR)**がやるので、ポート開放は一切できない |
| CE / BR / B4 / AFTR | CE=MAP-E の宅内側、BR=MAP-E の網側。B4=DS-Lite の宅内側、AFTR=DS-Lite の網側 |
| PSID | MAP-E で「あなたはこのポート番号群を使ってよい」を表す ID。プレフィックスから機械的に計算される |
| EA bits | 委譲された IPv6 プレフィックスの中に埋め込まれた「共有 IPv4 アドレス+PSID」の素になるビット列 |
| DUID | DHCPv6 のクライアント識別子。**NGN は DUID-LL という種類しか受け付けない**(頻出トラブル原因) |
| HGW | ひかり電話ルータ(ホームゲートウェイ)。機種により IPoE を自分で終端してしまうので二重終端に注意 |

## 10. ラボの割り切り(実網との差分)

- MAP-E BR は単一 CE 向けの静的トンネルで模擬(ルールベースの本格 BR が必要になったら FD.io VPP の map プラグインに差し替え可能)
- フレッツ・v6オプション(網内折返し)や網内 DNS は簡略化。「未契約で外に出られない」状態は経路遮断で擬似再現
- 帯域・遅延は実網と異なるため、性能測定ではなく**機能・手順・切り分けの検証**に使う
