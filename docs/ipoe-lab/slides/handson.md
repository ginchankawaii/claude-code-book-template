# 第1部 見る — 正常な状態を観察する(30 分)

## 演習 1: アドレスがどう降りてくるかを見る(10 分)

**目的**: 説明会で聞いた「ルータが住所の前半を配る」を、実際のパケットで見る。

### 手順

**① キャプチャを開始する**(先に流し始めてから、次の②をやります)

```
【CPE】  tcpdump -nvi eth0 'icmp6 and ip6[40] == 134'
```

> `134` は RA(Router Advertisement)の番号です。これだけを拾います。

**② 別の窓で、CPE の WAN を再接続する**

```
【CPE】  ifdown wan6 && ifup wan6
```

### 期待する結果

**RA が飛んできて、その中にプレフィックスが入っています。**

```
fe80::ac:ff:fe00:1 > ff02::1: [ICMPv6] router advertisement
    prefix info option (3), length 32: 2001:db8:1014:300::/64
    rdnss option (25), length 24: 2001:db8:cafe::53
```

### ここで確認してほしいこと

- **送信元が `fe80::` です。**グローバルアドレスではありません(説明会の「鶏と卵」)
- **プレフィックスは `/64` です。**後半 64 ビットは CPE が自分で作ります
- **DNS サーバのアドレスも RA に入っています**(`rdnss`)

### 詰まったら

| 症状 | 原因 |
|---|---|
| 何も流れてこない | インタフェース名が違う。`ip -br link` で確認 |
| RA は来るがプレフィックスが無い | **NGN-SIM が PD 方式**になっています。演習 4 で切り替えます |

## 演習 2: 「疎通した」を疑う(10 分)

**目的**: **今日いちばん持ち帰ってほしい感覚**です。ping が通っても何も証明できません。

### 手順

**① まず ping する**

```
【CLIENT】  ping -c3 203.0.113.80
```

通ります。**ここで「つながった」と言いたくなりますが、待ってください。**

**② どのアドレスで外に出たかを見る**

```
【CLIENT】  curl http://203.0.113.80/
```

### 期待する結果

```
lab-inet OK
src: 198.51.100.10        ← これが答え
host: 203.0.113.80
```

### ここで確認してほしいこと

| 出口アドレス | 意味 |
|---|---|
| `198.51.100.10` | **MAP-E(PD 方式)が成立している** |
| `198.51.100.20` | MAP-E(RA 方式) |
| `203.0.113.1` | DS-Lite の AFTR で網側 NAT された |
| `203.0.113.2` | PPPoE の BRAS で NAT された |
| **私設アドレスのまま** | **経路が間違っています** |

> **実話**: 自宅の検証で、**検証スクリプトが全項目 PASS したのに経路が間違っていた**ことがあります。
> DS-Lite の構成を誤った状態で `PASS=10`。出口を見たらクライアントの私設アドレスのままでした。
> `ping` も `curl` も成功するので、**見た目では絶対に分かりません。**

**切替当日、疎通確認だけで「OK です」と言わないでください。**

## 演習 3: MAP-E の計算が合っているか確かめる(10 分)

**目的**: 「計算で決まる」を、自分の目で一致させる。

### 手順

```
【CPE】  ip -4 addr show map0
【CPE】  nft list table inet fw4 | grep -A2 'snat'
```

### 期待する結果

**降ってきた IPv6 が `2001:db8:100a:500::/56` のとき:**

| 項目 | 期待値 |
|---|---|
| 共有 IPv4 | `198.51.100.10` |
| PSID | `5` |
| 使えるポート(先頭ブロック) | `4176` 〜 `4191` |
| ポート総数 | 16 個 × 15 ブロック = **240** |

**ポート集合の全体**(間隔 4096):

```
4176-4191 / 8272-8287 / 12368-12383 / … / 61520-61535
```

### ここで確認してほしいこと

- **`0` 〜 `4095` のブロックが存在しません。**だから **80 番も 443 番も原理的に使えません**
- 説明会の「若い番号は仕組みの上でそもそも配られない」は、これのことです

# 第2部 切り替える — 方式が変わると何が変わるか(30 分)

## 演習 4: RA 方式 ⇄ PD 方式 を切り替える(15 分)

**目的**: ひかり電話の有無で何が変わるかを見る。

### 手順

**① PD 方式(ひかり電話あり相当)に切り替える**

```
【NGN-SIM】  sudo ./ipoe/ngn/setup-ngn.sh pd
```

**② CPE を再接続する**

```
【CPE】  ifdown wan6 && ifup wan6
【CPE】  ip -6 addr show
```

**③ RA 方式(ひかり電話なし相当)に戻す**

```
【NGN-SIM】  sudo ./ipoe/ngn/setup-ngn.sh ra
【CPE】      ifdown wan6 && ifup wan6
```

### 期待する結果

| 方式 | CPE の WAN | LAN 側 |
|---|---|---|
| **RA 方式** | `/64` が 1 本 | 委譲が無いので配れない |
| **PD 方式** | `/64` が 1 本 + **`/56` の委譲** | `/60` が降りる(OpenWrt 既定) |

### 詰まったら

> **切り替えたら必ず `run-checks.sh` を流し直してください。**
> 方式が変わると**出口アドレスも変わります**(`198.51.100.10` ⇄ `198.51.100.20`)。

**⚠ Kea のリースが残っていると、Renew で旧プレフィックスが返ります。**
切り替え前にリースを消してください。

## 演習 5: MAP-E ⇄ DS-Lite を切り替える(15 分)

**目的**: NAT の位置が変わると、出口アドレスが変わることを見る。

### 手順

**① DS-Lite に切り替える**

```
【VNE】  sudo ./ipoe/vne/setup-map-br.sh stop
【VNE】  sudo CE_WAN6=<CPE の WAN アドレス> ./ipoe/vne/setup-aftr.sh
```

CPE 側も DS-Lite に切り替えます(OpenWrt なら `proto dslite`)。

**② 出口アドレスを確認する**

```
【CLIENT】  curl http://203.0.113.80/
```

### 期待する結果

| 方式 | 出口アドレス | 誰が NAT したか |
|---|---|---|
| MAP-E | `198.51.100.10` | **CPE 自身** |
| DS-Lite | **`203.0.113.1`** | **網側の AFTR** |

**この 1 行が変わるだけで、ポート開放の可否が変わります。**それを次の第3部で見ます。

# 第3部 壊す — 障害を注入して症状を見る(50 分)

> **ここが山場です。**そして、**手順書どおりでは再現しないものが 4 つあります。**

## 演習 6(R3): MAP-E のポートを枯渇させる(15 分)

**目的**: 240 個という制限を、実際に詰まらせて見る。

### 手順

**滞留するセッションを 20 本張ります。**

```
【CLIENT】  for i in $(seq 20); do curl -s --limit-rate 1k -m 60 http://203.0.113.80/big.bin -o /dev/null & done
【CLIENT】  sleep 5; jobs -r | wc -l
```

> `--limit-rate 1k` が肝です。**すぐ閉じる `curl` 連打では NAT テーブルが埋まりません。**

### 期待する結果 — ここが実測と違います

**設計上は 240 本。しかし OpenWrt が CPE のときは、成功するのは きっかり 16 本です。**

原因は OpenWrt が作る nft ルールです。**15 本の `snat` がすべて同じマッチ条件**のため、
nftables の終端判定で**先頭ブロック(4176-4191)しか使われません。**

```
【CPE】  nft list table inet fw4 | grep -B2 'counter packets'
```

カウンタで確定できます(`nat 1: packets 3462` / `nat 4 以降: packets 0`)。

### ここで確認してほしいこと

- **「設計値どおりに動くとは限らない」**という、この演習で一番大事な体験です
- 実機 CPE では NAT エンジンが正しく扱うはずですが、**未検証**です。
  **演習では「設計上 240」とだけ言い、「実測で 240 使えた」とは言わないでください**

## 演習 7(R4): DS-Lite でポート開放を試みて、失敗させる(15 分)

**目的**: 「できません」を、根拠を持って言えるようにする。

### ⚠ 先に対照実験をやってください

**「着信しない」理由が仕様なのか、そもそも受け側がいないのかは、外から見て区別できません。**
自宅の検証で、**待受が無いまま「再現した」と読みかけました。**

**① クライアントで待受を起動する**

```
【CLIENT】  sudo systemd-run --unit=r4test --collect python3 -m http.server 8000 --bind 0.0.0.0
```

> **多段 ssh 越しの `nohup ... &` では起動しません。**必ず `systemd-run` を使ってください。

**② LAN 内から到達できることを先に示す**

```
【CPE】  wget -O - http://<クライアントの IP>:8000/
```

**HTML が返ることを確認してから**、次に進みます。**ここを飛ばさないでください。**

**③ その状態で、外から試す**

```
【INET-SIM】  curl -m5 http://203.0.113.1:8080/
【INET-SIM】  curl -m5 http://192.0.0.2:8080/
```

### 期待する結果

| 宛先 | 結果 |
|---|---|
| `203.0.113.1:8080` | **接続拒否** |
| `192.0.0.2:8080` | **タイムアウト** |
| クライアントの私設アドレス | **タイムアウト** |

### 切り分けの見せ方

```
【CPE】  nft list ruleset | grep dnat
```

**CPE の DNAT ルールの宛先が `192.0.0.2`(RFC 6333 の B4 アドレス)になっています。**
**そもそも公開できる先が存在しない**ことが一目で分かります。

### 後始末

```
【CLIENT】  sudo systemctl stop r4test
```

## 演習 8(R5): MTU ブラックホールを再現する(15 分)

**目的**: **「さっきまで再現していたのに再現しない」**を体験する。演習中いちばん混乱します。

### 手順 — 3 段階を順にやってください

**① まず障害だけ入れる**

```
【VNE】  sudo ./ipoe/vne/setup-aftr.sh break-pmtu
【CLIENT】  SKIP_V6=1 ./ipoe/tests/run-checks.sh
```

**→ まだ PASS します。**再現しません。

**② CPE の MSS clamp を切る**

```
【CPE】  uci set firewall.@zone[1].mtu_fix='0'; uci commit firewall; /etc/init.d/firewall reload
【CLIENT】  SKIP_V6=1 ./ipoe/tests/run-checks.sh
```

**→ それでもまだ PASS します。**

**③ 両端で PMTU キャッシュを消す**

```
【CLIENT】     sudo ip route flush cache
【INET-SIM】   sudo ip route flush cache
【CLIENT】     SKIP_V6=1 ./ipoe/tests/run-checks.sh
```

**→ ここで初めて `FAIL: TCP 5MB over IPv4` が出ます。**

### ここで確認してほしいこと

- **小さいページと ping は PASS したままです。**「表示は出るのにファイルが落ちない」の正体です
- **既定の `mtu_fix` が、実務的な対処そのもの**だと分かります
- 一度成功した経路には PMTU が学習されているので、**キャッシュを消さないと再現しません**

### 直して、戻す

```
【CPE】  uci set firewall.@zone[1].mtu_fix='1'; uci commit firewall; /etc/init.d/firewall reload
【VNE】  sudo ./ipoe/vne/setup-aftr.sh restore-pmtu
```

**目的**: **同じ障害でも、クライアントによって症状が違う**ことを見る。

### 手順

```
【INET-SIM】  sudo ./ipoe/inet/setup-inet.sh break-v6
【CLIENT】    time curl -s -o /dev/null http://www.lab.example/
【CLIENT】    time wget -q -O /dev/null http://www.lab.example/
```

### 期待する結果 — ここが実測です

| コマンド | 結果 |
|---|---|
| `curl` | 8ms → **207ms**。**体感できません** |

**「A さんの PC は遅いが B さんは普通」というお客様申告の正体がこれです。**

### 戻す

```
【INET-SIM】  sudo ./ipoe/inet/setup-inet.sh restore
```

## 4-2. 切り分けの型(持ち帰り)

**症状から原因に辿り着く順番です。**

1. **どのアドレスで外に出たか**を見る(`curl http://203.0.113.80/`)
   → ここが違えば、経路の問題。方式か構成を疑う
2. **大きいパケットだけ落ちるか**を見る(`ping -M do -s 1432` と `-s 1472`)
   → 大きいものだけ落ちるなら MTU の問題
3. **名前解決だけ落ちるか**を見る
   → DNS の問題。**原因が 3 つ重なりえます**(§9-B / C / D)
4. **片方向だけ落ちるか**を見る
   → 復路を疑う(§9-K)

### やってはいけないこと

- **1 つ直して、確かめずに次を直す。**原因が複数あると、どれが効いたか分からなくなります
- **疎通確認だけで「直りました」と言う。**出口アドレスを見てください
