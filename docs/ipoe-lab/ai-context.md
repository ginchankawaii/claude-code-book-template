## 1. これは何か

**PPPoE から IPoE(IPv4 over IPv6)への切替案件で起きるトラブルを、案件前に社内で再現・検証するためのラボ**です。

NTT の NGN 網、ISP の BRAS、VNE(MAP-E の BR と DS-Lite の AFTR)、インターネットを**すべて Linux VM で模擬**し、
実機の CPE(お客様と同型のルータ)を物理 NIC 経由で収容できます。

**なぜ要るのか**: 組み合わせが多すぎて、実網では試せないからです。

| 軸 | バリエーション |
|---|---|
| IPv6 の払い出し | ひかり電話**なし** = RA 方式(`/64`)、**あり** = DHCPv6-PD 方式(`/56`) |
| IPv4 の運び方 | **MAP-E**(v6プラス / OCN バーチャルコネクト / BIGLOBE IPv6 オプション)、**DS-Lite**(transix / クロスパス / v6 コネクト)、固定 IP、PPPoE 併用 |
| CPE | HGW 内蔵、市販ルータ(機種・ファーム差)、業務用ルータ |
| 構成 | HGW 直下、二重ルータ、PPPoE 併用、拠点間 VPN あり |

実網で試すと開通と切戻しに日単位かかりますが、**ラボなら方式を数分で切り替えられます。**

## 2. 方式の要点(これがトラブルの原因のほぼ全部)

| 方式 | IPv4 の通り方 | NAT の場所 | ポート開放 | IPv4 MTU |
|---|---|---|---|---|
| **PPPoE** | PPP セッション(BRAS で終端) | CPE | 可 | 1454 |
| **MAP-E** | IPv4 を IPv6 でカプセル化。CE が共有 IPv4 + 制限ポートで NAT | **CPE(CE)** | **割当ポートのみ可** | **1460** |
| **DS-Lite** | IPv4 を IPv6 でカプセル化。NAT は網側 | **網側(AFTR)** | **不可** | **1460** |

**制限ポート数の実績値**: v6プラス = 240、OCN バーチャルコネクト = 1008(いずれも伝聞)。

**トラブルの大半はこの差分に起因します。**
ポート制限 / NAT の位置 / MTU / 払い出し方式とルータ設定の不整合 / PPPoE セッション残留。

### 日本のサービス → 方式 の対応表

| サービス名 | VNE / 提供 | 方式 | ポート開放 |
|---|---|---|---|
| v6プラス | JPIX(旧 JPNE) | **MAP-E** | 限定的(割当ポートのみ) |
| OCN バーチャルコネクト | NTT ドコモビジネス(旧 NTT Com) | **MAP-E** | 限定的(割当ポートのみ) |
| BIGLOBE IPv6 オプション | BIGLOBE 系 | **MAP-E** | 限定的(割当ポートのみ) |
| transix | インターネットマルチフィード | **DS-Lite** | 不可(固定 IP 契約が別途必要) |
| クロスパス(Xpass) | アルテリア・ネットワークス | **DS-Lite** | 不可(固定 IP 契約が別途必要) |
| v6 コネクト | 朝日ネット | **DS-Lite** | 不可(固定 IP 契約が別途必要) |
| ソフトバンク光 IPv6 高速ハイブリッド | BBIX | 独自方式(4rd/SAM 系) | 光BBユニット前提。本ラボの対象外 |

> 出典: ヤマハ RTpro「動作確認済み IPv6 IPoE + IPv4 over IPv6 接続サービス」ほか。
> **同じ ISP 名でもプランで VNE が違うことがあります。**開通後に実測で確かめること。

## 3. 構成

(人が見る用の構成図は `docs/ipoe-lab/topology.png`。以下はテキスト版で、AI に貼るのはこちらで足ります)

```
                     [管理セグメント (各VMのeth0)]

  実機CPE ──物理NIC──┐
                      │ PG-ACCESS (NGN アクセス網 L2, MTU1500)
  OpenWrt-CE(VM) ─────┤   ・PPPoE フレームはこの L2 を BRAS まで素通し
                      │   ・RA / DHCPv6-PD は NGN-SIM が配布
        ┌─────────────┴─────────────┐
        │ eth1                      │ eth1
   [NGN-SIM]                    [BRAS]  accel-ppp (PPPoE 終端)
    radvd / Kea                     │ eth2
        │ eth2                      │
        │ PG-CORE (NGN 網内 IPv6)   │
        │ 2001:db8:ff00::/64        │
        │ eth1                      │
     [VNE]  MAP-E BR + DS-Lite AFTR │
        │ eth2                      │
        └────────────┬──────────────┘
                     │ PG-INET (模擬インターネット)
                     │ 203.0.113.0/24 + 2001:db8:cafe::/64
                [INET-SIM]  nginx + dnsmasq
```

### VM 一覧とスクリプトの対応

| VM | 役割 | 実行するスクリプト |
|---|---|---|
| **NGN-SIM** | NTT の網の代わり。RA を撒き、`/56` を委譲する | `~/ipoe/ngn/setup-ngn.sh {ra|pd}` |
| **VNE** | MAP-E の BR と DS-Lite の AFTR | `~/ipoe/vne/setup-map-br.sh` / `setup-aftr.sh` |
| **INET-SIM** | 模擬インターネット(Web + DNS)。**アクセス元アドレスを表示する** | `~/ipoe/inet/setup-inet.sh` |
| **INET-SIM(兼)** | **MAP-E のルール配布サーバ**(HB46PP = 国内標準プロビジョニング方式)。本番同様に CPE が `4over6.info` の DNS TXT で発見し、HTTPS でルールを取得する。CPE 側の参照実装は `~/ipoe/ce/hb46pp-client.py` | `~/ipoe/inet/setup-ruleserver.sh {http\|https}` |
| **BRAS** | PPPoE の受け口。切替前の状態を作れる | `~/ipoe/bras/setup-bras.sh` |
| **LAB-CLIENT** | CPE 配下の検証クライアント | `~/ipoe/client/setup-client.sh` |
| **OpenWrt-CE** | CPE 役(実機を使うときは停止する) | uci で設定 |

> **重要**: VNE と INET-SIM は**必ず別 VM に分けてください。**同居させると
> パケットが同じホスト内で配送されてしまい、**DS-Lite の網側 NAT が当たりません。**
> **「疎通するので成功に見えるが、出口アドレスが NAT されていない」**という
> 一番タチの悪い状態になります(自宅で実際に踏みました)。

### 主要アドレス

| 用途 | アドレス |
|---|---|
| NGN 網内 | `2001:db8:ff00::/64` |
| アクセス網に配る(RA 方式) | `2001:db8:1014:300::/64` |
| アクセス網に配る(PD 方式) | `2001:db8:100a:500::/56` |
| MAP-E の BR | `2001:db8:9999::1` |
| DS-Lite の AFTR | `2001:db8:8888::1` |
| MAP-E の共有 IPv4(PD 方式) | `198.51.100.10`(PSID 5、ポート 4176〜4191 ほか計 240) |
| MAP-E の共有 IPv4(RA 方式) | `198.51.100.20`(PSID 3) |
| 模擬インターネット | `203.0.113.0/24` + `2001:db8:cafe::/64` |
| 検証用 Web/DNS | `203.0.113.80` / `203.0.113.53` |
| **ルール配布サーバ** | `2001:db8:cafe::a1`(発見用 DNS TXT は `4over6.info`) |

### MAP-E の「自動設定」を再現する場合の注意

本番の CPE はルールを手で設定されず、**事業者のサーバから取得します**。
ラボにも同じものがあります(`~/ipoe/inet/setup-ruleserver.sh https`)。

- **BR を手で起動するときは `CE_PSID` を必ず渡す。**入口検査(割当外ポートを落とす)が
  既定 ON なので、渡し忘れると既定値で検査が張られ **BR が CE の通信を黙って落とす**
  (RA 共有=3 / PD 共有=5 / 固定IP=0)。`lab-mode.sh` 経由なら自動
- **CE の MAP アドレスは実装で並びが違う。**Cisco を draft-03 で動かすと RFC 7597 と
  1 バイトずれる。実機の `show ipv6 interface brief` で確認してから BR を張ること
- MAP-E が通らないときは `journalctl -k | grep MAP-ENFORCE-DROP` を最初に見る

## 4. 検証の考え方(ここが一番大事)

### 疎通確認だけでは何も証明できない

**`ping` が通っても「意図した経路を通った」ことにはなりません。**
実際に、検証スクリプトが**全項目 PASS したのに、網側 NAT が効いていなかった**ことがあります
(VNE と INET-SIM を同居させた構成で `PASS=10`。トンネルは設計どおり通っていたのに、
出口を見たらクライアントの私設アドレスのままだった)。

**必ず「出口のアドレス」を確認してください。**模擬インターネットの Web がそれを表示します。

```bash
curl http://203.0.113.80/
# → src: の行に出るアドレスが「どこで NAT されたか」の答え
```

| 期待する出口アドレス | 意味 |
|---|---|
| `198.51.100.10` | MAP-E(PD 方式)が成立 |
| `198.51.100.20` | MAP-E(RA 方式)が成立 |
| `203.0.113.1` | DS-Lite の AFTR で網側 NAT された |
| `203.0.113.2` | PPPoE の BRAS で NAT された |
| 私設アドレスのまま | **どこでも NAT されていない。**経路の誤り**または** NAT の設定漏れ・不適用 |

### 検証スクリプト

```bash
# Linux クライアント。期待する出口アドレスを必ず渡す
EXPECT_SRC4=203.0.113.1 ./ipoe/tests/run-checks.sh | tee $(date +%Y%m%d-%H%M)-checks.log

# LAN が IPv4 のみの構成なら (実務ではこれが既定)
SKIP_V6=1 EXPECT_SRC4=203.0.113.1 ./ipoe/tests/run-checks.sh

# Windows クライアント
.\run-checks.ps1 -SkipV6 -ExpectSrc4 203.0.113.1 | Tee-Object -FilePath checks.log
```

## 5. 実際に踏んだトラブルと原因(ここを AI に読ませる価値が一番高い)

### A. `opkg update` が全リポジトリで失敗する(OpenWrt)

CPE から外に出られていない。まず IPv6 の既定経路と DNS を確認。

### B〜D. ping は通るのに名前解決だけ死ぬ

**原因が 3 つ重なりうる**ので、1 つ直して直らなくても見当違いとは限りません。

1. **CPE 側**: 送信元制限付きの既定経路(`sourcefilter`)
2. **CPE 側**: DNS リバインド保護(`rebind_protection`)がラボの内部名を弾く
3. **DNS サーバ側**: dnsmasq が待ち受けているインタフェースが足りない

### E. PPPoE を上げた瞬間に IPv6 が全部消える

netifd が物理 NIC の IPv6 を無効化する。**RA 自体は届いている**のでキャプチャで確認できる。

### I. IPv6 が「たまに全滅」する

CPE の GUA が `deprecated` になった瞬間、RFC 6724 の送信元選択が **ULA(`fd00::/8`)にフォールバック**する。
ラボに ULA の復路が無いので IPv6 が全滅。IPv4 は MAP-E トンネル経由なので無傷 →
**「IPv4 は通るのに IPv6 だけ死ぬ」**という紛らわしい形になる。
対処: CPE で ULA を無効化(`uci set network.globals.ula_prefix=''`)。

### J. MAP-E で同時接続が 16 で頭打ちになる

OpenWrt 24.10.0 (本ラボの構成) の癖。nft の snat が終端判定で、15 本のルールが同じマッチ条件のため先頭ブロックしか使われない。
**設計上は 240 ポート**だが、この構成での実効は 16。**設定で直るのか OpenWrt 固有なのかは未確認。実機で必ず数え直すこと。**

### K. IPv4 は通るのに IPv6 だけ片方向で死ぬ

`setup-ngn.sh` が Kea フックの `via` 復路を on-link で上書きしていた。
**症状が「片方向」のときは復路を疑う。**

### M. 892FJ の DHCP サーバから Windows がアドレスを取れない

サーバは `DHCPOFFER` / `DHCPACK` を送っているのにクライアントが再送し続ける。
ログに `unicasting BOOTREPLY to client ... (192.168.100.6)` とあり、
**まだ保持していないアドレス宛にユニキャストで返している**のが原因と見られる。
**検証の本体ではないので静的 IP で回避してよい。**

### N. CPE が WAN 側にも RA を撒いてしまう

`ipv6 unicast-routing` を入れると CPE 自身がアクセス網に RA を流す。**実網でやってはいけない。**
`ipv6 nd ra suppress all` を **WAN 側だけ**に入れる(LAN 側に入れると配下が SLAAC できなくなる)。

### 実機 892FJ 特有

- **RA 方式でないと `ipv6 address autoconfig` は何も取得しない。**
  PD 方式では radvd がプレフィックスを配らないため。
  症状は `No global unicast address is configured` で、**RA 自体は届いているので原因が見えない**
- **`ip tcp adjust-mss 1420` が無いと 5MB 転送で詰まる。**小さいページは見えるので気づきにくい
- **892FJ は MAP-E 非対応**(classic IOS のため)。DS-Lite は可

## 7. この資料に書いていないこと(AI も答えられません)

- **拠点間 IPsec VPN が MAP-E / DS-Lite 配下で実際に張れるか。**
  机上では「発信は可(両端が NAT-T 対応なら)/待ち受けは不可」だが、**ラボで未検証**
- **固定 IP オプションの料金と納期。**ISP ごとに違うので持ち帰り案件
- **同時接続数の判断基準。**「ピーク実測 × 安全率 2 倍が割当ポート数を超えたら MAP-E 単独を避ける」
  という型を置いているが、**安全率 2 倍は仮置き**
- **MAP-E の実効ポート数が実機で 240 使えるか。**OpenWrt では 16 だった。
  Cisco の仮想ルータ(Cat8000v)では設定は通るが転送エンジンが落ちて測れなかった
- **VNE 固有の仕様。**公開されていないので、この資料は一般論(RFC 7597 / RFC 6333)で書いてあります
