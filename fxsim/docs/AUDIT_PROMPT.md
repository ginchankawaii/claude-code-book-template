# 敵対的システム監査プロンプト（汎用テンプレート）

fxsimのRound-1〜6監査（累計バグ41件・全て再現付きで発見）から、効いた規律だけを
蒸留した再利用テンプレート。`[ ]` を埋めてエージェントに渡す。サブエージェント/
ワークフロー機能があれば並列で、無ければレンズを順番に実行させる。

---

## 本体（コピーして使う）

```
あなたは [対象システム] の敵対的監査チームのリーダーだ。守るべきものは
[実マネー/本番データ/ユーザー資産 等]。目的は安心材料の生産ではなく、
本物の欠陥を再現可能な証拠付きで見つけることである。以下の規律に従え。

## 0. 信頼の土台を先に作る
- 実システムの挙動を再現する検証ハーネス/複製環境を先に構築し、既知の
  基準値 [例: 本番の出力・過去の実測値] と一致することを確認してから使う。
  一致しないハーネス上の「発見」はすべて無効とする。
- 監査計画そのものを先にレッドチームへ渡し「この計画では何が見つからないか・
  どの検査が形骸化しうるか」を批判させ、計画を直してから実行する。

## 1. 直交する専門レンズをファンアウトする
同じ観点のレビュアーをN人並べるな。互いに違う壊し方をする専門家を立てる：
  - 状態機械レンズ：全経路を行番号付きで手トレース（起動/再起動/異常系/割込みの交差）
  - 境界・プロトコルレンズ：コンポーネント間の競合・部分書き込み・時計ズレ・二重起動
  - 数値エッジレンズ：NaN/ゼロ/極小/極大/丸め/浮動小数を実際にコードに食わせる
  - 文書と実装の乖離レンズ：ドキュメントが約束して実装が守っていない安全機能（逆も）
  - 統合実走レンズ：偽の外部環境を作って本物を起動し、故障を注入して観察する
各レンズへの共通指示：
  「発見ゼロは正当な結果である。埋め草を書くな。計算していない数字を書くな。
   すべての発見に、実行可能な再現コマンド or 正確な行番号トレースを付けよ。」

## 2. 不変条件を監査前に明文化する
壊れたら問答無用でバグと言い切れる性質を先に列挙する：
  [例: 「Xは決してYを超えない」「開いているZには必ずWが付随する」「二重書き込みは起きない」]
重要：不変条件は「存在」ではなく「生存性」で書け。
  悪い例「保護機構が設定されている」→ 良い例「保護機構が直近N分以内に実際に評価された。
  評価できない状態が続いたら有限時間内に安全側へ倒れる」。

## 3. 発見は敵対的に検証する
すべての発見を、別の独立エージェントが「反証」を目標に検証する。発見者の
スクリプトを再利用せず、ゼロから再計算・再現すること。CONFIRMEDを名乗れるのは
動く再現か隙のない行トレースを伴うものだけ。反証されたら破棄。

## 4. 判断規則を事前登録する
結果を見る前に「XがYを下回ったらZに戻す/止める」という行動規則を固定する。
結果を見てから基準を決める監査は劇場である。統計的な主張（改善・優位・効果）には
多重比較の請求書を回せ：これまでに試した案の総数Nを見積もり、N=25/100/300/1000の
感度カーブで補正後も主張が立つかを検査する。

## 5. 修正は攻撃者の武器で閉鎖証明する
バグを直したら、自作の確認テストだけで満足せず、攻撃者自身の再現スクリプトを
修正後コードに再実行して「再現失敗」を確認する。

## 5.5 修正が新しい失敗モードを作っていないか審査する
追加した保護機構ごとに「これが誤判定したとき何が起きるか」を書け。
**保護機構がプロセスを終了させる設計は、スーパーバイザの再起動と結合した瞬間に
再起動ストームになる**（fxsimではこれで実運用3回・最大30分の無監視状態を作った）。
規則：保護機構の失敗モードは「停止」ではなく「待機」または「安全側の縮退」に倒せ。
判定関数の返り値の型から「終了」という選択肢を消せるなら、それが最善の修正である。

## 5.6 運用点で検証せよ
閉鎖テストは**所有者の実際の数字**（残高・ロット・最小単位/ステップ・価格・設定既定値）で書け。
きりのいい数字で通った修正は、運用点では死んだコードかもしれない（fxsim：0.24ロットで検証した
adopt規則は、口座が持てる最大0.09ロットでは一度も実行されなかった）。
規則：修正が「Xより上でしか閉じない」なら、所有者のXが下にある限り**開いている**と扱う。

## 5.7 修正が作る新しい状態を列挙せよ
保護機構を足したら「この修正で新たに生まれる状態は何か。その各状態で、機構が頼る印（ID・フラグ・
ロック）は誰がいつ付けるのか」を書け。fxsimでは「引き継いだ建玉」という新状態のIDに誰も実行済みの
印を付けず、前ラウンドの穴が別の扉から開いた。検証者は**送り手の出力**でなく**受け手のその後の挙動**
（外部イベント後に何をするか）を見ること。

## 5.8 フラグは「その時点の入力」で決めよ
状態フラグ（盲目・凍結・不信）は毎ティック入力から**再計算**し、履歴で粘着させるな。
クリア分岐が到達不能なフラグは、一度立つと死ぬまで下りない（fxsim：切れた行を1回読んだだけで
永久盲目→フェイルセーフが健全な建玉を決済）。フラグを足したら「これはどの入力で下りるか」を
テストに書け（悪い行→良い行→信頼が戻る、を必ず1本）。

## 6. loop-until-dry（乾くまで回す）
修正で生まれたコードを次のラウンドの主攻撃対象にせよ（経験則：バグは一番新しい
コードに棲む）。新しい攻撃者を投入し続け、2ラウンド連続で新規発見ゼロになるまで
「監査完了」を宣言しない。収束していない場合はその事実を正直に報告する。

## 6.5 「常設の指示書」を疑う
コンポーネント間で状態を渡すとき、受け手が**それを何度実行し直すか**を必ず確認せよ。
片方が「現在の目標」を書き、もう片方がそれをポーリングして実行し直す設計では、
**指示が古くなったこと**と**まだ有効なこと**が区別できない。fxsimではこれが致命的欠陥に
なった（決済済みの建玉を30秒ごとに買い戻す）。処方：指示に**識別子**を持たせ、
受け手に「未実行の指示にだけ作用する」規則を課す。安全な方向（縮小・停止）は無条件、
危険な方向（拡大・開始）だけ識別子で門を作るのが定石。

## 8. 人が判断に使う出力は注文経路である
「最新コードを叩け」（規律6）には対抗軸が要る。増額・縮小・停止を**人間が決める根拠になる出力**
（健康診断の🟢、ランブックの対処文、損益の出口分類）は、注文を出すコードと同じ不変条件
（生存性で書いたI10）と同じハーネスで攻撃せよ。fxsimでは10パス目まで誰も監視計器を攻撃せず、
EAが1日止まっていても🟢が出ていた——その🟢が増額の条件だった。
そして計器の修正もまた最新コードである（fxsim：計器の修正が「バー欠落で🟢」の穴を持ち込んだ）。

## 9. カバレッジ台帳を作れ
完全性批評家に「コンポーネント × 不変条件 × 最後に攻撃したパス」の表を作らせよ。
「一度も攻撃されていない」は、レンズが報告した内容から**推測する**のではなく、台帳に**空欄として見える**
ようにする。ハーネスの忠実度（規律0）には、配備環境の**時計の系**（サーバー時刻・端末のGMT・コンテナのUTC）
の列挙を含めること（fxsim：バーがサーバー時刻で刻印されUTCとして読まれ、鮮度判定が2〜3h甘かった）。

## 7. 正直な限界で締める
最終報告には「この監査が証明できないこと」を必ず含める。
[例: 未来の市場環境・未入手データの品質・運用者の規律 等]
```

## 短縮版（1回のレビュー依頼に埋め込む用）

```
このコードを敵対的にレビューせよ。規律：(1)発見ゼロは正当、埋め草禁止
(2)全発見に再現コマンドor行番号トレース必須、計算してない数字は書くな
(3)まず壊れたら即バグの不変条件を列挙してから探せ（存在でなく生存性で書く）
(4)見つけたら別視点で自ら反証を試み、生き残ったものだけ報告
(5)一番新しい変更部分から攻めろ。
```

## 各規律の実績（なぜ入っているか）

| 規律 | fxsimで捕まえたもの |
|---|---|
| 0. ハーネス先行検証 | ハーネスがエンジンと一致して初めて「ライブは理論値の半分」を断定できた |
| 0. 計画のレッドチーム | 「ストップの存在でなく生存性を見よ」の指摘→最重要バグ発見に直結 |
| 1. 直交レンズ | 状態機械/プロトコル/数値/文書乖離/実走で、重複の少ない31件 |
| 2. 生存性の不変条件 | 「ストップはある」では素通りする盲目ハートビート穴を捕捉 |
| 3. 敵対的検証 | 35件の指摘を8件のCONFIRMEDに濾過（誤検知に工数を払わない） |
| 4. 事前登録 | 凸ランプの優位が選択バイアスと判明→感情抜きで自動リバート |
| 5. 攻撃者の武器で閉鎖 | 修正が「グレース期間中を見ただけ」の見かけ倒しでないことを実証 |
| 5.5 修正の失敗モード審査 | 監査が追加したロックが実運用で3回の停止を起こした（この規律の不在が原因） |
| 6. loop-until-dry | 第2巡で致命1件、第3巡で致命2件——**どちらも直前の修正が作った欠陥**だった |
| 6.5 常設の指示書を疑う | ストップ約定を30秒で買い戻す致命欠陥（両側は個別には正しかった） |
| 5.6 運用点で検証 | 当日の修正が口座の全サイズで死んだコードだった（0.24で検証、実口座は0.09） |
| 5.7 新状態の列挙 | 「引き継いだ建玉」のIDに誰も印を付けず、前ラウンドの穴が別の扉から再発 |
| 5.8 フラグは入力で決める | 粘着した「切れた行」フラグが永久盲目を作った（r6e、9パス目） |
| 8. 人が使う出力は注文経路 | EAが1日止まっていても🟢（増額の条件）が出ていた。10パス目まで未攻撃 |
| 9. カバレッジ台帳 | 「攻撃されていない」が台帳で見えず、レンズの沈黙から推測されていた |
