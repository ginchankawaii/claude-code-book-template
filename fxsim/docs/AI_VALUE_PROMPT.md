# AIの判断は、自分の費用を稼げるか ―― 確かめて、稼げる場合だけ任せる指示書

版 0.1（2026-11-23・下書き）

> **所有者の方へ**
>
> 「プロのように自分で判断するAIを入れて、APIの費用を自分で稼がせる」ための指示書です。ただし、**先に費用ゼロで確かめ、稼げると分かった場合だけ先へ進む**形にしてあります。
>
> - **正直な見込み**：いまの元手（約27万円）では、AIが費用を稼げる可能性は低いです。月300円のAPI代でも、年1.3%の上乗せが要ります。
>   これまでの検証では、AIが途中で降りる・建てを見送ると、この売買ルールの利益はむしろ減る構造でした（利益の約9割が、数か月持ち続けた数回の取引から来ているためです）。
> - **それでも確かめる価値がある理由**：最初の2段階はAPIを1回も呼ばず、お金がかかりません。「重要な発表の前は外す」というあなたの考えを、過去11年のデータで、ごまかしなしに試せます。
> - **始め方**：新しい会話に、次の文を貼ってください。
>   「ブランチ claude/fx-trading-simulator-vnAEG にある fxsim/docs/AI_VALUE_PROMPT.md を読んで、その通りに進めて。このブランチと、claude/ で始まる作業用のブランチへのプッシュを許可します」
> - APIの鍵は、段階2まで要りません。段階2に進むかどうかは、数字を見て、あなたが決めます。

以下が指示書の本体である。`docs/PRODUCT_PROMPT.md` の R1〜R13（絶対に破らない規則）と §5（変更の分類）は、この指示書にもそのまま適用する。最初に読むこと。

---

## 0. 最初に覚える5つ

1. **既定の結論は「AIは付けない」。** 証拠が基準を超えたときだけ、次の段階へ進む。惜しくても進まない。
2. **費用ゼロの段階が先。** 段階0と1は、APIを1回も呼ばない。鍵を求めない。
3. **LLMに過去を判断させた結果は、証拠にしない。** モデルは過去の相場の結末を知っている。証拠は、決定論的な規則のバックテストと、本番での前向きの記録だけ。
4. **AIに渡してよい権限は「新しく建てるのを、決めた時間だけ遅らせる」まで。** 持っている建玉を閉じない・減らさない・増やさない。ショートしない。
5. **費用を引いて測る。** 純便益（円）＝ AIがいた場合の損益 − ルールだけの損益 − API代。円と、損益分岐の元手で報告する。

## 1. 使命

所有者の目標は、複利で資産を増やすことである。そのために「プロのトレーダーのように、要人の発言や重要な発表の前には外す、といった判断をAIが自分で行い、
しかもAPIの費用を自分で稼ぐ仕組み」を求めている。

あなたの仕事は、**それが成り立つかどうかを、自分を騙さない方法で確かめること**、そして成り立つ場合に限り、最小の権限で組み込むことである。
成り立たないと分かったら、そう報告して終える。それも成果である（所有者はAPIの費用を払わずに済む）。

### 正直な出発点

- この売買ルール（H1足の終値がSMA2400より上の間だけロング）は、**小さく何度も負け、たまに大きく勝つ**型である。勝つ取引は約1割。
  Round-3の審問の時点で、11年の利益の89.6%が、92〜296日持ち続けた3回の取引から来ていた（`docs/RESEARCH.md`）。
- だから、**途中で降りる判断は右の裾（大きな勝ち）を壊す**。建てを見送ったときの機会損失には上限がなく、ストップで負けるときの損は1回1〜2%で上限がある（非対称）。
  同じ審問で、AIが建玉を清算できたこと・見送りが高くつくこと・プロンプトが見送りを作り出していたことが確定し、AIの権限は既定で shadow（助言のみ）になった。
- 「重要な発表の前に外すプロ」は、短い時間軸で売買している。このルールに近いプロ（トレンドに乗る運用）は、発表をまたいで持ち続け、危険は建玉の大きさで管理する。
- それでも、**「予定された発表の前後だけ、新しく建てるのを少し待つ」が得かどうかは、まだ誰も測っていない**。これは費用ゼロで測れる。

### 費用の物差し（2026-11時点の公表価格。使う前に確かめ直す）

- 損益分岐：**必要な上乗せ（年率）＝ 年間のAPI代 ÷ 元手**。月300円なら、27万円で年1.3%、100万円で年0.4%。月3,500円なら、27万円で年15.6%、100万円で年4.2%。
- いまの脳のAI層は、1回の判断でweb検索を最大6回、予定表の取得で最大5回（12時間ごと）使う作りである。検索は1,000回あたり10ドルで、読み込んだ検索結果も入力として課金される。
  モデルの単価は、安いもの（Haiku 5.5：入力100万トークンあたり0.10ドル）と高いもの（Sonnet 4.6：同3ドル、Opus 5.5：同4ドル）で数十倍違う。
- 所有者が過去に実際いくら払ったかは、APIの管理画面の利用明細がいちばん確かである（`scripts/diagnose_live.py` の概算は、1回あたりの量を小さく見積もっている）。

- `app/ai_trader.py`（判断の呼び出し。web検索の回数、出力の形）、`app/events.py`（予定表。`imminent_high_impact`、12時間ごとの取得）、

## 3. この指示書だけの規則

`PRODUCT_PROMPT.md` の R1〜R13 に加えて：

- **V1 APIを呼ばない。** 段階2で、所有者が鍵と月の上限額を明示して出すまで。段階0と1の仕組みは、環境に `ANTHROPIC_API_KEY` があったら実行を拒否する。
- **V2 権限の上限。** AIができるのは、最終的にも「新規の建てを、最大N時間遅らせる」ことだけ（Nは事前登録で決める。上限は24時間）。遅らせた後は、ルールどおりに建てる。
  保有中の建玉には触れない。脳のAI層の `entry`・`full` は使わない。
- **V3 証拠の種類。** (i) 決定論的な規則のバックテスト（事前登録つき）、(ii) 本番での前向きの影の記録。LLMに過去の日付を見せて判断させた結果は、数に入れない。
- **V4 事前登録。** 結果を見る前に、仮説・候補（3つまで）・判定基準・既定の行動をコミットする。基準の閾値を、判定するデータから作らない。近い長さ9通りで判断する。
  試行はすべて台帳に数える。この研究は、所有者が明示的に求めたものとして、研究の枠（`RESEARCH_RULES.md`）の1つに数える。
- **V5 偽薬を置く。** 「発表の前後に外す」の効果を測るときは、同じ回数・同じ長さで**でたらめな時刻に外す**対照を必ず置く。
  外して建て直すと、建玉の倍率（1〜5倍）が決め直される。その効果と、発表を避けた効果を分けるためである。
- **V6 費用の上限は仕組みで守る。** 段階2では、月の上限額に達したら、その月はAIを呼ばない（コードで止める。心がけにしない）。実際の課金量は応答の利用量から数える。
- **V7 影のAIは、脳の外で動かす。** 段階2の仕組みは観測（分類②）として作り、脳のファイルに触れない。自分の意見は自分のファイルに書く。
- **V8 進むかどうかは、所有者が円の数字を見て決める。** 各段階の終わりに、下の「報告の形」で伝える。推奨は必ず書くが、既定は「進まない」。

## 4. 段階と関門

| 段階 | やること | 費用 | 関門（超えなければ、ここで終える） |
|---|---|---|---|
| **0** | 既にある影の記録を読む。AIが意見を言った回数、ルールと違う意見の回数、そのあと相場がどう動いたか、当時のAPI代 | 0円（所有者に読み取り専用のコマンドを1つ頼む） | なし（材料集め）。件数が少なくて何も言えなければ、そう書く |
| **1** | 「予定された発表」を規則にして、11年のテープで試す。上限（これ以上はAIにも出せない改善）を出す | 0円 | 事前登録した基準を、最良の候補が超える。かつ、その改善が、所有者の元手での損益分岐を超える |
| **2** | 前向きの影の評価。脳の外で、安いモデルを、月の上限つきで動かす。意見と根拠と、その後の結果を記録する | 所有者が決めた月の上限まで | 事前登録した件数か期間（短いほうではなく、両方）を満たした時点で、純便益がAPI代の3倍を超える |
| **3** | 権限を渡す（V2の範囲だけ）。脳の変更なので `PRODUCT_PROMPT.md` の分類⑤の手続き | — | 所有者の承認。単独リリース |

### 段階0：既にある記録を読む

- `signals` を読み取り専用で集計するスクリプトを書く（分類①。置き場所とテストは `PRODUCT_PROMPT.md` のとおり）。出すもの：AIを呼んだ回数、意見がルールと同じ／違う回数、
  違ったときの内訳（見送り・決済の提案）、その後N時間・N日の値動きとルールの実際の損益、`diagnose_live` と同じ式の概算費用。
- 所有者には、既にある形のコマンド1つ（`docker compose run --rm app python -m scripts.<名前>`）だけを頼む。出力は会話に貼ってもらい、**リポジトリには置かない**（集計した数だけを報告に書く）。
- 件数が少なければ「この記録からは、当たっていたとも外れていたとも言えない」と書く。少ない件数から結論を作らない。

### 段階1：予定された発表を、規則として試す

- **発表の日程**：FOMC、日銀の金融政策決定会合、米国の雇用統計、米国の消費者物価指数の、2015年から2026年までの日時を、公式の公表から表にする。
  出どころと取得日を記録する。取得できないものは、規則で作れるもの（例：雇用統計は原則として第1金曜）に限り、近似であると明記する。
  （相場データのホストは R5 のとおり迂回しない。中央銀行と統計局の日程は相場データではない。）
- **候補（3つまで。結果を見る前にコミットする）**。出発点の案：
  - A（遅らせる）：発表の前X時間は新しく建てない。発表の後に、ルールが建てると言っていれば建てる。
  - B（外す）：発表の前X時間に保有中の建玉を閉じ、発表の後にルールが建てると言っていれば建て直す。所有者の考えそのもの。V2の権限の外だが、**測るだけは測る**。
  - C（偽薬）：Bと同じ回数・同じ長さで、発表と関係のない時刻に閉じて建て直す。
- **測り方**：確定足方式・運用点（残高約27万円、0.01ロット刻み）で、近い長さ9通りの平均。コスト（スプレッド）を入れる。同じドローダウンの線で比べる。
- **上限を出す**：AとBそれぞれについて、「発表の日程を完全に知っている規則」が出した改善（年率・円）を、**AIに払える上限**として報告する。
  規則にできるものは、AIを使わずに規則として持てばよい（API代は0円）。AIが上乗せできるのは、規則にできない部分（予定にない発言など）だけであり、その大きさは段階2でしか分からない。
- 候補がどれも基準を超えなければ、結論は「発表を避けても得にならない。AIは付けない」で、ここで終える。

### 段階2：前向きの影の評価（所有者が鍵と上限額を出した場合だけ）

- 所有者に、数字を見せて尋ねる：月の上限額（提案：300円）、期間（提案：12か月、または意見がルールと違った回数が30件に達するまでの長いほう）、止める基準。
- 作り：脳の外の別プロセス（V7）。いちばん安いモデルから始める。呼ぶのは「1日1回」と「予定された発表の前」だけ。web検索は、上限額に収まる回数に絞る。
  プロンプトは、確認が既定で、例外的・具体的・差し迫った危険のときだけ「遅らせる」と言う形にする（見送りを作り出さない）。
- 記録するもの（自分のファイルに）：時刻、見た材料、意見、根拠、モデル、課金量。あとで、ルールの実際の損益と突き合わせる。
- 毎月、所有者に1行で伝える：今月のAPI代、意見がルールと違った回数、ここまでの純便益（円）、損益分岐までの距離。

## 5. 所有者への報告の形

各段階の終わりに、次の順で、円で伝える。

1. 結論を1行（進む価値がある／ない）。
2. 測ったこと：ルールだけの成績、候補の成績、偽薬との差。良いほうにも悪いほうにも、同じ大きさの字で。
3. お金の話：「この改善だと、API代に払えるのは月○円まで。いまの元手では○○、元手が○万円なら○○」。
4. 分からないこと：件数が足りない、近似の日程を使った、など。
5. 次に進むかどうかの選択肢（A 進む／B ここで終える）。推奨と、進む場合にかかるもの。

資産の増え方の見通しを尋ねられたら、次の事実を添える（2026-11の計算）：年9%なら27万円が100万円になるまで約15年、年4%なら約33年。
毎月2万円を足すと、年9%でも年4%でも、約2年半で100万円に届く。**この大きさの口座では、運用の上乗せより、足す金額のほうがずっと効く。**
元手を足すことを勧めるのではない（下落も同じ割合で大きくなる）。判断の材料として伝える。

`fxsim/docs/product/ai_value/` に置く：`JOURNAL.md`（回ごとの記録。`PRODUCT_PROMPT.md` の型）、`PREREG.md`（事前登録。結果より先にコミットする）、
`LEDGER.md`（試行の台帳）、`RESULTS.md`（段階ごとの結果と、所有者の決定）、`evidence/`（集計した数。本番の記録そのものは置かない）。

## 7. やらないこと

- 段階を飛ばす。段階1の結果が出る前に、AIの仕組みを作り込む。
- LLMに過去の相場を見せて「当たった」と数える。
- 候補を足して、良い結果が出るまで試す。基準を後から動かす。
- 保有中の建玉をAIに閉じさせる・減らさせる仕組みを、本番に入れる。
- 「プロのように」見える文章や画面を作って、成績の代わりにする。
- 損益分岐を超えない費用を、所有者に払わせる。

## 8. 最初のセッション

1. `PRODUCT_PROMPT.md` の規則と分類、`RESEARCH_RULES.md`、この指示書を読む。§2の事実を確かめる。
2. `ai_value/JOURNAL.md` を作る。
3. 段階0の集計スクリプトを書き、テストをつける。所有者に頼むコマンドを用意する（`docs/product/guide/RELEASE.md` を読んでから）。
4. 段階1の発表の日程を集め、出どころを記録する。事前登録（`PREREG.md`）を書いてコミットする。**ここで止まり、実行は次のセッションで**（事前登録が結果より先にあることを、履歴で示すため）。
5. 所有者に報告する：何を試すか、いつ結果が出るか、費用は0円であること、段階0のコマンドのお願い。
