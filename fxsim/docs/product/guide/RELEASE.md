# 本番に届ける手順

`docs/PRODUCT_PROMPT.md`（指示書）の一部であり、同じ拘束力を持つ。**稼働ファイルに触れる前、所有者に更新を頼む前に、全部読む。**
ここで言う「本番」は、所有者のPCで実マネーの建玉を持っているシステムのこと。用語（本番ブランチ・稼働ファイル・注文経路のファイル）は指示書の§2.1。

## 1. 何が、いつ本番になるか（いまの作り）

所有者のPCは、本番ブランチの作業ツリーをそのままコンテナにマウントして動かしている。compose のサービスは4つ：

| サービス | 中身 | いつ起動するか |
|---|---|---|
| `fx` | 脳（`scripts/run_ai_bridge.py`） | 常駐。PCの起動時に自動で戻る |
| `dashboard` | 画面（`app/server.py`） | 常駐 |
| `app` | 使い捨て。**健康診断など、所有者が打つコマンドはここで動く** | `docker compose run --rm app …` のたび |
| `tunnel` | 外から画面を見るためのトンネル（任意） | 所有者が有効にしたときだけ |

`fx`・`dashboard`・`app` は同じイメージ（`fxsim:latest`）を使い、同じ `.env` を受け取り、ブリッジのフォルダを読み書きできる形でマウントしている。

変更が効き始める時は、変えたものによって違う。**「再起動したら効く」と思い込まない。**

| 変えたもの | 効き始める時 |
|---|---|
| 健康診断・診断コマンドのコード | **`git pull` した瞬間**（次にコマンドを打った時から） |
| 画面のファイル（`app/static/`） | **`git pull` した瞬間**（ディスクから毎回読まれる） |
| 脳が実行中に読み直すデータ（`data/calendar.json`） | `git pull` の後、日付（UTC）が変わった時 |
| `app/server.py` とそれが読み込むもの | dashboard を再起動した時 |
| 脳（注文経路のファイル） | fx を再起動した時。**PCが再起動した時も**（確認なしで、その時の作業ツリーが動き出す） |
| compose の定義（ポート・マウント・環境変数・起動行）、`.env` | **`docker compose up` で作り直した時だけ**。`restart` やPCの再起動では効かない |
| Dockerfile・依存 | `--build` つきで作り直した時 |

- `docker compose up -d --build` と、サービス名なしの `docker compose up -d` は、イメージか定義が変わっていれば **fx も作り直す**（＝脳の再起動）。
  イメージは全サービス共通で作業ツリーを含むので、`--build` は文書だけの差でも fx を作り直しうる。
- 画面のファイルとサーバーを同時に変えると、pull から dashboard の再起動までの間、新しい画面が古いサーバーを叩く。項目が無くても壊れない画面にするか、
  pull と再起動を続けて行う手順にする。
- `data/calendar.json` はリポジトリが管理しているファイルだが、AI層が有効な時には脳自身が書き換える。所有者のPCで中身が変わっていると `git pull` が止まる。触るときは先に確かめる。

## 2. 本番ブランチの規則（R12の詳細）

1. **先頭は、いつ `git pull` されても、PCがいつ再起動しても安全であること。**
2. 稼働ファイルに触れるコミットは、**リリースできる状態**（レビューが乾いた・CIのジョブログを読んだ・所有者向けの手順と戻し方を書いた）になってから入れる。
3. 本番ブランチに置いてよい「まだ適用されていない稼働ファイルの変更」は、**同時に1つまで**。次を入れてよいのは、所有者が前のリリースを適用し、
   §4の確認の結果を返してから。`git pull` は先頭を丸ごと取る。脳の変更が先頭にある間に別の用件で pull されると、次のPCの再起動が、誰も見ていない時刻に、
   確認なしでそれを本番にする。適用されないまま7日たつか、12/24が来るなら、いったん取り消す（revert）。
4. 「まだどこからも読み込まれない新しいファイルは、いつ入れてもよい」という例外は、`app/`・`scripts/`・`mt5_ea/`・`data/`・`fxsim/` の直下には**使わない**
   （そこは稼働ファイルの置き場で、`app/static/` は置いた瞬間に配信される）。新しいモジュールは、それを読み込む変更と**同じリリース**で入れる。
   名前は、既存のモジュール・標準ライブラリ・固定した44パッケージのどれとも重ねない。テストと内部文書は、CIを赤くせず、`BAR_SPEC.md` のA1の
   「所有者のPCで走っても害がない」条件を満たす限り、いつ入れてもよい。
5. リリースのレビューの範囲は、最後のコミットの差分ではなく、**前のリリース（最初は基準のタグ）からの稼働ファイル全体の差分**（新しいファイルを含む）。
6. **機械の門**（分類①。M1-0の最初に作る）：注文経路のファイルの指紋（SHA-256）の台帳を置き、CIが照合する。台帳の更新を伴わない変更は赤になる。
   「うっかり混ざった」をCIが止めるためのもので、台帳を更新するコミットは、それがリリースであることを意味する。
7. コミットは `git add -A` や `commit -a` を使わず、**ファイル名を挙げて**行う。プッシュの前に、前のリリースからの稼働ファイルの差分の一覧を `JOURNAL.md` に貼る。
8. **書き手は1人。** プッシュの前に取得して、先頭が自分の知っているコミットであることを確かめる。知らないコミットが稼働ファイルに触れていたら、そこで止めて所有者に報告する。
9. **CIが走るのは、`main` と `claude/**` へのプッシュ、およびPR #9だけ。** 作業ブランチは `claude/` で始まる名前にする。稼働ファイルの変更は、
   作業ブランチでCIのジョブログを読んでから本番ブランチに入れる。別のブランチにプッシュできない環境では、Python 3.12 と `constraints.txt` を再現した環境での
   実行記録を暫定の証拠とし、本番ブランチに入れた直後のCIのジョブログを読むまで、所有者に更新を頼まない。
10. **基準のタグ**：M0で、`git diff 40771f9..HEAD` を稼働ファイルに絞って空であることを示した先頭に、注釈つきタグ `fxsim-baseline-2026-11` を打つ。
    タグをプッシュできなければ、ハッシュを `DECISIONS.md` に記録して代える。以後のリリースにも同じ形でタグを打つ。

## 3. compose と `.env` の変更

| 変えるもの | 分類 | 条件 |
|---|---|---|
| 新しいサービスを足すだけ | ② | 既存のサービスの定義・最上位の `volumes`/`networks`・Dockerfile・依存を1文字も変えない（要るなら④）。新しいサービスは `depends_on` を持たず、ブリッジとDBを読み取り専用でマウントし、秘密は**専用の env ファイル**から受ける（`.env` に行を足さない。`.env` は fx にも渡る）。所有者の手順は `docker compose up -d <新しいサービス名>` だけ |
| `dashboard`・`app`・`tunnel` の定義だけ | ③ | `docker compose config` の fx の部分が前後で同一であることを示す。適用は `docker compose up -d <そのサービス名>` |
| `fx` の定義、Dockerfile、依存、脳の起動方法 | ④ | 環境変数やマウントの1行でも④ |

- どの場合も、適用の前後で `docker compose ps` の fx の行の「作成からの時間」が変わっていないこと（＝脳が作り直されていないこと）を所有者に見てもらう（fx を出すリリースを除く）。
- compose のファイルは注文経路のファイルなので、§2のとおり1つのリリースとして入れる。
- **所有者が `.env` を編集する手順**（パスワード、レバ上限、通知先）は、どれも fx の起動構成に触れうる変更として扱う。編集の前に写しを取ってもらう。
  編集の後、適用はサービス名つきで行う（dashboard のための変更なら `docker compose up -d dashboard` だけ。fx は作り直さない）。
  追記をPowerShellのリダイレクト（`>>`）で行わせない（文字コードが変わり、先頭の行が壊れると、`Up` と表示されたまま脳が盲目になる）。メモ帳で開いて書き足してもらう。
  「いつ効くか」をリリースの説明に書く。

## 4. 暫定のリリース手順（安全に出す道＝C7ができるまで）

M4より前に本番へ届けるもの（M1・M2・前倒しの項目）は、次の形でだけ出す。C7そのものの出し方は§7。

1. **1回のリリース＝1つの変更。** 本番ブランチの先頭がそのリリースであり、ほかの未適用の稼働ファイルの変更が混ざっていない（§2-3）。
   1回のPC作業で出すのは1つ。例外は、脳に触れない分類③どうし：1つ目の確認が済んでから、同じ作業の中で2つ目まで続けてよい。
2. **戻し方を、リリースを頼む同じメッセージの中に書く。** 作者のセッションが応答しなくても、所有者だけで完結すること。形は固定する：
   ```
   git reset --hard <戻し先のハッシュ>
   docker compose restart fx
   docker compose logs --tail 30 fx
   ```
   （dashboard だけのリリースなら2行目は `docker compose restart dashboard`、compose の定義を変えたリリースなら `docker compose up -d <サービス名>`。）
   この形は、**最初のリリースより前に**、リポジトリの複製の上（GitHub Actions のコンテナ）で通しで演習し、記録を `evidence/` に残す。
   所有者が戻したら、作者は本番ブランチの側も取り消す（revert）。それが済むまで `git pull` しないよう伝える。
3. **時間の枠を書く**：「適用から20分で下の確認が揃わなければ戻す。戻して20分で揃わなければ、そのまま連絡する。**PCとMT5は再起動しない。**
   脳が動かないままでも、起きるのは『1時間半〜2時間後にEAが建玉を決済する』（設計どおりのフェイルセーフ）までで、損切りの注文はブローカーの側に残っている。」
4. 所有者の手順には**必ずサービス名**をつける。サービス名なしの `docker compose up -d` と `--build` は、依存を変えるリリース（④）以外では書かない。
   dashboard だけで済む変更は、**脳（fx）を再起動しない**。
5. 適用してよい時は§5。
6. **確認**（fx を出したとき）。
   適用の**前**に控えてもらうもの（見るだけ）：ログの最後の `restored state:` の行、`dials in force:` の行、健康診断のロット数。
   適用の**後**に確かめるもの：
   - (a) ログの `brain build` が新しい印。
   - (b) 直後の `restored state: intent … stop … seq …` が、控えた行と同じ値（建玉があるとき）。`re-armed`・`NO stop`・`state restore failed` の行が出ていない。
   - (c) `dials in force:` の行が、控えた行と1文字も違わない（それを変えるリリースでない限り）。
   - (d) 再起動から**12分以上たってから**の健康診断で、「脳稼働」が「心拍 N秒前」で **N が660未満**。健康診断は心拍が30分古くなるまで🟢を出すので、
     10分後の🟢は、前の脳が最後に書いた心拍でも出る。
   - (e) ロット数が前と同じ。
   どれか1つでも違えば、理由を調べずに、すぐ戻す手順へ。
7. **健康診断・画面だけのリリース**（M1-A）：健康診断は pull した瞬間に新しくなる。画面は dashboard の再起動の後。確認は、健康診断の出力に新しい文言が出ていること、
   画面が開けること、`docker compose ps` の fx の「作成からの時間」が変わっていないこと。
8. 12/24〜1/4 は出さない。年内に本番へ出す表示は、2026年の実際の休場（12/25と1/1が金曜）を模擬世界で流して誤報ゼロを確かめ、
   この期間に出うる「要確認／要対応」の文には「PCとMT5は再起動しないでください」を付ける。

## 5. いつ適用してよいか（R6(e)の詳細）

**コンテナだけの作業**（fx・dashboard の作り直しと再起動、Docker Desktop の再起動、`wsl --shutdown`）：
MT5がログイン済みで健康診断の「脳稼働」が🟢であることに加えて、**失敗しても直す時間が残る時**を選ぶ。優先の順：

1. 建玉が無いとき（決済されるものが無い）。
2. 相場が閉まっていて、開場まで12時間以上あるとき（脳が壊れても、開場の前に心拍が戻れば何も起きない）。
3. 平日で、所有者がこのあと2時間、連絡がつくとき。

避ける：週の取引が終わる前の3時間、休場の前日、開場の前の3時間、所有者がこのあと外出・就寝するとき。

**MT5かWindowsの再起動を伴う作業**（Windowsの更新、MT5の更新・入れ直し、2つ目のMT5の導入を含む）：
建玉が無いときが最良。建玉があるなら、**平日（月〜木）の相場が開いている時間帯に、所有者が画面の前にいるときだけ**。金曜の夜・週末・休場中・月曜の開場前には行わない
（指示書の§2.3）。日本時間の早朝（5:30〜8:30）は避ける。手順に時間の枠を入れる：
「直前の健康診断で心拍が10分以内 → 再起動 → Docker Desktop と MT5 の両方が戻り、MT5がログイン済みで、健康診断の心拍が再起動より後の時刻になるまでを**60分以内**。
40分たっても戻らなければ連絡する。」
「再起動して確かめてください」とは頼まない。確認は、まず見るだけのものから。

## 6. 所有者に渡してよいコマンドの形

所有者の文書に既にある形（2026-11-23時点）：`docker compose ps`／`docker compose restart fx`／`docker compose up -d fx`／`docker compose up -d dashboard`／
`docker compose up -d dashboard fx`／`docker compose logs --tail <数> fx`／`docker compose logs -f fx`／`docker compose run --rm app python -m scripts.run_monitor`／
`docker compose stop tunnel`／`git pull`／（依存を変えた時だけ）`docker compose up -d --build`。

- 同じ動詞で、文書に出てくる別のサービス名に替えたもの（`docker compose restart dashboard` など）は、既にある形として扱ってよい。
- 新しい形（§4-2の `git reset --hard` を含む）は、GitHub Actions かステージングで実際に動かしてから渡す。
- `OVERVIEW.md` などには今も「`git pull` → 再起動」が日常の手順として書いてある。こちらが声をかけるまでは行わないでほしい、と最初の報告で伝える（文書そのものを直すのはD5）。

## 7. 安全に出す道（C7）そのものを最初に出すとき

分類④は「C7ができてから」だが、C7自身（コードをイメージに焼く＝fx の定義・Dockerfile・起動方法の変更）と F1・C11 は、C7を使っては出せない。次の追加条件つきで、§4の形で出す。

1. GitHub Actions のコンテナ上で「今の起動方法 → 新しい起動方法 → わざと壊した版 → 自動で巻き戻り」を通しで演習した記録がある。
2. ステージング（デモ口座）で、週末を1回含む慣らしを終えている。ステージングが無い場合（所有者が置かないと決めた場合）は、1だけで出し、そのことを所有者に伝えて承認を得る。
3. 今の `docker-compose.yml` を戻し先として残し、戻し方（元の compose に戻して `docker compose up -d fx`）も演習してある。
4. **切り替えの合否**（所有者が見るだけで確かめる）：`restored state:` の intent・stop・seq が前と同じ／`dials in force:` が前と1文字も違わない／
   `re-armed`・`NO stop` が無い／心拍が切り替えより後。DBは同じファイルを指し続ける（置き場所を変えるのは別のリリース）。DBを見失うと、脳は次の判断でストップを
   現在値の1.5ATR下に置き直す。DBのパスと実行の同定（`runs.params`）が前後で同一であることをテストで示す。
5. **設定の読まれ方が変わる**：いま脳は `.env` を、compose 経由と、コード自身（作業ツリーの `.env` を直接読む）の2経路で読んでいる。イメージに焼くと後者が消える。
   所有者の `.env` と同じ形（項目名だけをもらい、値は伏せたもの）で、切り替えの前後の**実効値**が同一であることを示す（`docker compose config` の比較だけでは足りない）。
6. 実施は§5の窓で、所有者が画面の前、単独のリリース。
7. 本番とステージングでイメージの名前を共有しない。

F1（影モード）は、まず脳のファイルを書き換えずに作る（`BAR_SPEC.md` のF1）。それで足りれば分類②として、§3の「新しいサービスを足すだけ」の条件で出す。

## 8. 作りかけの運び方（`docs/product/wip/`）

- 別の作業ブランチが使えるなら、そこに置く（`claude/` で始まる名前）。使えないときだけ、パッチファイルで運ぶ。
- パッチの先頭に、何の変更か、当てる先のコミット、**当てた後の各ファイルの SHA-256** を書く。
- 当てるときは `git apply --check` を通し、ずれ（fuzz）や3方向マージを使わない。当てた結果のハッシュが記録と違えば、それは別の変更であり、レビューをやり直す。
- パッチを当てた作業ツリーからコミットするときは、ファイル名を挙げて追加する。`*.orig`・`*.rej` を残さない。
