# 練習用の環境（ステージング）と訓練

`docs/PRODUCT_PROMPT.md`（指示書）の一部であり、同じ拘束力を持つ。**ステージングを作る前、訓練の前、デモ口座や2つ目のMT5について所有者に何かを答える・手順を渡す前に、全部読む。**

ステージングとは、OANDAのデモ口座につないだ2つ目のMT5と、それを相手にする2つ目の脳のこと。EAの変更（分類⑥）と挙動の変更（分類⑤）を、
本番の前に確かめる唯一の場所である。置くかどうかは所有者が決める（`OWNER.md`）。

## 1. 手順ができるまで、所有者にさせてはいけないこと

所有者には、次をはっきり伝える（`FOR_OWNER.md` の「今日から守ってほしいこと（3つ）」の3つ目に入れてある）。

- **デモ口座と2つ目のMT5は、こちらが手順を渡すまで、開設しない・入れない・ログインしない。**
- とくに、**いま動いているMT5の中で**デモ口座を開いたり、別の口座にログインし直したりしない。MT5はその瞬間に口座を切り替え、EAは読み込み直されて、
  別の口座の残高と「建玉なし」を状態ファイルに書き出す。脳はそれを「外で決済された」と読み、新しい識別子で FLAT を書く。本番の口座に戻った瞬間に、
  EAはその FLAT を実行して、本物の建玉を決済する。脳がその間に建て直せば、ロット数はデモ口座の残高から計算される。
- OANDAのインストーラをもう一度実行するのも同じ（動いているMT5を閉じることがある。閉じれば指示書の§2.3の形になる）。
- 既存の文書（`MT5_SETUP.md` など）の「デモ口座でログインしてEAを付ける」は、本番が動いているPCでは行わない。

## 2. 同じPCに置くときの危険

同じWindowsユーザーの2つのMT5は、**同じ `Common\Files` を共有する**。デモ側のEAを既定のファイル名のまま付けると、30秒ごとに本番の状態ファイルを上書きし、
本番の脳がデモ口座の残高と建玉を読む（残高が違えばロット数まで変わる）。逆に、ステージングの脳が本番のフォルダを向くと、本番の脳がロックを手放した瞬間
（リリースで fx を作り直した時など）にロックを取り、本番の口座を別のDBの状態で動かす。

別のPC・別のWindowsユーザー・仮想マシンに置けるなら、そのほうが分離は強い（`Common\Files` が別になる）。所有者に用意できるか尋ねる。

## 3. 分け方（同じPCに置く場合）

分けるのは**フォルダ**である（ファイル名ではない）。脳のファイル名とロック名はコードの定数で、変えるには注文経路のファイルの変更（分類④）が要り、
変えた時点で「本番と同じコードを試す場所」ではなくなる。

- **ステージング用のEA**は、既定の3ファイルが `Common\Files` の下の**専用のサブフォルダ**を指す別ビルドにする（入力を変え忘れても本番のファイルに触れない）。
  .mq5／.ex5 の名前も、マジック番号も、本番と別にする（本番の端末で誤ってコンパイルしても、チャートのEAが入れ替わらない）。
  本番ビルドとの差が、生成した定数（ファイル名・ビルド印・マジック番号）だけであることを、CIのテキスト差分で示す。
- **ステージングの脳**は、本番と**同じコード**を、そのサブフォルダをマウントして動かす。
- **ステージングのフォルダを、本番のフォルダのコピーで作らない**（`.env` と `data/fxsim.db` まで複製され、本番の `Common\Files` をマウントしてしまう）。
  新しく取得し、`.env` は専用の雛形から作る。
- compose は、プロジェクト名・イメージ名・ポートを本番と別にする。ブリッジのフォルダの指定が、未設定・本番と同じ・専用のサブフォルダでない、のどれかなら、
  **起動用のスクリプトが起動を拒否する**（脳のコードには入れない）。
- DBも別のファイル。
- **ステージング用のEAは、本番の口座では取引しない。** 起動時と毎回の点検で口座の種別を調べ、デモ口座でなければ、注文・変更・決済を一切行わず、チャートに
  「これは練習用のEAです。本番の口座では動きません。外してください」と出す（MQL5 の口座種別の問い合わせを使う。デモの端末で確かめるまで「こちらでは未確認」）。
  ファイル名は入力にせず、専用のサブフォルダ名を定数として必ず前に付ける（入力やテンプレートで本番のファイル名を指せない）。
- 本番の端末のチャートにステージング用のEAを付けると、本番のEAが外れる（1つのチャートにEAは1つ）。「EAのファイルを置く」「チャートに付ける」手順の直前に、
  その端末に表示されている口座がデモであることを見る一手を入れる。
- **ステージングの compose は別のファイル・別のサービス名**（例：`fx-stg`・`dashboard-stg`）にする。マウントは「所有者が指定したフォルダ ＋ 固定のサブフォルダ名」とし、
  サブフォルダ名は compose の側に書く（`.env` に本番の Common\Files をそのまま貼っても、コンテナからは本番の3つのファイルとロックが見えない）。
  起動用スクリプトの拒否は残すが、それだけに頼らない（`docker compose up -d` を直接打つと通らず、PCの再起動後の自動起動も通らない）。
- 訓練と日常の手順に書くコマンドは、**本番のフォルダで打つと「そのサービスはありません」で止まる名前だけ**にする（`docker compose stop fx` は、本番のフォルダで打てば本番の脳を止める）。

## 4. 作る手順の条件

- R6(e) の「MT5の再起動を伴いうる作業」として扱う（インストーラが本番のMT5を閉じうる）：建玉が無いときが最良。建玉があるなら、平日の相場が開いている時間帯に、
  所有者が画面の前にいるときだけ。週末・休場中・月曜の開場前は不可。
- デモ口座はブローカーのウェブサイトで開設し、**本番の端末では開かない**。2つ目のMT5は別のフォルダに入れ、本番の端末のログイン先を一度も変えない。
- 手順の前後で、本番の状態ファイルの残高・ロット・実行済みの識別子が同じであることと、本番の端末に表示されている口座が変わっていないこと（見るだけ）を確かめる。
  作った直後に、本番の健康診断が🟢のままであることを見る。
- Windows・MT5の画面の手順は、こちらでは確かめられない。「こちらでは未確認」と明記し、1段ずつ、見えている文言を教えてもらいながら進める。
- 所有者の作業は、1回・1時間前後の見込み（目安）。PCが重くならないかの確かめ方を先に案内する。

## 5. 証拠（C11）

- 設定の照合ではなく、**動いているコンテナ**の実際のマウント元・プロジェクト名・イメージ・DBのパスを読み、本番と1つも重ならないことを示す点検
  （GitHub Actions で2つのプロジェクトを立てて演習済み）。所有者のPCでは、点検の出力を貼ってもらう。
- 「動いているステージングのコンテナの中から、本番の `steady_signal.txt`・`steady_status.csv`・`steady_brain.lock` が**見えない**」ことを確かめる点検。
- 「ステージングの脳が本番のフォルダを向いて起動した」場面で書き込みがゼロなのは、本番の脳が心拍を続けている間だけである（ロックの証拠であって、分離の証拠ではない）。
  同じ場面で本番の脳を作り直すと、ステージングの脳がロックを取って書く。これを「既知の危険」の再現として1本持ち、上の点検が要る理由として残す。
- ステージング用のEAが、本番を模した口座種別に対して注文ゼロで終わることを、適合ベクトルとデモ端末で示す。
- ステージングで何かを操作する手順には、「いま触っているのがデモ側の端末・ステージング側のフォルダである」ことを確かめる一手を必ず入れる。

## 6. 訓練（C10）

故障を2種類に分ける。

**(a) 双子だけに閉じる故障**：ステージングの fx を止める、デモ側のMT5をログアウトする・閉じる・起動し直す、デモ側のアルゴ取引を切る、ステージングのDBを壊す。
ステージングで実際に起こし、検知・通知・回復が設計どおりかを記録に残す。A9のドリル（デモ側のMT5を落とし、期限が切れた後に戻す）もここ。

**(b) PC全体に及ぶ故障**：Docker Desktop の停止、回線断、電源断、Windowsの再起動、スリープ。
**本番が動いているPCでは決して起こさない**（本番の建玉に対して11/16を再現することになる。指示書の「確かめるための再起動を頼まない」が優先する）。
別のPC・別のWindowsユーザー・仮想マシンがあるときだけ、そこで行う。無ければ、次で代える：

- GitHub Actions のコンテナ上での模擬（Docker の停止と再開、ネットワークの遮断）と、模擬世界（D1・A2）での訓練。
- R6(e) の条件で所有者がどうせ行う再起動（保留中の Windows Update など）を、「観察つきの実地記録」として残す。

その場合、`BAR.md` には「PC全体の故障は、実機では自然発生分のみ」と書く。

## 7. 実機での受け入れ記録（A10）

ステージングができた直後に、`BAR_SPEC.md` のA10の一覧を、ステージングの名前空間で採る。本番のファイルには触れない（§3の仕組みで強制する）。
ログアウト中・切断中のEAが状態ファイルに何を書くか（指示書の§2.3で「分かっていないこと」）は、ここで初めて観測できる。観測したら、C1aの文言とA5の仕様を事実に合わせる。

## 8. 所有者が置かないと決めた場合

C11、C7のステージング分、M5のEAの変更すべて、C10の(a)、A10、D7の実機部分は「対象外」にして `DECISIONS.md` に記録する（`EA.md` の§7）。
M4の関門は「影の並走で差分ゼロ。壊した版が GitHub Actions 上で自動で巻き戻る」に読み替える。分類⑤の変更は、ステージングでの慣らしの代わりに、
模擬世界での全場面の通過と、所有者への説明と承認を条件にする——それでも足りないと判断したら、出さない。
