## 1. Operations (unattended running on a home Windows PC)

### Summary

LENS: unattended operation on a home Windows PC. Method: read the live path (scripts/run_ai_bridge.py, mt5_ea/SteadyBridge.mq5, app/bridge.py, app/monitor.py, scripts/run_monitor.py, app/server.py, docker-compose.yml, docs), ran the suite (274 passed in 64 s, `python -m pytest tests -q -p no:cacheprovider`), and replayed the 2026-11-16 incident through the real `R.main()` loop with a model of the EA's expiry branch. Scratch scripts (repo untouched, `git status` clean): docs/product/baseline/sre/repro_1116.py and docs/product/baseline/sre/frozen_weekday.py.

HEADLINE. The order path is hardened against its own bugs, but the HOST layer (Windows session, MT5 login, Docker Desktop, power, network) has no detection that names a cause, no notification at all, no preflight and no supervised update. docs/COVERAGE.md has no row for any host component. The only boot-chain guidance in the repo is one line (docs/AI_TRADER.md:197, Docker autostart) plus "make a habit of `docker compose ps` after a reboot" (:198). Nobody is paged: a grep of all .py/.mq5/.yml/.md/.html for SendNotification, Alert(, webhook, smtp, ntfy, slack, discord, telegram, pushover returns zero hits. The health check runs only when the owner pastes a command (docs/OVERVIEW.md:130 "weekly") and always exits 0 (no sys.exit in scripts/run_monitor.py).

11-16 RECONSTRUCTED AGAINST THE CODE (replay output matches the incident: 28 BLIND lines 02:22-06:52, 16 failed closes 06:54:41-07:02:11, heartbeat back at 07:02:30, zero DB rows):
1. Not-logged-in EA exports balance 0.00 / equity 0.00 / position 0.000 with an advancing clock and correct build (SteadyBridge.mq5:186-196). The EA never reads TERMINAL_CONNECTED, ACCOUNT_LOGIN or any *_TRADE_ALLOWED (grep: 0 hits).
2. Brain: `_trend_gate` returns None on `equity <= 0` with NO log line (run_ai_bridge.py:529-530). The two messages that would have named a cause are unreachable: "EA status untrusted" (1157) sits inside `if probe is not None`, and "waiting for EA status" (751) is in decide_once, which blind mode skips (1124). So docs/OVERVIEW.md:164 ("MT5 not running -> `waiting for EA status`") describes a line the resident loop cannot print in this state.
3. After the restart intent_lots is 0.0 (1051) until a trusted probe (1221-1222), so the heartbeat guard (1432-1433) wrote nothing at all: the 30-minute grace of line 1087 did not apply, and the standing EXP was the pre-reboot one (about 03:36). The only output was "BLIND Nm while LONG (no trusted feed)" (1427).
4. EA while offline: expiry branch (mq5:335-343) sees CurrentLots()==0 and does nothing. On login the position appears, the EXP is long lapsed, and CloseAll runs every 30 s with the result unchecked (mq5:226, 337-340). The brain polls every 600 s, so it structurally loses this race: the weekday variant of the replay closes the position on the first EA tick (06:54:41) and the brain adopts FLAT at 07:02:30, then re-enters on a later closed bar at a re-drawn leverage (the "lottery").
WOULD HAVE FIRED (only if someone looked): MT5 chart comment "!! BRAIN SILENT !!" from about 03:36 (mq5:121-123, blames the brain); run_monitor brain-liveness RED from about 30 min after the last heartbeat, with the WRONG cause and remedy ("brain heartbeat stopped -> `docker compose restart fx`", monitor.py:332-337); /live `stalled` with the same text (server.py:306-307).
WOULD NOT HAVE FIRED: EA-liveness (status fresh, monitor.py:349-363 — and it appends no row when healthy); bar freshness (about 50 h < 75 h); clock; EA build; run freshness (<30 h); execution match (YELLOW "cannot judge", the book read as FLAT); the brain's frozen-status, torn-row, skew and lock checks. `signal_expired` is passed to build_report (run_monitor.py:366) but never used (monitor.py:187 only). After 07:03 every instrument was normal and nothing durable recorded the event.

RELATED LATENT CASE (Python side verified, MT5 side an assumption to drill): a terminal that loses the broker connection mid-week but stays running keeps exporting cached account and bars. The brain trusts any feed younger than 75 h on any weekday (bridge.py:34, run_ai_bridge.py:140-144); frozen_weekday.py shows probe TRUSTED and monitor all GREEN at 2, 12, 36, 60 and 74 h, RED only at 76 h. The broker stop is then the only protection, and no instrument verifies it exists (status has no SL column).

TIME-CRITICAL. 2026-12-25 and 2027-01-01 are Fridays (docs/OVERVIEW.md:166). A Windows Update reboot inside either closure replays 11-16, and the fail-safe then closes at the reopening gap price. Until gap 1 is fixed, the zero-code mitigation is to pause Windows Update and forbid restarts across those weeks.

WHAT A PRODUCT NEEDS, in order: (1) the terminal-offline fail-safe race closed; (2) every blind/idle state carrying a named cause, the same in log, health check and dashboard; (3) push to the owner's phone plus an external dead-man switch; (4) a Windows-native preflight/watchdog after every boot; (5) session-aware feed freshness; (6) observed (not assumed) broker stop; (7) one-command update with automatic rollback; (8) state backup and a brain that survives an unreadable DB; (9) an SLO ledger for "minutes without a supervised position".

### Gaps

#### operations-1 [P0·L] The fail-safe closes a healthy position after a terminal-side outage (the 11-16 race is structural, not luck)

- **Evidence.** mt5_ea/SteadyBridge.mq5:335-343 closes on any lapsed EXP the moment a position is visible; the EA ticks every 30 s (InpTimerSec, :24) while the brain polls every 600 s (run_ai_bridge.py:950), so after a login the EA acts first about 95% of the time. After a brain restart no heartbeat is written until a trusted probe because intent_lots starts at 0.0 (run_ai_bridge.py:1051, guard 1432-1433), so the 30-min grace of :1087 does not apply. Replay `python .../product-gap/sre/repro_1116.py`: actual case = 0 heartbeats 01:42-07:02, 16 failed closes 06:54:41-07:02:11; `repro_1116.py weekday` = 'FLAT fail-safe -> CLOSED' at 06:54:41, brain logs 'book closed EXTERNALLY ... adopting FLAT' at 07:02:30. tests/test_ea_protocol.py FakeEA has no 'not logged in' or 'market closed' state, so no test can see this.
- **Why it blocks product grade.** A protection mechanism destroys the thing it protects in an ordinary home-PC event (update reboot, weekend terminal restart, broker login failure). During the outage the EA could not have closed anyway and the broker stop was still live, so withholding bought no safety; the forced close then re-enters at a re-drawn leverage, which docs/OVERVIEW.md says decides most of the return. It will recur at the 12-25 and 1-1 closures, at a gap price.
- **Done.** (1) A written, pre-registered rule for 'EXP lapsed while the EA itself was offline' (for example: on regaining connection the EA waits one brain poll plus slack for a fresh heartbeat, provided a broker stop is confirmed on the position, before the fail-safe applies), added to docs/COVERAGE.md as a new invariant. (2) FakeEA gains offline/login/market-closed states; a test replays 11-16 in its weekday form through R.main() and ends with the same lots, the same SEQ and zero close attempts. (3) Control tests still pass: a truly dead brain is flattened within TTL + grace; a brain that stays blind after reconnect is flattened within the new bound; no path re-opens a closed position. (4) The existing 274 tests pass unchanged. (5) Drill checklist on a DEMO terminal, signed off: restart MT5 on Saturday, leave it until Monday open, position intact, journal shows no close attempt. (6) EA_BUILD and EA_BUILD_EXPECTED bumped together and the handshake goes RED on a mismatch.
- **Risk to live.** HIGH. This edits the last line of defence (invariant I3) and requires recompiling and re-attaching the EA on the live chart. A wrong grace keeps an unsupervised position open longer; a wrong connected-test disables the fail-safe entirely. Stage on a demo account first, make status changes column-additive (old readers parse the first six), deploy with a flat book or at the weekend, and keep the old .ex5 for rollback.

#### operations-2 [P0·M] Blind and idle states carry no cause; the health check misdiagnoses a terminal outage as a dead brain and prescribes the wrong remedy

- **Evidence.** run_ai_bridge.py:529-530 returns None silently on equity<=0; the cause-naming lines at :1157 and :751 are unreachable in this state; the only output is 'BLIND Nm while LONG (no trusted feed)' (:1427). Replay monitor snapshot mid-outage: brain-liveness RED 'heartbeat stopped 144 min ago -> `docker compose logs fx` ... `docker compose restart fx`' (app/monitor.py:332-337), EA-liveness row absent (monitor.py:349-363 fires only on a stale clock, and the offline EA's clock advances), execution match YELLOW. /live shows the same wrong reason (app/server.py:306-307). `signal_expired` is computed (scripts/run_monitor.py:219, 366) and never used (app/monitor.py:187). docs/OVERVIEW.md:164 promises a 'waiting for EA status' line the resident loop cannot print when blind.
- **Why it blocks product grade.** A stranger without the developer acts on what the instrument says. Here it says 'restart the brain' while the brain is healthy and the real remedy is 'log MT5 in'. Every named-cause alert, runbook entry and SLO record depends on the system knowing why it is blind.
- **Done.** (1) The EA status row carries, additively: terminal connected, account login/server, terminal/EA/account trade-allowed, last tick time, and does not present offline zeros as a real book. (2) The brain classifies every non-trusted probe into a closed list of cause codes (for example MT5_NOT_LOGGED_IN, MT5_DISCONNECTED, EA_NOT_EXPORTING, ALGO_TRADING_OFF, BARS_STALE, BARS_SHORT, CLOCK_SKEW, STATUS_UNREADABLE, MOUNT_UNWRITABLE, LOCK_WAIT) and logs it on the FIRST blind poll, not after 40 minutes. (3) run_monitor and /api/live print the same code and its one-step remedy; a table-driven test injects each cause and asserts code and remedy text in log, monitor and API. (4) Replaying 11-16 yields 'MT5 is not logged in to the broker -> open MT5 and log in' and never 'restart fx'. (5) run_monitor exits non-zero on RED and offers machine-readable output. (6) A docs test: every log message quoted in docs/*.md exists in the code.
- **Risk to live.** MEDIUM. Brain-side classification and monitor text are low risk if they only label states and do not change which probes are trusted. The new status columns need the EA recompile of gap 1 (do both in one EA build). Monitor changes must not turn a healthy state RED (invariant I10): run the existing monitor tests plus the new table.

#### operations-3 [P0·M] Nobody is told: no push channel, no dead-man switch, health check only on demand

- **Evidence.** grep over the whole repo for SendNotification, Alert(, webhook, smtp, ntfy, slack, discord, telegram, pushover: zero hits. The health check is run by pasting a command about weekly (docs/OVERVIEW.md:130); the dashboard is pull-only and needs the PC and Docker alive (docs/REMOTE.md); the EA's 'BRAIN SILENT' is a chart comment on the PC screen (mq5:116-129). On 11-16 the owner noticed nothing for 5 h 20 min and afterwards every instrument read normal. Time to human notice today: up to 7 days for a standing fault, never for one that self-heals.
- **Why it blocks product grade.** Unattended operation without notification means the mean time to detect equals the owner's checking habit. Everything that needs a human (MT5 login, Docker Desktop dialog, algo trading off, power loss) waits for a look at a screen.
- **Done.** (1) A notifier outside the order path sends to the owner's phone on every cause code of gap 2 held longer than a per-code threshold, on fail-safe fired, on external close, on recovery, plus a daily or weekly 'alive, position X, N incidents' digest. Messages are in plain Japanese with cause and one-step remedy, de-duplicated. (2) An external dead-man heartbeat (a service that alerts when pings STOP) covers PC off, sleep, network down, Windows frozen: the cases where nothing on the PC can speak. (3) One 'send test notification' command, also run by the preflight. (4) Drill checklist, each producing a phone message within the stated minutes: stop the fx container; quit Docker Desktop; quit MT5; log MT5 out; turn algo trading off; unplug the network; power the PC off. (5) Notifier failure never affects the brain (test: endpoint unreachable, loop timing unchanged). (6) Secrets live only in .env; nothing but the alert text leaves the PC.
- **Risk to live.** LOW if built as a separate process or container that only reads the bridge files, the DB and logs. Risks to control: alert storms (rate-limit), false alarms that train the owner to ignore it (thresholds validated on a replay of weekends and holidays), and leaking balance or account data to a third-party service (the owner chooses the channel).

#### operations-4 [P0·L] No boot chain and no preflight: nothing verifies the dozen dependencies after a reboot, and nothing runs natively on Windows to watch Docker itself

- **Evidence.** The only boot guidance is docs/AI_TRADER.md:195-198 (Docker Desktop autostart, then 'make a habit of `docker compose ps`'). No document or script covers: reaching a signed-in desktop after an update reboot, MT5 autostart and saved login, EA attached with algo trading on, sleep/hibernate, Windows Update timing, disk space, WSL memory (grep for powercfg, netplwiz, active hours, startup, sleep in the current docs: only DOCKER.md disk hygiene and one historical line in GOLIVE.md:63). No compose healthcheck (docker-compose.yml). Everything that watches runs inside Docker, which is itself a dependency that dies with Docker Desktop (AI_TRADER.md:195 says so). docs/COVERAGE.md has no host row. scripts/mt5_check.py is for the abandoned IPC path.
- **Why it blocks product grade.** On 11-16 MT5 and Docker 'came back by themselves' by an undocumented, unverified mechanism, and the one link that did not (broker login) was checked by nothing. A product has a specified boot chain and proves after every boot that it held, or names the broken link.
- **Done.** (1) A boot-chain document listing every link with what restarts it and what verifies it. (2) A Windows-native preflight (PowerShell, registered by an installer as a Task Scheduler job at logon and every few minutes) that prints named PASS/FAIL checks and exits non-zero: Windows last boot time and reason, pending-reboot flag, sleep/hibernate off, update active hours and restart window, MT5 process, status fresh, terminal connected and logged in to the expected account, algo trading allowed, EA build, bar count and session freshness, Docker engine, fx and dashboard Up with a stable restart count, brain build and running commit, heartbeat fresh with EXP in the future, mount writable via a probe file (never the signal or lock), clock skew <300 s, free disk above a floor, broker stop present when long, no leftover second writer (old Task Scheduler job). (3) Safe self-remedies only: start Docker Desktop, `docker compose up -d dashboard fx`, start the terminal; it never writes the signal, lock or DB. (4) After every boot the owner's phone gets 'boot OK' or the named FAIL within N minutes. (5) Drill checklist: three unattended reboots (weekday, Saturday, forced update restart) each end all-PASS or with the correct named FAIL. (6) Unit tests run the preflight logic against fixture directories on Linux CI.
- **Risk to live.** LOW to MEDIUM. Read-only checks are safe. Auto-starting Docker or MT5 is safe because the lock and SEQ gate already tolerate restarts. ## 6. Security and distribution

### Summary

Lens: security, privacy, distribution rules. Read-only; scratch probes are in docs/product/baseline/security/ (probe.py, foreign_writer.py). The suite still passes (274 passed, run against a scratch DB) and the repo is unchanged.

Verdict: the system is careful about what its OWN brain may do, and has almost no defence against anything that is not its brain. Every limit (5x leverage, the stop, SEQ/EXP) is enforced by the Python side; the EA executes whatever one unauthenticated text line says.

- **Order channel:** on the test suite's own EA transcription, overwriting steady_signal.txt with "LONG 2.00 SEQ 9999999999" made a 0.09-lot book add 1.91 lots. "LONG 2.00" on a flat book bought 2.00 lots with no stop and no expiry. Only the broker's margin bounds this.

REMOTE.md "method B" quick tunnel bypasses the tunnel guard (probe: 200 with no password). /docs, /openapi.json, /redoc and /static answer 200 without credentials when a password is set. 300 wrong guesses were answered in 1.09 s with no lockout. ### Gaps

#### security-compliance-1 [P0·L] The EA has no safety limit of its own: no hard maximum lot, no mandatory stop, expiry or id, no price or account-state sanity check, no kill switch

- **Evidence.** mt5_ea/SteadyBridge.mq5:20-29 has no max-lot or max-leverage input. NormalizeLots (203-216) clamps only to the broker's SYMBOL_VOLUME_MAX. SL, EXP and SEQ are all optional (321-329). Expiry is checked only if present (335). An unsequenced line counts as a new order whenever its text differs (62-69). The add leg is trade.Buy(add, InpSymbol) with no stop (441). A grep of the EA for InpMax, TERMINAL_CONNECTED, ACCOUNT_TRADE_ALLOWED, ResultRetcode or kill returns nothing. I ran the test suite's own transcription (tests/test_ea_protocol.FakeEA) from scratch foreign_writer.py: 'LONG 2.00 SEQ 9999999999' on a 0.09 book gave 'add 1.91'; 'LONG 2.00' on a flat book gave 'buy 2.00', sl 0.0, never expiring. The brain's own cap is --max-lots 5.0 (scripts/run_ai_bridge.py:943), about 50x what this account holds. On 2026-11-16 the same EA tried 17 closes from a not-logged-in view of the world.
- **Why it blocks product grade.** A product cannot let one text line decide position size up to the broker's margin limit (roughly 25x here, against a designed 5x) with no stop. RTS 6 pre-trade limits and kill functionality must sit at the execution point and work when the strategy process is wrong, absent or impersonated. Today both families are empty, and a stranger has no developer to notice.
- **Done.** 1. EA inputs for a hard maximum lot and a maximum notional-to-equity ratio; anything above is refused with a logged reason. 2. Opening or increasing requires SEQ, EXP and a valid SL together; an unsequenced or stop-less LONG may only reduce or close. 3. The added leg carries the stop at fill. 4. The EA takes no trading action unless the terminal is connected, the account is logged in with trading allowed, and balance is above 0. 5. A bid sanity band (for example the SL must lie within N ATR of bid). 6. A documented kill with two modes, tested on a demo account: 'stop opening' and 'flatten now'. 7. The transcription tests cover each refusal, and a demo-account conformance script replays the forged lines above and shows zero fills. 8. The EA build tag is bumped together with app/bridge.py:31.
- **Risk to live.** Highest of all gaps: it needs a recompile and re-attach of the EA while a position may be open. A cap set too low, or a new mandatory-token rule that the current brain's lines do not satisfy, would silently refuse legitimate orders. A build-tag mismatch turns the monitor red. Do it flat or at the weekend, on a demo account first, with the brain change shipped and verified before the EA starts enforcing.

#### security-compliance-2 [P0·M] The order channel is an unauthenticated file writable by many parties, and the internet-facing container is one of them

- **Evidence.** docker-compose.yml:25-27 mounts the repo (./:/app, which includes .env and the code the fx container runs) and the MT5 Common\Files folder read-write into the dashboard service; fx (48-50) and app (99-101) get the same. The EA accepts it (see the EA-limits gap). docs/COVERAGE.md:53 lists I8 for 'docker-compose / Dockerfile / .env' as never attacked, and I8 covers only a second brain, not a foreign writer.
- **Why it blocks product grade.** 'Who is allowed to move money' is not defined anywhere. A stranger's PC will also have other EAs and sync tools the developer never saw.

The signal line carries an authenticator (for example an HMAC over action, lots, SEQ, EXP and SL with a per-install secret set as an EA input); the EA refuses risk-increasing actions without a valid one, and the transcription tests prove a forged line, a replayed old line and a line from an older install cannot open or increase. 4. - **Risk to live.** Medium to high. Making the mounts read-only for the dashboard is low risk, but it must not touch the fx service's write path or the SQLite file the dashboard initialises (app/server.py:66-68 calls db.init_db). Signal authentication changes the wire protocol on both sides and must roll out brain first, EA accepting both forms, then EA enforcing; otherwise the EA refuses real orders or the fail-safe closes the position.

#### security-compliance-3 [P0·M] Dashboard authentication fails open, and parts of it are reachable without credentials

- **Evidence.** docker-compose.yml:17-18 publishes 8000 on all interfaces, app/server.py:423 binds 0.0.0.0, and the .env.example default is an empty password, which means open (server.py:53-54). docs/REMOTE.md:41-47 'method B' is a quick tunnel that needs no token, so the 503 guard (keyed on the token variable, server.py:44-52) never fires. Scratch probe.py results: with no password and tunnel-style headers, /api/live returned 200. With a password set, /static/live.html, /static/app.js, /docs, /openapi.json and /redoc returned 200 without credentials. 300 wrong passwords took 1.09 s, all 401, with no lockout or delay. With a Japanese password (REMOTE.md:13 suggests 'any long password you like', in Japanese) the correct credentials got 401 and a wrong ASCII one got 500. Responses carry no security headers, and there is no Host check.
- **Why it blocks product grade.** The owner's balance, equity, position and decision log are the private data of this product. The documented remote path can publish them to the internet with no login, and when a login exists it can be brute-forced at about 275 guesses per second. A non-programmer cannot be expected to know that 'method B' skipped the only guard.
- **Done.** 1. The published port is bound to 127.0.0.1 by default. 2. Any request that is not from loopback (or that carries forwarding headers) is refused unless a password of minimum strength is set; tests cover the quick-tunnel case. 3. /docs, /openapi.json and /redoc are disabled or behind auth, and static assets are behind auth or shown to contain no data. 4. Failed logins are rate-limited or locked out, with a test asserting the delay. 5. Non-ASCII passwords either work or are rejected at startup with a clear message. 6. REMOTE.md method B is removed or made to pass through the same gate, and Cloudflare Access is described as the primary gate. 7. A test enumerates every route and asserts 401 without credentials.
- **Risk to live.** Low for the trading path (the dashboard does not trade). The risk is locking the owner out of their only phone view, or breaking localhost access on Docker Desktop if the bind is changed wrongly; verify from the Windows host before and after.

#### security-compliance-4 [P1·M] Dashboard input and output handling: unescaped model text, path-taking POST, writes into the live database

- **Evidence.** app/static/live.html:129-151 builds the decision list with innerHTML from x.reason, x.factors and x.plan. Those strings are the model's output after web search (app/ai_trader.py:103-113, 133-134) or raw exception text ('AI error: {exc}', ai_trader.py:115), stored in the DB and served by server.py:379-406; app.js:174-180 and 186-195 do the same for trade reasons and fundamental views. POST /api/backtest passes the caller's 'instrument' into a filesystem path (app/providers/csv.py:52-58): the probe showed an absolute path is accepted (400 'no candles' after reading my scratch CSV) and a traversal string returns a 500 that discloses the server's data directory. bars='x' returns a bare 500. Each run is persisted into the same SQLite file the brain writes (3 small runs took the scratch DB from 0 to 708,608 bytes; the cap is 20,000 bars per run with no limit on the number of runs).
- **Why it blocks product grade.** With the AI overlay enabled, a web page the model reads can plant script that runs in the owner's logged-in dashboard and reads the account data (latent today only because the key is disabled). Any dashboard user, or anyone on the LAN in the default open mode, can grow the live database without bound and contend for its lock with the trading process.
- **Done.** 1. All DB-sourced text is rendered with textContent or an escaping helper; a test feeds '<img onerror>' through the decision log and asserts it arrives inert; a Content-Security-Policy without inline script is set. 2. 'instrument' and 'granularity' are validated against an allow-list; errors return a fixed message. 3. Backtests triggered from the dashboard write to a separate database (or are removed from the product dashboard), and the dashboard opens the live database read-only. 4. Tests assert the traversal, absolute-path and bad-type cases each return 400 with no path in the body.
- **Risk to live.** Low to medium. Opening the live DB read-only from the dashboard must not break the startup init_db call or /api/live; moving backtest rows changes what latest_live_run_id sees (it already excludes backtests). No effect on order flow.

#### security-compliance-5 [P1·M] Secret and personal-data hygiene: keys in object repr, every secret in every container, personal identifiers in the docs, undeclared data flow to the AI provider

- **Evidence.** The Settings dataclass has default repr and holds oanda_token and anthropic_api_key (app/config.py:149-157, 234); the probe confirmed both fake values appear in repr(settings). env_file gives the whole .env to dashboard, fx and app (docker-compose.yml:19-21, 41-43, 93-95). The tunnel token is passed on the command line (compose:76), visible in docker inspect. docs/MT5_SETUP.md:29-30 tells the user to put the broker login and password in .env for a legacy path (scripts/run_mt5_live.py:49-50); app/brokers/kabu.py:57-58 reads a stock order password. The owner's Windows user name appears in 9 lines of 7 docs (git grep 'C:\\Users\\...': OVERVIEW.md:105,121, DOCKER.md:25,32,116 and others). When the overlay is on, balance and equity are sent to the API (scripts/run_ai_bridge.py:719-723 into ai_trader.py:108-110) and nothing tells the user. There is no secret scan in CI, no rotation procedure, and no redaction step for the logs the owner pastes to a developer.
- **Why it blocks product grade.** A product's support loop is 'send us your logs'. Today nothing guarantees those logs are free of keys (one print of the settings object or one traceback is enough) or of balances the user did not mean to share. Shipping the original owner's user name and telling users to store a broker password in a plaintext file are not acceptable in a distributed package.
- **Done.** 1. Secret fields are excluded from repr; a test asserts that no secret value appears in repr(settings), in any log line of a full simulated brain cycle, or in any DB row. 2. Each service receives only the variables it needs. 3. A 'support bundle' command collects logs, status and versions with secrets and, optionally, amounts redacted; a test seeds fake secrets and asserts the bundle contains none. 4. CI runs a secret scanner and a check that no tracked file contains a real user path. 5. The docs use a placeholder for the user folder. 6. A privacy note lists exactly what leaves the PC (to the AI provider and to the tunnel provider) and when. 7. The broker-password path is removed from the product or clearly excluded. 8. A key rotation procedure exists in the owner manual.
- **Risk to live.** Low. Narrowing env_file per service is the one change that can break the live brain if a needed variable (MT5_COMMON_FILES_HOST, FXSIM_MAX_LEVERAGE, the model override) is dropped; diff the effective environment with 'docker compose config' before and after.

#### security-compliance-6 [P1·M] Supply chain: floating images and actions, no hashes, no vulnerability scan, no component inventory

- **Evidence.** Dockerfile:3 is FROM python:3.12-slim with no digest (requirements.txt itself notes the base image patch level still floats). docker-compose.yml:75 and docs/REMOTE.md:43 use cloudflare/cloudflared:latest for the container that holds the public tunnel. Workflows pin actions by tag, not commit (fxsim-tests.yml:34-35 checkout@v4, setup-python@v5; claude.yml:35 claude-code-action@v1, with id-token: write). pip installs by version without --require-hashes. There is no pip-audit, Dependabot or equivalent (.github holds only workflows). The developer environment is not the pinned one: scripts/setup.sh:17 installs without constraints, and the local venv is Python 3.11.18 with annotated-doc 0.0.7, httpcore2 2.16.2, pydantic 2.14.4 and pydantic_core 2.50.5 against pins 0.0.6, 2.16.0, 2.14.3 and 2.50.4. chart.umd.js (v4.5.1, sha256 ecc3cd1e...7652a) has no recorded checksum or source. There is no SBOM or third-party notices file.
- **Why it blocks product grade.** The stated goal of Round-10 was that the live container cannot change without a line of the repository changing. That is still untrue for the OS layer, the tunnel binary and the CI actions. A stranger's install six months from now would be a combination nobody tested, and nobody would know when a pinned package gets a published vulnerability.
- **Done.** 1. Base image and cloudflared are pinned by digest, with a documented, tested bump procedure. 2. Actions are pinned by commit SHA. 3. Constraints carry hashes and both the Dockerfile and CI install with --require-hashes. 4. CI runs a vulnerability audit on the pinned set and fails on a known high-severity issue. 5. setup.sh installs with constraints on the image's Python version. 6. An SBOM and a THIRD_PARTY_NOTICES file are generated in CI and shipped; the vendored chart.js checksum is asserted by a test.
- **Risk to live.** Low to medium. Hash-pinned installs fail closed: a rebuild during a registry problem, or a wrong hash, leaves the old container running or none at all (docs/DOCKER.md:80-87 already describes that failure). Change it on a release boundary and prove one clean rebuild before the owner's.

#### security-compliance-7 [P1·M] Change management and release identity: live runs whatever the head of a working branch is

- **Evidence.** 'git tag' prints nothing. The documented update is 'git pull' then 'docker compose restart fx' (docs/OVERVIEW.md:130-131, 229), and the code is bind-mounted over the image (docker-compose.yml:26, Dockerfile:12 comment), so a pull changes the live money path on the next restart. The branch in use is a claude/** work branch (git branch -a). Version identity is two hand-edited strings (BRAIN_BUILD scripts/run_ai_bridge.py:172, EA_BUILD mq5:33). The EA ships as source that the user compiles in MetaEditor. There is no changelog, no rollback instruction and no signature or checksum on anything the user installs.
- **Why it blocks product grade.** RTS 6 change management asks that what runs in production is an identified, tested, approved version that can be rolled back. For a stranger there is no developer to say 'this update needs a rebuild' or 'this EA is stale'; they need a version number, a checksum and a way back.
- **Done.** 1. Releases are tagged and immutable, and CI must be green on the tagged commit. 2. One version string is reported by the brain log, the status file, the dashboard and the health check, and the health check goes red when brain, EA and docs versions are not a tested combination. 3. Each release ships a checksum list covering the compiled EA and its source; the health check verifies the code tree against it. 4. A CHANGELOG entry per release states whether orders, sizing or stops change. 5. A rollback procedure is written and rehearsed once on a demo account. 6. The live install tracks tags, not a branch head.
- **Risk to live.** Medium. Moving the owner's checkout from a branch head to a tag, or turning on an integrity check that goes red because of a local edit (for example the 8000-to-8001 port edit the docs suggest at OVERVIEW.md:238), can produce a false alarm or a confusing first update. No effect on order logic.

#### security-compliance-8 [P1·M] Record keeping: no order or fill journal, and operational logs die with the container

- **Evidence.** The signal file is overwritten on every heartbeat (app/bridge.py:171-173) and only decisions, not heartbeats or the lines actually published, are stored. Fills live only in MT5 ('the bridge persists trades in MT5, not our DB', app/server.py:254-255). Brain output goes to Docker's json-file driver capped at 3 x 10 MB (docker-compose.yml:30-34, 53-57), and those files belong to the container, so 'docker compose down' or 'up -d --build' (both in the owner's command table, docs/OVERVIEW.md:132-133) discards them. A grep of the docs for backup or retention finds nothing. The dashboard process can write to the same database (see the dashboard input gap). The 2026-11-16 'BLIND' lines exist only in such a log.
- **Why it blocks product grade.** 'Every claim is backed by evidence' and 'recover from trouble without the developer' both need a durable, complete record: what order line was standing when, what the EA did with it, and what the broker filled. After the next rebuild the primary evidence of the latest incident is gone, and a dispute with a broker or a tax question cannot be answered from the product's own records.
- **Done.** 1. An append-only journal on the host records every published signal line (including heartbeats), every EA action and broker return code, and every status transition, with timestamps from both clocks. 2. It survives 'docker compose down' and a rebuild, proven by a test or scripted drill. 3. Retention length and size are documented and enforced. 4. A daily local backup of the database and journal exists, with a restore drill. 5. A reconciliation command compares the journal with the MT5 account history export and reports differences. 6. An export command produces the records as CSV for the user.
- **Risk to live.** Low to medium. Extra writes inside the brain loop and the EA timer add I/O on the shared folder, which has a history of torn reads and lock trouble (docs/RESEARCH.md Round-6e and Round-7). Journal writes must never block or fail the heartbeat; make them best-effort and test that a full disk does not stop trading.

#### security-compliance-9 [P1·M] Licence and intellectual-property position is undefined, and bundled market data has no provenance

- **Evidence.** The only licence is the repository-root LICENSE: MIT, 'Copyright (c) 2025 Generative Agents' (LICENSE:3), inherited from the book template this repo was created from; fxsim/ has none. fxsim/package.json says 'license': 'ISC'. fxsim/data holds about 24 MB of price history: five H1 files and one H4 in MetaTrader export format (header '<DATE> <TIME> ... <TICKVOL> <VOL> <SPREAD>', about 71,000 rows each; commit 82e328c calls it 'real MT5 history'), a daily file 'exported from Central Tanshi FX historical data' (commit 09122b6), and a 1971-onward daily file (USD_JPY_D.csv) whose source is not stated in the data folder. - **Risk to live.** None to the trading path if the files stay in the owner's checkout. Moving or removing data/USD_JPY_H1.csv would break the brain's history fallback (scripts/run_ai_bridge.py:948 --history default) and the CI harness; change the distribution package, not the live tree, until a verified fetch path exists.
