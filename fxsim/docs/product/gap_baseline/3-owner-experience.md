# 3. Owner experience — the non-programmer's whole journey

（[一覧に戻る](README.md)。測定日 2026-11-22、対象コミット `40771f9`。）

## Summary

Lens: the non-programmer owner's whole journey. Method: read every owner-facing document and instrument, then reproduced the owner's view in scratch (fake MT5 Common\Files feed + scratch DB, no API, no repo writes; 274 tests pass). Scratch evidence incl. phone-width screenshots: docs/product/baseline/owner-journey/live_phone_healthy.png, docs/product/baseline/owner-journey/live_phone_incident.png, docs/product/baseline/owner-journey/root_phone.png.

Headline: the trading core and its honesty are far ahead of the owner experience. The system is operated through about 25 distinct PowerShell commands spread over five "current" documents, and every question the owner recently had to ask the developer is one the product cannot answer by itself today.

Journey findings:
(1) First install: about 30 documented manual steps across OVERVIEW/DOCKER/AI_TRADER/REMOTE plus 8 prerequisites no current document covers (OANDA MT5 account, MT5 install and saved login, Git install, clone URL, finding one's own Common\Files path, sleep settings, MT5 autostart, Windows sign-in after an update reboot). No installer, no .ps1/.bat, no preflight. A wrong MT5 path silently mounts an empty folder: fx shows "Up", the brain prints one English line, the health check prints "ライブrunがまだありません" and exits 0.
(2) Reading status: I reproduced the 2026-11-16 state. The health check names the wrong cause and remedy in both phases ("執行ズレ→アルゴ取引ON" in the first 30 min; then "脳の心拍が止まっています → docker compose restart fx"), the phone dashboard shows a 10px grey dot, 12px text "stalled", and "ポジション なし（待機）" while the broker holds the long; after recovery nothing anywhere records that it happened. On a perfectly healthy system the overall verdict is 🟡 for the first 60 days, because operational health and statistical sufficiency share one verdict - so "is it working normally?" has no answer.
(3) Nothing is pushed to the owner: no notification code exists, run_monitor exits 0 on RED, the documented cadence is weekly.
(4) Dashboard: 3 of 6 cards and one panel are dead or false for the live system, reasons are English, drawdown turns red at 10% although 30% is the stated norm, a failed fetch leaves the dot green, and "/" still says "FX Paper-Trading Simulator ... 約定はシミュレーション".
(5) Updating depends on the developer's notice (restart vs rebuild, which brain-build string to look for in the log); the running build is shown nowhere.
(6) Deposits/withdrawals are unmodelled: a 100,000 JPY withdrawal reads as a permanent 🔴 36.8% drawdown, a 300,000 JPY deposit as +110% 🟢. No tax, backup or generic year-end flow.
(7) Documents: three generations coexist; the "current" AI_TRADER.md still tells the reader to run the brain with Windows Python; the EA attach steps exist only in a file marked "do not read"; REMOTE.md (the password answer) is not in the index; diagnose_live still prints the retired 15.5%/24.6% reference.

None of the gaps touches the strategy. Most can be closed with read-only observers beside the live path; the only high-risk items are those that require an EA recompile, which should be batched into one planned recompile.

- Honest expectation text in docs/OVERVIEW.md sections 1 and 8 and the run_monitor 基準 lines (scripts/run_monitor.py:394-403; app/monitor.py:41-51): 9%/yr (2-15%), ~4% without 2021-22, DD 30% typical/35% worst/52% proxy, 'SMA2400's 15% is the top draw'. Do not rewrite the numbers; reuse them from this single source.
- Span-aware performance envelopes in app/monitor.py (ENVELOPE_CHANGES/ENVELOPE_RETURN, same-length windows, closed-bar segment only) and RED messages that already say 'not necessarily broken' and 'do not close the position by hand' (monitor.py:213-220, 278-284). Keep the statistics; only the presentation layer and the operational verdict need work.
- EA build handshake: the EA reports its build in steady_status.csv, the brain warns every poll and run_monitor goes RED on a mismatch (app/bridge.py:31, run_ai_bridge.py:1187-1193, monitor.py:384-387). This is the model for how every version check should work.
- Liveness rules already distinguish a dead brain, a frozen EA, stale/short bars, clock skew and lock waits, with thresholds shared between brain and instruments (bridge.py:34-91; monitor.py:320-380; server.py:291-317). The inputs for a correct status page mostly exist.
- Dashboard is read-only and fail-closed: with a tunnel token and no password every request is refused with a Japanese explanation (app/server.py:41-60; tests/test_dashboard_auth.py). Backtest endpoint cannot reach the live broker or mutate settings.
- Reproducible, isolated runtime: Docker removes Windows Python entirely, all 44 packages pinned (constraints.txt), CI installs exactly the pinned set and fails on any drift (.github/workflows/fxsim-tests.yml), .env never enters an image (.dockerignore), container logs capped at 30 MB, restart: unless-stopped, state restored from DB on restart.
- docs/DOCKER.md section 6 rebuild-failure guidance is accurate and specific (before/after 'Recreate'), and the disk-usage section is correct and careful. The content should be preserved - as automation rather than prose.
- docs/README.md openly labels which documents are current and which are historical, and legacy writers refuse to start beside the live brain (tests/test_legacy_bridge_refuses.py). The honesty is right; the fix is consolidation, not more labels.
- Automatic holiday handling (bridge.holiday_extra_h, 99 h over 25 Dec / 1 Jan) - the owner does not have to do anything for the closure itself.
- scripts/diagnose_live.py opens the DB read-only (mode=ro) and never creates files - the right pattern for any diagnosis bundle.
- The always-visible on-chart EA line (build tag + heartbeat countdown) is the right idea and the only instrument that survives a Docker death; only its wording and missing fields are gaps.
- docs/RESEARCH.md, docs/COVERAGE.md, docs/AUDIT_PROMPT.md as developer/auditor evidence. They are not owner documents and should not be rewritten for the owner - only linked from one manual.

- **Done.** One pure function status_model(inputs) -> {operation: 正常|要確認|要対応, performance: 範囲内|判定には早い|範囲外, cause_ja, next_step_ja, since} used by CLI, dashboard, digest and notifier.
