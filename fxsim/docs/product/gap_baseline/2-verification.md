## Summary

LENS: how do we know it is correct, and how fast would we know if it were not. Verdict: the assurance that exists is real but is almost entirely (a) human adversarial audit rounds and (b) unit tests of helper functions. What a product needs and this repo lacks is machine-checked evidence about the closed loop (real brain + EA + broker + clock) and about the live account itself. Measured, not estimated:

1) Suite: 274 passed in 74 s (local venv is Python 3.11.18; CI and Docker use 3.12). Harness validations re-run: 14 OK + 4 OK, 0 MISMATCH.

2) Branch coverage (coverage 7.17.4 installed into scratch, `coverage run --branch --source=app,scripts -m pytest tests`): scripts/run_ai_bridge.py 80% overall, but main() 70% and the resident loop body (lines 1104-1459) only 63% of statements / 66% of branches. decide_once 92%, app/bridge.py 86%, app/sizing.py 100%, app/indicators.py 100%, app/monitor.py 97%, scripts/run_monitor.py 53%, app/server.py 58%, app/db.py 67%. mt5_ea/SteadyBridge.mq5 (449 lines, the only code that touches money): 0% executed by anything.
   Loop branches NO test ever executes: external-close reconciliation, i.e. every broker-SL exit (1278-1299); the trend gate-exit trigger, i.e. the normal exit (1349); external shrink (1265-1268); cancel-unfilled (1240-1257); untrusted/frozen/torn status handling (1153-1165); implausible restored stop (1306-1308); gate-rearm (1338); event trigger (1364-1369); entry back-off (1401-1407); lock-lost heartbeat withholding (1431, 1450-1456); the whole --once path (976-990). Both normal ways a trade ends are untested at loop level.

3) Sampled mutation run on a scratch copy (36 hand-written order-path mutants, whole suite per mutant; targeted, not random): 20 killed, 16 SURVIVED. 14 of the 16 are genuine behaviour changes, 9 of them on lines that ARE covered (so coverage alone would not find them). Survivors include re-introductions of defects recorded as fixed in Rounds 4-7: heartbeat EXP in the container clock (r6c), 'LONG 0.00' heartbeat (r4), heartbeat without the broker stop (I3), id not stepped over the EA's executed id (r6b), frozen/torn status trusted (r6c/e), heartbeating after losing the lock (r7), external close never reconciled, gate exit disabled, stop distance 1.5 -> 2.5 ATR, and the guard that makes a logged-out EA's 'balance 0, book empty' row untrusted (the 2026-11-16 guard). The forming-bar defect itself (M01/M30) IS killed in 3 s.

4) The 2026-11-16 incident reproduces on the first run of a 150-line closed-loop script (real scripts.run_ai_bridge.main + the repo's own FakeEA + real bridge files): on a weekday the EA closes the healthy long on its first tick after the terminal logs in ('expire-closeall -> book 0.00'), the brain notices 10 minutes later as an 'external close'; 28 BLIND lines carry no cause (the probe returns None silently at run_ai_bridge.py:529-530). No kept test covers it.

5) Time to detect: the repo's own numbers say the statistical health check flags the forming-bar defect within 730 days for only 56.6% of start dates, and a steady doubled trade rate first reads RED on day 897 (docs/RESEARCH.md:1359-1361). There is no decision-by-decision parity check, no broker reconciliation, no staging, and decision rows do not carry their inputs or their order id.

Scratch artefacts (nothing in the repo was edited): docs/product/baseline/assurance/mutate.py, docs/product/baseline/assurance/mutation_results.txt, docs/product/baseline/assurance/incident_sim.py, cov.json (not kept; regenerate as described in docs/product/baseline/README.md). Limits of this report: the mutation sample is 36 hand-picked mutants, not a systematic run; I could not execute MQL5 or anything on Windows; the incident replay uses the repo's Python EA transcription extended by me with a 'not logged in' and a 'market closed' state, so it shows the brain-side mechanism, not the compiled EA's behaviour.

The behaviour fix itself changes fail-safe semantics on both sides (EA and brain) and is high risk: it must go through the simulator and the demo twin, and must not weaken I3 (an unsupervised position still fails safe in finite time).

### verification-5 [P0·M] No daily decision-parity check between the live account and the validated engine on the live tape; time-to-detect for a timing defect is months to years

- **Evidence.** The forming-bar defect ran from Round-2 to Round-9 on real money and was found by a human review of a monitor false alarm (docs/RESEARCH.md:1020-1028). The repo's own measurement of the statistical monitor: 'forming-bar defect: RED within 730 days = 56.6%' and 'steady doubled trade rate: first RED on day 897' (docs/RESEARCH.md:1359-1361, pinned in tests/test_monitor.py:462); a steady 3%/month bleed reads RED on day ~440 (app/monitor.py:73-74). The only live-vs-rule check is point-in-time: current trend basis vs current book (scripts/run_monitor.py:130-154). scripts/diagnose_live.py:363-398 compares aggregates only. Inputs needed for parity are not stored: the decision row (scripts/run_ai_bridge.py:886-897) has no signal-bar time, close, SMA, ATR, live price, balance or build; the live path never writes the candles table (db.upsert_candles is called only from non-live modules) and the EA file is a rolling 2,500 bars (mq5:22) while data/USD_JPY_H1.csv ends 2026-06-05, so the bars the first live months were decided on are no longer on disk in the project. Equity is sampled only at decisions (single call at run_ai_bridge.py:830).
- **Why it blocks product grade.** The product's central claim is 'the live system trades the validated rule'. For five months that claim was false and no instrument could say so. A parity check turns detection from 'statistically, in a year or two, maybe' into 'the first bar on which live and engine disagree'.
- **Done.** (1) Every decision row additionally records bar_t, sig_close, sma, atr, live price, balance, eff_leverage, order seq, brain build, EA build (additive JSON keys). (2) A daily job appends the EA's closed H1 bars to an append-only store and fails on a gap, an overlap that changes a closed bar, or a timestamp-offset change. (3) `python -m scripts.parity` replays app/engine (or the CI-validated harness) over the archived live tape from the first closed-bar decision and exits non-zero unless, for every closed bar, engine position state == broker book state within (1 poll + 1 EA tick), each live entry is on the engine's entry bar, entry leverage matches within one lot step, and each stop matches within a stated tolerance; documented, enumerated exceptions only (outage windows taken from the flight log). (4) run_monitor prints it as a check line with the first divergent bar. (5) Sensitivity is pre-registered and proven in the simulator: with mutant M01 (forming bar) and M03 (2.5-ATR stop) injected, parity goes RED within one trading day of the first divergent decision in 100% of seeded runs (today: 56.6% within 730 days). (6) MT5 history for June-November 2026 is back-filled once so the existing run is checked from its first closed-bar decision.
- **Risk to live.** Low. Read-only analysis plus additive fields in a JSON column that readers access with .get(); verify _restore_state/_restore_reentry and run_monitor ignore unknown keys (they do by construction, but pin it with a test). A second reader of steady_bars.csv can make the EA skip one 30 s export (exclusive FileOpen), which the monitor already does today.

### verification-6 [P1·L] The brain's records are never reconciled with the broker's deal history; fills, slippage, swap and commission are unknown to the system

- **Evidence.** grep HistorySelect|HistoryDeal|deal|ticket over mt5_ea/, app/ (live modules), scripts/run_ai_bridge.py, scripts/run_monitor.py: no hits except a comment at mq5:230. The live path writes only `signals` and `equity` rows; the `trades` table (app/db.py:44-57) is written only by the backtest engine (app/engine.py:127, 158). scripts/diagnose_live.py:240-287 (attach_pnl) infers trade P&L from equity rows before and after a cycle. Orders carry no brain id at the broker: trade.Buy at mq5:393 passes no comment, so a deal cannot be tied to a SEQ. The backtest's cost model (spread 0.8 pip, commission, no swap: scripts/research_harness.py:89) has never been compared with a measured fill. docs/RESEARCH.md:739-742 lists OANDA margin stop-out, swap timing and weekend-gap fills as unprovable.
- **Why it blocks product grade.** 'Every claim backed by evidence' fails at the most basic one: what did the account actually do. An exit is classified by inference (the book went to zero, so it was 'broker SL / fail-safe / manual'), a manual trade under the same magic is invisible, and the 9%/yr expectation rests on cost assumptions nobody has checked against the broker.
- **Done.** (1) An append-only export of the account's deals (ticket, time, type, volume, price, commission, swap, profit, magic, reason SL/expert/client, comment) and balance operations, produced by a read-only exporter that is NOT the trading EA. (2) Orders opened by the trading EA carry the brain's SEQ in the order comment (bundled with the next EA release). (3) `python -m scripts.reconcile` exits 0 iff: every deal with our magic maps to exactly one decision id or to a classified external cause; every LONG decision id maps to deals or to a recorded cancel/unfilled; and initial balance + sum(profit+swap+commission) + balance operations == current balance within 1 JPY. Unknown deal -> RED in the health check with the ticket number. (4) A generated table publishes measured spread/slippage/swap per trade next to the backtest assumptions, and the owner-facing expectation cites it. (5) Simulator test: an injected manual trade, a partial close and a deposit are each classified, never silently absorbed.
- **Risk to live.** Low for the exporter (separate read-only program on its own chart or as a script; the trading EA is untouched). Adding the SEQ comment is a one-line change to the EA's Buy call: batch it with the EA release in the EA-conformance gap, never as its own re-attach.

### verification-7 [P1·M] Decision rows carry no order id and are written before the bridge write; there is no write-ahead intent journal and no crash-point testing

- **Evidence.** docs/COVERAGE.md:59 (item 0b) and docs/RESEARCH.md:1128-1131 record it as accepted. In code: db.record_signal at scripts/run_ai_bridge.py:886-897 has no seq key; the id is minted afterwards at 920 and published at 927. The brain's state after a restart is rebuilt from three places that can disagree (newest DB row via _restore_state 646-688, signal file via read_signal 1058-1060, EA status exec_seq), with ~25 in-memory variables (1000-1102) that are not persisted (e.g. entry_backoff, veto_until, seen_long). Restore code is among the least covered: _restore_state 73%, _restore_reentry 64%, _record_blocked 55%. Existing crash tests restart at two chosen polls (tests/test_ai_bridge.py:903-910), not at every boundary between side effects.
- **Why it blocks product grade.** Without an id on the row, 'ordered and filled', 'ordered and never filled' and 'never ordered' cannot be told apart after a crash, which blocks exact reconciliation (previous gap) and forces heuristics (an unfilled entry is read as an external close). A product recovers from a kill at any instant by construction and can show it.
- **Done.** (1) The order id is minted before the decision row is written and stored in it; the row records the publish state (intended -> published). (2) The simulator kills the brain at every boundary between two side effects (DB write, signal write, lock touch, status read) in decide_once and in the loop, for each scenario in the corpus, restarts it, and the invariant checker passes (no entry or exit without a decision, no misclassified external close, re-entry rule kept). (3) The count of boundaries x scenarios exercised is printed in CI. (4) COVERAGE.md item 0b and the two residuals of Round-9e are closed with a test id.
- **Risk to live.** Medium: it reorders statements on the order path. Do it only after the simulator and golden-trace check exist; the reordering must leave the bytes written to steady_signal.txt identical on the whole scenario corpus.
