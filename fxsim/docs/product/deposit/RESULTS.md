## 1. 入れる条件（日付ではなく、条件で決める）

**この§1は、入金・出金の判断について、`docs/OVERVIEW.md` §6の5項目と `docs/GOLIVE.md` の「増やし方」に優先する。** あちらの5項目がそろっていても、ここの条件がそろうまでは入れない。

### 所有者に「入金していい？」と聞かれたセッションへ

- 下の条件を1つずつ確かめ、条件ごとに「いつ・何で確かめたか」を書く。**確かめる材料が無いことを、合格に数えない。** 確かめられない条件は「未判定」で、「未判定」は「まだ」である。
- 答えは、必ず次の形で終える（所有者は、この形の返事だけを合図にする）：
  「結論　まず半分：入れてよい／まだ　　残り：入れてよい／まだ」
  「まず半分」はア〜エだけで判定する。「残り」はア〜エに加えて、カ・キ・クで判定する。所有者がすでに半分を入れたかどうかは、リポジトリからは分からない。推測せず、2つとも書く。
  「入れてよい」と書くときは、結論の行の直前に、次の2つを書く（結論の行は、返事のいちばん最後のまま）：
  「下の結論が有効なのは、今日から3日間です。過ぎたら、入れる前に、もう一度同じ文を送ってください」
  「入金したら、その日のうちに、日付と金額を手元に控えてください（ここには書かないでください）」
- この問いの中で所有者に頼んでよいのは、**見るだけのもの**に限る：健康診断（`docker compose run --rm app python -m scripts.run_monitor`）、`docker compose logs -t --tail <数> fx`、`docker compose ps`、MT5の画面を見ること。
  それ以外の表示（`diagnose_live` など）は、読み取りだけであることを、頼む前にコードで確かめる。
  `git pull`・再起動・設定の変更・MT5のログインし直しは、この問いの中では頼まない（「fxsimを更新してください」と書かない。アがPCに入っていなければ、答えは「まだ」で止める）。
  何かを頼む前に、`docs/product/FOR_OWNER.md`、`docs/product/guide/OWNER.md` の§1・§2、`docs/product/guide/RELEASE.md` の§5・§6を読む。
- 確かめた結果は、下の各条件の「いまの状態」の行に書く：日付、確かめた版（脳の `brain build` の印と、EAの build）、何で確かめたか、合否。**金額と、取引の中身は書かない**（`OWNER.md` §2）。
  行が無い、または版が違うときは「未判定」。
- **聞かれたその日に、毎回確かめるもの**（記録があっても）：ア、エ、ウの後半（フェイルセーフの決済も `BLIND` も起きていないこと）、動いている版。
  その日に、健康診断と `docker compose logs -t --tail <数> fx` を貼ってもらい、次を見る。(1) 貼られた行が、前にウを確かめた日より前の日付から始まっている。
  (2) そこから今日までを、ウの「見るもの」と同じ見方で読む（`BLIND`、`book closed EXTERNALLY`。あわせて `torn read`）。(3) いちばん新しい `brain build` の印が、記録の版と同じである（健康診断は、脳の版を表示しない）。
  (1)が満たせなければ、ウは「未判定」。ウの「いまの状態」には、合否と一緒に「○月○日までのログを読んだ」と書く。

**イ いま動いている版が、規則どおりの決済を1回、そのあとの新しい建てを1回行い、どちらも規則と合っていた。**

- 数えるもの：規則どおりの決済（ストップに届いた／確定足が平均線を下回った）と、そのあとの新しい建てだけ。所有者が止めたことによる決済、フェイルセーフの決済、手での決済は、この1回に数えない。
- 照らし合わせるもの：確定足の終値と平均線の向き。建てた大きさ（残高・倍率・ATRから計算した値と同じか）。ストップの位置。決済の理由。ストップの後、次の確定足まで建て直していないこと。EAが、脳の指示と同じロット数を執行したこと。

  ロット数・ストップ・決済の理由は、MT5の側の記録と比べる。出どころと手順は、作業を始めるときに決め、独立の目で確かめてから、所有者に渡す。

- 見込み（§4の最後の表）：いまと同じ状況（建ててから10〜14日の建玉がある）から、次の新しい建てまでは、真ん中で44日。53日以内に来ないことが47%、3か月以内に来ないことが32%、半年以内に来ないことが13%ある。
- **イを早くそろえるために、手で決済したり、止めたりしない**（数えないうえに、検証したやり方から外れる）。
- いまの状態：未判定（2026-11-23、版 r10c-2026-11。所有者の承認あり）。所有者が貼った健康診断と脳のログ（11/13〜11/23）を読んだ。上の「なぜ要るか」の前提（いまの版はまだ建てていない）は、もう成り立たない：11/17以降、この版で、外部の決済（ストップと見られる）・トレンドの終わりによる決済・新しい建てが、どれも複数回あった。脳のログの中では、どの建ても「確定足の終値＞平均線」、どの決済も「確定足の終値＜平均線」か外部の決済で、ストップの後の建ては次の確定足からだった。**ただし、これは脳のログどうしの比較なので、合格には数えない**（上の「何と比べるか」）。次は、MT5の側の記録（口座履歴）と比べる。
  2026-11-24：所有者が送ったMT5の口座履歴（11/11〜11/24の建て・決済）と、脳のログを1件ずつ突き合わせた。ロット数・損切りの値段・時刻・決済の種類（証券会社の損切り／トレンドの終わり）が一致し、フェイルセーフの決済は無かった。最後の1件の決済（11/24）も、同じ日に届いた脳のログで、確定足が平均線を下回ったことによる決済と確かめた（MT5の決済時刻・値段と一致）。そのあとの新しい建ては、倍率の計算（ランプ）・大きさ・損切りの位置が、ログの数字どうしでは辻褄が合う。**残り**：確定足の終値と平均線を、脳以外の出どころで確かめること。それが済むまで、イは「未判定」のまま。

- 残りを入れる前にも、同じ文を送る。「入れてよい」の返事から3日を過ぎたら、入れる前に、もう一度同じ文を送る（返事の中に、そう書いてある）。
- 入金・出金をしたら、その日のうちに、日付と金額を手元に控える（リポジトリには書かない）。健康診断を正しく直すのに要る（§5）。
- 入金のあと、建玉が大きくならなくても正常である（§5）。早く効かせようとして、手で決済したり、再起動したりしない。
- 健康診断が🔴を出して「レバを下げて再起動」と言ってきても、入金・出金のあとや、返事を待っている間は、設定を変えない・何も再起動しない。出ている言葉を、そのまま会話に貼る。

### 出金を聞かれたとき

出金は、所有者が決めてよい。入金の条件（ア〜エ）で止めない。所有者は、上の文の最初を「出金していい？」に替えて送る。返事がない間は、出金しない。
返事は、最初の行に「この返事の最後に『結論　出金』の行が出るまで、出金しないでください」と書き、最後を「結論　出金：建玉がある間は○円まで（建玉が無ければ、上限なし）」で終える。途中で切れた返事は、返事がないのと同じである
（上限の計算には、健康診断の表示が要る。最初の返事は、たいてい「健康診断を貼ってください」になる）。セッションが答えるのは、次の4つである。

1. 建玉がある時は、出金のあとの実効の倍率（建玉のロット数×10万×値段÷出金後の純資産）が5倍を超えない額まで。上限を計算して伝える（健康診断の「今の建玉」の行と、純資産から）。建玉が無い時のほうがよい（§5：保有中に出金しても、ロット数は変わらない）。
2. アが入るまでは、出金のあとに、健康診断が出金を損として数え、🔴と「レバを下げて再起動」を出すことがある（§5）。従わない。
3. 日付と金額を、手元に控える（リポジトリには書かない）。
4. `FXSIM_DD_BRAKE=1` にしている場合だけ、出金のあとの新しい建玉が小さくなる（§5）。

### 金額の目安と、足すのをやめる合図

- これまでの方針は「コア＝インデックス9割／FX＝サテライト1割」である（`docs/GOLIVE.md`。`docs/OVERVIEW.md` §6にも「コア＝インデックスは崩さない」とある）。足したあとの口座が、所有者の金融資産の1割を超えるなら、多すぎる。
  投資信託との成績の比較は、していない（`docs/RESEARCH.md` Round-8）。
- 足すのをやめる合図は、エの🔴である。入金を数え間違えると、この合図が狂う（入金で下落が小さく見える。§5）。だから、アが入金より先である。
- 早い目安：ドル円が6か月で5%以上上がったのに、口座が（入金・出金を除いて）増えていなければ、足さずに見直す（`docs/RESEARCH.md` Round-8）。

### なぜ、こう決めたか

**「執行一致」が基準にならない理由。** `app/monitor.py` の執行一致は、最後の判断の向き（LONG／FLAT）と、点検した瞬間のEAの建玉の向きを比べるだけである（`scripts/run_monitor.py` の `_live_position`）。
ロット数・ストップ・判断のタイミングは見ない。履歴も残さない。だから、EAが脳に従ってさえいれば、脳の判断が規則から外れていても🟢のままである。直す前の不具合が、まさにこの形だった。
11/16のような出来事のあとも🟢に戻り、跡は残らない（`docs/product/gap_baseline/3-owner-experience.md`）。

**待つだけでは足りない理由。** 建玉の変化は年に約41回で、ならせば11/4から1/4までに約7回の見込みだが、これは平均である。いまのように建玉が続いている間は、1回も起きない。
健康診断は、61日の時点で「変化23回まで・リターン−5.8%以上」を範囲内とする。不具合と不運を見分けるには粗い（直す前の不具合が730日以内に🔴になる開始日は56.6%。`docs/RESEARCH.md` Round-10C）。
確定足方式の区間が60日になる1月の初めごろ、健康診断の「リターン」が、いまの🟡（判定は60日以降）から、初めて判定に変わる。入金の合図ではない。
本番の記録を規則と照らし合わせる仕組みは、製品化の基準測定で最上位の欠落とされている（`docs/product/gap_baseline/README.md` の research-integrity-1）。

**待つ代償は小さい。** 建玉がある間に入れても、そのお金は建玉が終わるまで使われない。だから、その間は待っても損にならない。
そのあとの代償は、過去のテープのならしで、足したお金の年1〜5%ほど（§4）。誤差も同じくらいある。

**この§1は、同じ日に3回、独立の点検を受けて書き直した。** 3回とも、「確かめていないのに合格になる道」が見つかった（日付だけ／照らし合わせる売買が無い／建玉が無いまま越えた、など）。
4回目の点検（3回目の指摘がふさがったかの確認）では、7点のうち6点がふさがっており、新しく5点が見つかった（記録済みのウを、聞かれた日に読み直していなかった、など）。その5点も直したが、**この最後の直しは、点検を受けていない。**
まだ残っていると考えて、迷ったら「まだ」と答える。

## 5. 入金・出金のとき、コードは何をするか

読んで確かめ、1回目の点検役が本物の常駐ループ（`main()`）を模擬の世界で走らせ、2回目の点検役が本物の `decide_once` を作業用のブリッジの上で走らせて確かめた。
EAは、リポジトリのPython転写（`tests/test_ea_protocol.py` の `FakeEA`）で走らせた。コンパイル済みのMQL5は、ここでは実行できない。
**この節の「模擬では」の数字は、リポジトリからは再現できない**（点検役の模擬の世界のスクリプトは、作業用フォルダにあり、ここには入れていない）。コードから直接言えること（保有中はロット数と注文IDを保つ、破れた行で0.03 → 0.08／0.30ロット、8.2倍の計算）は、2回目の点検役が別に確かめた。

**売買の側**

- **入れた時に建玉があれば、その建玉は変わらない。** 保有中は、建てた時のロット数をそのまま出し続ける（`scripts/run_ai_bridge.py` の `decide_once`：`lots = pos_lots`。注文IDも同じものを使う）。EAは差が0なので何もしない。
  模擬では、入金の前後で同じ行（`LONG 0.03 SEQ … SL …`）を128回書き、EAの動作は無かった。ストップも動かない。
- **入れたお金は、次に新しく建てる時まで使われない。** 大きさは、新しく建てる時にだけ `status["balance"]`（EAが書く口座残高）から計算する。
  入れた時に建玉が無ければ、次に建てる時から新しい大きさになる。早ければ、その日のうちである（模擬では、建玉なしで入金すると、次の建てが0.07ロットになった）。
- **次の建玉は、一段で大きくなる。** 模擬では、入金のあと最初のストップ決済の55分後に、0.03ロットから0.30ロットになった。
  1円の値動きで動く金額は、0.03ロットで3,000円、0.19ロットで19,000円、0.31ロットで31,000円。
  ストップでの損（1.5×ATR）は、0.03ロットで約900〜1,350円、0.30ロットで約9,000〜13,500円（ATR 0.20〜0.30円）。上限は残高の2.4%（100万円で24,000円）。
- **損切りが決めた値段で約定する前提である。** 再生は、足の途中のストップを、ストップの値段で約定させる（休場明けの窓は、始値で約定させる）。値段が飛んだときの滑りは、どの数字にも入っていない。
  テープには、1時間で始値から4円以上下がった足が6本ある（最大5.771円、2016-06-24。ほかは2022-09-22、2024-05-01、2024-04-29、2019-01-03、2022-12-20）。休場明けの下への窓は、最大1.478円（2025-04-07）。
  割合で言えば今と同じだが、金額は建玉に比例する（0.31ロットなら、1円の滑りが31,000円）。証券会社のストップがこういう時にどう約定するかは、未確認。
- 脳に「残高が急に変わったら疑う」検査は無い。入金で盲目になったり止まったりはしない。実行の同定（`_find_run`）も残高を使わない。
  下落ブレーキは既定で切ってある（模擬の起動行は `dd_brake=False`）。`FXSIM_DD_BRAKE=1` にしている場合だけ、出金が下落と数えられて、新しい建玉のリスクが×0.70／×0.40／×0.20（5%／10%／20%の出金）になり、入金は効いているブレーキを外す。
  所有者の `.env` は見られないので、どちらかは未確認（起動時の `[ai] dials in force: … dd_brake=` の行で分かる）。
- EAは残高を見ない（残高と純資産を読むのは、状態ファイルに書く2行だけ）。0.10ロットという境目はEAのリサイズ不感帯の話で、脳が保有中に出すロット数は建玉と同じなので、この経路は通常は通らない。
- どちらの制約が大きさを決めるかは、残高ではなくATRで決まる（§2、`docs/COVERAGE.md` の「運用点の注意」）。
- **保有中に出金しても、ロット数は変わらない。** 5倍の上限は、新しく建てる時にだけ効く。だから、出金のあとは実効の倍率が5倍を超えうる。
  模擬では、100万円で0.31ロットを保有中に40万円を出金すると、8.2倍になった。警告は出ない（健康診断の「実効」の数字に出るだけである）。

**観測の側（直す必要がある。売買には触れない）**

- `app/monitor.py` の `equity_stats` は、資産の列の最初と最後を比べるだけである。
  - 見出しの「初期 → 現在（+○%）」に、入金がそのまま利益として出る。
  - 「リターン」は、確定足方式の区間が60日になるまでは🟡（水増しされた%つき）、60日からは🟢になる。本当の成績が悪くても見えない。
    模擬では、同じ相場で本当は−30%のとき、入金が無ければ🔴（下落36.8%・リターン−30.0%）、入金があると🟡（下落27.9%）と🟢（リターン+150.1%）になった。
  - 「ドローダウン」は、入金した時点が新しい高値になり、そこから測り直しになる。
  - **出金は、損として数えられる。** 「リターン」は、区間が60日になるまでは🔴にならない（🟡で、マイナスの%が出る）。区間が60日に達した日から、出金が口座の約26%を超えていれば🔴に変わる（出金した日ではない）。
    120日からは約34%、150日からは約37〜41%を超える出金で🔴。「ドローダウン」の警告線は36%で、こちらは一度🔴になると、健康診断を直すまで消えない（実行の全期間の最大を見るため）。どちらの線も、それまでの損益の分だけ動く。
    模擬では、100万円から30万円を出金すると（売買の損は0）、リターンが🔴（−30.0%）になった。40万円なら、ドローダウンも🔴（40.0%）。
    🔴の文は「`.env` の `FXSIM_MAX_LEVERAGE` を下げて `docker compose restart fx`」を指示する。出金のあとにこれに従うと、起きていない損のために、以後の建玉が小さくなる。
  - 「今の建玉」の行の「実効○倍」も、入金のあとは小さく出る（建玉は同じで、口座だけ大きくなるため）。
- `scripts/diagnose_live.py` は、取引ごとの損益を「決済の後の残高 − 建てた時の残高」で出す。模擬では、本当は−2,100円のストップ決済を、入金の分だけ大きな利益として表示し、「プラス圏」と判定した。出金は、同じ大きさの負け取引に見える。
- 画面（`/live`）の「損益」は、いまの純資産 ÷ 実行の最初の残高 − 1 である（`app/server.py`）。模擬では、入金のあと+223.3%と出た。
- **直すための材料。** `equity` の表に、残高と資産が判断のたびに記録されている。建玉が閉じていないのに残高が動いたら、それは入出金である。おおよそは、これでさかのぼって直せる。
  ただし、正確ではない。資産の行は判断の時にしか書かれない（約20時間ごと、および建て・外しの時）。ストップ決済・外部決済・再起動後の整理では、判断の行は書くが資産の行は書かない。
  だから、決済の損益は次の判断の行で初めて残高に出て、その間（最長約20時間）に入金があると、2つは混ざる。約定の値段・スワップ・手数料も記録していない。
  正確に直すには、入出金の日付と金額の控え（所有者のメモか、MT5の口座履歴）が要る。それを `app/db.py` に持たせると、脳が読み込むファイルに触れることになるので、置き場所は別に考える。

**この点検で見つかった、入金で大きくなる弱点（記録のみ。未修正）**

- `decide_once` は、状態ファイルを自分でもう一度読む。ポーリングの側にある「build列の無い行は破れた行として捨てる」検査（`_row_trust`）が、この読み直しには無い。
  読み直しが、建玉の列の途中で切れた行（例：`…,0`）に当たると、建玉0と読み、保有を新規の建てと取り違えて、新しい注文IDで全額の大きさを書く。EAはそれを買い増しとして執行する。
- **これは、上の「入れた時に建玉があれば変わらない」「入れたお金は次に建てる時まで使われない」の、分かっている唯一の例外である。** 起きると、入れたお金は、建玉が終わる前に使われる。
  27.2万円では0.03 → 0.08ロット（+0.05）、入金のあとは0.03 → 最大0.30ロット（+0.27）になった（1回目は模擬の世界、2回目は本物の `decide_once` で再現）。27.2万円では、倍率が1倍に近いと、買い増しではなく一部決済になることもある。
- 5倍の上限の内側ではある。ただし、そのとき、いまのストップは捨てられ、その時の値段 − 1.5×ATR に付け直される（再現では 158.880 → 160.046。値段は160.234）。
  買い足した分には、EAの次の点検（30秒以内）まで、証券会社側のストップが付かない（EAは買い足しをストップなしで出し、次の点検で付ける）。
- EAは一時ファイルに書いてから置き換えるので、破れた行が今も読まれうるのかは、所有者のPCでしか確かめられない（`docs/COVERAGE.md`）。ポーリングの側は、破れた行を読むと `torn read` とログに書く。その行数が、頻度の手がかりになる（§1のイで見る）。台帳に追記した（`docs/COVERAGE.md` の0c）。

## 7. ついでに分かったこと（記録）

本番の脳は shadow では確信度0.6固定なので、リスクの割合は 4%×0.6＝2.4% である。バックテストのハーネスは4%で計算している（§2〜§4の表は、すべて4%）。
効くのはATRが大きい建てだけで（9通りの建て2,329回のうち9回。点検役の計算）、差は小さい：9通りの平均で年率9.17% → 8.89%、SMA2400で15.09% → 14.69%、最大下落はほぼ同じ。
「年約9%」という見通しは変えないが、本番はこの分だけ控えめである。
