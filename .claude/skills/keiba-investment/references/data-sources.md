# データの入手経路と環境制約

**読むタイミング：** 分析を始める前。オッズや出馬表が手元に無い時。

**最重要の原則：オッズと出走表が手元に無い状態で、記憶や推測から数値を作らないこと。**
存在しないオッズを前提にした期待値計算は、単なる間違いではなく、資金を直接溶かす嘘になる。
データが無いなら「データが無いので判断できない」と答えるのが正解。

---

## この実行環境での制約

Claude Code のリモート実行環境では、ネットワークポリシーにより **netkeiba.com / jra.go.jp への直接アクセス（curl・WebFetch）が遮断されている**（CONNECT に 403 が返る）。一方 **WebSearch は利用できる**。

したがって、この環境での既定の運用は次のようになる。

| 用途 | 手段 |
|---|---|
| 出馬表・オッズ | **ユーザーに貼ってもらう**（後述のフォーマット） |
| レースの背景情報・ニュース | WebSearch |
| 過去データの蓄積 | ローカルのCSV／JSONをリポジトリに置く |
| 期待値計算・記帳 | `scripts/` のローカル実行（ネットワーク不要） |

ユーザー自身のPC（ローカルのClaude Code）で動かす場合はこの制約が無いこともある。
**遮断されているかどうかを推測しないこと。** 実際に一度アクセスを試して、結果を見てから判断する。

---

## ユーザーに貼ってもらうときのフォーマット

netkeiba や JRA のアプリから該当レースの画面をコピーして貼ってもらうのが最も速い。整形されていなくても読み取れるので、**「きれいにしてから貼って」と要求しない**（それは分析ではなく作業をユーザーに押し付けているだけ）。

最低限そろっていれば計算できるもの：

```
レース名 / 日付 / 開催 / 距離 / 芝orダート / 馬場状態
馬番, 馬名, 性齢, 斤量, 騎手, 単勝オッズ, 人気
```

あるとエッジの判断が大きく変わるもの：
- 各馬の**近3〜5走**（着順・距離・馬場・上がり3F・通過順・斤量・騎手）
- 馬体重と前走比
- 調教評価
- 当日の他レースの決まり方（内外の有利不利）

**足りない情報があるときは、無いまま推測で埋めずに、何が足りないかを明示して聞く。**

## 本格的にやる場合のデータ基盤

継続運用して統計的な検証まで行うなら、過去データの蓄積が必須になる。1000件規模の検証は、手入力では不可能。

### JRA-VAN DataLab（推奨・公式）
- JRA公式データの正規の配信サービス。月額1,100円程度
- JV-Link（ActiveX/COM）経由で取得するため **Windows 環境が前提**
- PostgreSQL / MySQL 等へ取り込むツールが公式・非公式に用意されている（PC-KEIBA Database など）
- **オッズの時系列**も取得できるのが大きい。確定オッズだけでは検証にならないため、これは決定的な差になる
- 「公式データを規約の範囲で使う」という点で、運用の土台として最も安心できる

### netkeiba のスクレイピング
- 無料で地方競馬まで含めて広くカバーできる
- ただし**利用規約とアクセス頻度への配慮が必須**。過度なリクエストは相手のサーバに負荷をかけるうえ、遮断されて自分のデータ基盤も止まる
- 実務上は「一度取得したものはローカルにキャッシュし、二度取りに行かない」設計にする

### 判断
本気で運用するなら **JRA-VAN DataLab**。理由は月1,100円というコストではなく、**オッズ時系列が取れること**と**規約が明確なこと**。
ペーパー運用の段階（Phase 0）であれば、手貼りのデータでも十分に始められる。

## 検証時の落とし穴（再掲するに値する）

- **確定オッズで検証しない。** 購入可能だった時点のオッズを使う。この一点で、多くのバックテストは無効になる
- **未来の情報を混ぜない。** 特に「レース後に判明する情報」を特徴量に入れてしまう事故（リーク）は、初回の検証でほぼ必ず起きる
- **取り消し・除外馬の扱いを決めておく。** 返還が発生した場合の記帳ルールを事前に決める
- **同じデータで戦略を作り、同じデータで検証しない。** 期間を分けて、片方は最後まで見ない
