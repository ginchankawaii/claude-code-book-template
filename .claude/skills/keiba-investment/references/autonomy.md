# 自走のさせ方

**読むタイミング：** データを自動取得したい時、定期実行を組みたい時、取得が失敗した時。

---

## ループの形

```
run.py scan --date YYYYMMDD     取得・検証・レースJSONを揃える     ← 自動
  ↓
run.py brief --race-id ...      判断材料と「必要確率」を1画面に     ← 自動
  ↓
各馬の p を埋める                近走・馬場・展開・枠・調教を見る     ← 判断
  ↓
ev.py plan --file ...           期待値とケリー配分                  ← 自動
  ↓
ledger.py bet --race-id ...     記帳（購入前に）                    ← 自動
  ↓
run.py settle --date ...        公式払戻から決済し、レポート        ← 自動
```

**pを埋めるステップだけ自動化していない。** これは手抜きではなく、自動化してはいけない箇所だから。
オッズから確率を作ると、期待値は定義上どの馬でも払戻率ちょうど（単勝なら80%）に一致する。
つまり「完全自動で回るループ」を作った瞬間、それは**確実に年20%ずつ資金を溶かす機械**になる。
確率はオッズ以外の情報から来なければ意味を持たない。ここを埋める作業こそが運用の本体である。

将来ここを自動化するなら、必要なのは「予想ロジック」ではなく**過去データで較正済みのモデル**であり、
較正が済むまでは Phase 0 のペーパー運用で回す。順序を逆にしない。

---

## 必要な環境

`fetch.py doctor` が最初にやるべきこと。自走できるかを白黒つける。

```bash
python3 scripts/fetch.py doctor
```

- `race.netkeiba.com` に到達可 → `run.py scan` が使える
- 到達不可 → 下の「遮断されている場合」へ

Python 3.8以降だけあればよく、外部パッケージは不要（`pip install` するものは無い）。

---

## 遮断されている場合

### Claude Code on the web（リモート実行環境）
組織の egress ポリシーで、許可されたホスト以外への通信が遮断されている。
2026-07-26 時点のこのリポジトリのセッションでは、pypi・github は通るが
netkeiba・JRA・JRA-VAN はすべて 403（CONNECT 拒否）で通らなかった。

**対処は、環境のネットワークポリシーを広げること。** 迂回を試みてはいけない
（プロキシのREADMEにも「回避せず報告せよ」と明記されている）。
環境の設定は https://code.claude.com/docs/en/claude-code-on-the-web を参照し、
ネットワークアクセスの設定で以下を許可対象に加える：

```
race.netkeiba.com
www.netkeiba.com
db.netkeiba.com
```

許可後にもう一度 `fetch.py doctor` を実行し、到達可になれば自走できる。

### ローカルのClaude Code
通常このポリシーは無いので、そのまま `run.py scan` が動く。
**パーサの実地検証はこちらで行うのが早い。**

### どちらも無理な場合
`fetch.py import` で手元のCSVから同じ形式を作れる。列は `umaban,name,odds`。

```bash
python3 scripts/fetch.py import --file race.csv --race-id 202601020811 \
    --venue 札幌 --race-no 11 --bankroll 100000
```

これ以降のパイプライン（brief → plan → bet → settle）は取得経路に依存しないので、
スクレイピングが使えなくても運用そのものは止まらない。

## パーサの検証状態

スクレイピングのコードは、相手のHTML構造が変われば壊れる。しかも
**「例外で止まる」ではなく「それらしい別の数字を返す」形で壊れることがある。**
馬券の期待値計算にとって、これは無害な不具合ではなく資金を溶かす嘘になる。

そのため二重に守ってある。

**1. 境界での検証（`validate_*`）**
取得したオッズは Σ(1/オッズ) から控除率を逆算し、15〜32%の範囲外なら例外にする。
頭数の取りこぼし・券種の取り違え・パース失敗は、ほぼこの1つの検査で捕まる。
推測での補完は一切しない。

**2. セルフテスト（`selftest.py`）**
ネットワーク不要。実構造を模したフィクスチャに対してパーサを走らせる。

```bash
python3 scripts/selftest.py
```

ただし**これで潰せるのはロジックの誤りだけで、構造の想定違いは潰せない。**
ネットワークの通る環境で一度 `fetch.py card --race-id <実在のID>` を通すまで、
パーサは「未検証」として扱うこと。壊れていた場合、直すべき箇所は
`fetch.py` の `fetch_card` / `fetch_win_odds` / `_parse_payouts` の3つに閉じている。

## 取得先とマナー

**既定は netkeiba。** ただし無条件に叩くわけではない。

- `robots.txt` を尊重する。禁止されていたら取得せず、その旨を出して止まる。
  無視するオプションは用意していない（公式に認められた経路が別にあるのに、
  規約を踏み越える理由がないため）
- リクエスト間隔は最低2秒（`MIN_INTERVAL`）。短くしたくなったら、遮断されて
  自分のデータ基盤ごと止まることを思い出すこと
- 取得済みはローカルにキャッシュし、二度取りに行かない
  （オッズは動くのでTTL 120秒、出馬表は6時間、結果は24時間）

**本格運用なら JRA-VAN DataLab（月1,100円程度）。**
理由はコストではなく、**オッズの時系列が取れること**と規約が明確なこと。
確定オッズだけでは検証にならない（購入時点で見えていたオッズと違うため）ので、
1000件規模の検証をやる段階になったら、ここが事実上の必須になる。

## 定期実行

開催日の朝に取得、レース後に決済、という2本を回すのが基本形。

**Claude Code の Routine（推奨）**
セッションに紐づけて定期起動できる。Claudeが起きて `run.py scan` を実行し、
briefを読んで p を埋め、記帳まで行う。判断のステップが挟まるので、
cronでシェルスクリプトを回すより、この形の方が素直。

**cron（取得と決済だけを自動化する場合）**
```cron
# 土日の朝9時に当日のレースを取得
0 9 * * 6,0 cd <skill-dir> && python3 scripts/run.py scan --date $(date +\%Y\%m\%d)
# 土日の18時に未決済を決済してレポート
0 18 * * 6,0 cd <skill-dir> && python3 scripts/run.py settle --date $(date +\%Y\%m\%d)
```

どちらの形でも、**pの記入を伴わないレースは自動で買われない**（`ev.py plan` が
p=null の候補を買い目にしないため）。取得だけが自動で走っても、
勝手に賭けが発生することはない。

## データの永続化

リモート実行環境のコンテナは一定時間で回収される。**コミットしていないものは消える。**

- `data/races/*.json` — コミットする（取得したレースの記録）
- `data/cache/` — コミットしない（再取得できる生HTML。`.gitignore` 済み）
- `portfolio/bets.jsonl`, `portfolio/bankroll.json` — **必ずコミットする。台帳が消えると運用実績がゼロに戻る**

scan や settle を実行したら、その日のうちにコミットしてプッシュする。
